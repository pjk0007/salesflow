# 발신 주소별 무작위 예약 발송

대량 명단의 AI 첫 메일을 `회사 조사·본문 작성·저장 → 주소별 무작위 시각에 전송`으로 분리한다. 발신 설정 전체 선택 토글도 같은 `dev` 검토 PR에 포함된다. 운영 반영은 개발자 검토 후 별도 배포 절차로 진행한다.

## 바뀌는 동작

- 하루 한도와 웜업을 기준으로 주소별 오늘 준비할 통수를 정한다. 사용량과 전송 전 예약을 함께 세어 초과 배정을 막는다. 남은 명단은 다음 발송일에 이어서 준비한다.
- 기존 발송 시간대·평일만 설정을 따른다. 시간대가 없으면 KST 09~18시다. 오후에 처음 준비하면 남은 시간에 할당량을 나눈다. 토큰 비용을 미리 쓰는 범위는 오늘 배정한 양이다.
- 하루를 구간으로 나누고 구간 안의 시각을 주소·날짜별로 다르게 정한다. 예약표의 시작 기준과 각 예약을 DB에 저장하므로 재시작해도 이어진다. 문의 몫 10%는 기존 해제 시각 이후의 구간에 배정한다.
- 작성된 본문·서명·수신거부 토큰을 저장한다. 전송 시 AI·회사 조사·토큰 쿼터를 다시 호출하지 않는다. 수신자나 규칙이 바뀌면 본문을 다시 준비한다.
- 실제 전송 직전에 수신거부·회신·반송·명단 보류·발신 정지·한도·요일·시간대를 다시 확인한다. 사용량과 후속 메일 기준 시각도 실제 전송 시 반영한다.
- 예약보다 일찍 전송하지 않는다. 2분 넘게 밀린 예약은 저장 본문을 재사용해 남은 미래 구간으로 다시 배정한다. 자리가 없으면 다음 발송일로 넘긴다. 같은 주소의 연속 전송에도 간격을 둔다.

단건 문의, 수동·템플릿·후속 메일, 하루 한도가 없는 주소는 기존 경로를 유지한다. 한도 없는 주소와 한도 있는 주소를 섞으면 한도 있는 주소의 예약을 먼저 채우고, 나머지는 한도 없는 주소로 기존 방식대로 처리한다. 모든 발신 주소에 하루 한도를 설정해야 전체 대량 발송이 무작위 예약을 따른다.

## 검토와 배포

1. `dev` → `main` 초안 PR에서 검토한다. 자동 병합하지 않는다.
2. 마이그레이션 `0078_email_prepared_sends`는 새 테이블 두 개와 색인을 추가한다. 기존 고객·발신 설정 데이터를 변경하지 않는다. `instrumentation.ts`가 마이그레이션 성공 후 스케줄러를 시작한다.
3. `NODE_ENV=production`이고 운영 주소가 `https://sendb.kr`인 서비스에서는 내부 스케줄러가 자동 시작한다. `EMAIL_SEND_SCHEDULER=off`면 내부 스케줄러만 중지한다. 이 값은 기존 외부 cron 호출이나 모든 메일 발송을 중지하는 스위치가 아니다. 개발 서버에서는 내부 스케줄러가 시작되지 않는다.
4. 준비 작업과 별도로 완료 후 30초마다 예약 전송을 확인한다. 실제 도착 시간은 예약 시각 이후의 첫 실행이며 NHN 응답 시간 등에 따라 차이가 난다. 기존 `/api/email/queue/process`와도 원자적 큐 선점으로 공존한다.
5. 개발 환경은 `sendb-dev` / `sendb-dev-db`를 사용한다. 운영 DB 접근, 실제 고객 발송, R2 삭제 시험 없이 검증했다.

잠금 키: 기존 큐 `0x5c4edf02`, 예약 전송 `0x5c4edf11`, 조직별 예약 배정 `(0x5c4edf12, 조직 해시)`, 수신자 중복 선점 `(0x5c4edf13, 조직·파티션·수신자 해시)`. 기존 후속·반복·여정 작업의 키와 겹치지 않는다.

## 검증 재현

타입 검사와 변경 파일 ESLint, 관련 단위 테스트를 실행한다. 별도 테스트 런타임은 Git에서 제외되는 `.testenv` 아래에만 설치하며 운영 의존성을 추가하지 않는다.

```sh
node node_modules/typescript/bin/tsc --noEmit
node --import tsx --test src/lib/email-random-schedule-rules.test.ts src/lib/email-send-scheduler.test.ts src/lib/email-send-queue-rules.test.ts src/lib/email-sender-limit-rules.test.ts src/lib/email-sender-limit-paths.test.ts src/lib/auto-personalized-email-outcome.test.ts
npm install --prefix .testenv/test-runtime --no-save --no-package-lock @electric-sql/pglite@0.5.8
node --import tsx scripts/check-random-email-schedule.cjs
```

격리 검사는 외부 네트워크를 차단하고 실제 마이그레이션·큐 워커·AI 메일 처리 함수를 인메모리 Postgres에서 실행한다. AI·NHN·수신거부/회신/보류 조회 등 외부 경계만 가짜 구현을 쓴다. 회사 조사·메일 작성, 주소 2개 × 하루 10통, 1,000건 명단의 이틀 분산, 예약 전 전송 0건, 저장 본문 재사용, 실제 전송 시 사용량·후속 예약, 지연 재배정, 수신거부 취소, 오후 첫 준비, 중복 선점을 확인한다. PGlite는 단일 연결이므로 실제 여러 서버 인스턴스의 병렬 운용을 재현하는 부하 시험은 아니다.

## 전송 결과가 불명확할 때

NHN 요청 직후 연결이 끊기거나 서버가 종료되면 `sending` / `uncertain` 예약을 자동 재전송하지 않는다. `log_id`의 발송 로그와 NHN 접수 여부를 개발자가 확인한 뒤 처리해야 한다. 확인 전에 상태만 `ready`로 되돌리면 중복 메일이 나갈 수 있다. 미리 작성했더라도 당일 문의가 한도를 소비하거나 준비·전송이 늦어지면 일부 예약은 다음 날로 넘어갈 수 있으며, 하루 한도는 발송 보장 수량이 아니다.
