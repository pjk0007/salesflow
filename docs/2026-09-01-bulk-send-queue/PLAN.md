# 대량 발송 큐 이전

- **track**: Full
- **날짜**: 2026-09-01

## 왜

2026-09-01 10:37, 파티션 56에 3,000건을 업로드했으나 **29건만 발송**되고 나머지 2,971건이 영구 유실됐다.

### 확정된 원인

운영 DB에서 배치 경계를 복원해 확정했다. `BATCH_SIZE=5`이므로 마지막 배치는 record 291440~291444다.

| 배치 | record_id | 발송 결과 |
|---|---|---|
| n-2 | 291430–291434 | 5건 ✅ |
| n-1 | 291435–291439 | 5건 ✅ |
| **n** | **291440–291444** | **291441·291442·291443만 3건** ❌ |

AI 호출 로그가 정확히 일치한다:

```
10:40:04~05  auto_company_research × 3   (5건이어야 함)
10:40:13~14  auto_personalized_email × 3
10:40:18     auto_company_research × 1    ← 4번째가 14초 늦게 도착
(5번째는 영영 오지 않음)
```

인과 사슬:

1. `new Anthropic({ apiKey })` — **타임아웃 없음** (`src/lib/ai/claude.ts:63,87`)
2. `requestWithRetry`는 **에러가 나야** 재시도한다. 응답이 안 오면 catch 자체가 안 걸린다 (`claude.ts:42-54`)
3. `auto_company_research`는 web search 툴을 써서 최대 4회 연속 API 호출 — 매달릴 표면적이 가장 넓다
4. `Promise.allSettled`는 **모든 promise가 settle돼야** resolve된다. 1건이 매달리면 배치가 끝나지 않는다
5. 다음 배치가 영원히 시작되지 않음 → **2,971건 유실**

### 재발이 아니라 상습이다

| 날짜 | 파티션 | 멈춤 | 재개 | 공백 |
|---|---|---|---|---|
| 08-28 | 55 | 21:59 | 22:12 | 13분 |
| 08-28 | 55 | 22:14 | 22:40 | 26분 |
| 08-31 | 34 | 10:19 | 11:47 | **88분** |
| 09-01 | 56 | 10:40 | — | **영구** |

8월엔 매달린 호출이 결국 응답을 받아 되살아나서 아무도 몰랐다. 9/1은 그 대기 중 12:26 배포가 겹쳐 영구 유실됐다. 같은 배포로 파티션 55·34의 진행분도 함께 날아갔다.

### 타임아웃만으로는 부족하다 — 증거

`processEmailFollowupQueue`는 **구조가 완전히 같다** (`BATCH_SIZE=5` + `allSettled`, 타임아웃 없음). 그런데 누적 **13만 건**을 처리하며 한 번도 문제가 없었다.

차이는 하나뿐이다:

| | 대량 발송 (터짐) | followup (안 터짐) |
|---|---|---|
| 보낼 목록 | **메모리에만** | **DB에 `pending`** |
| 멈추면 | 영구 유실 | 다음 cron이 다시 집어감 |

followup도 매달리면 그 회차는 똑같이 멈춘다. 하지만 큐에 `pending`으로 남아 다음 실행이 이어받는다. **살아남은 이유는 타임아웃이 아니라 "실패해도 되는 구조"다.**

따라서 큐 이전이 본체이고, 타임아웃은 짝으로 같이 넣는다 — 큐가 있어도 타임아웃이 없으면 매달린 회차가 cron 주기 하나를 통째로 날린다.

## 인프라는 이미 있다

새로 만드는 게 아니라 **검증된 길로 옮기는** 작업이다.

- 큐 테이블 패턴 — `email_followup_queue` (sent 107,081 / pending 3,454)
- cron route 패턴 — `CRON_SECRET` 헤더 인증 (`src/app/api/email/automation/process-followups/route.ts`)
- 외부 스케줄러 — **이미 돌고 있다**. 8/30은 업로드 0건인데 `ai_followup` 2,685건이 나갔다

## 범위

### 대상 경로

`dispatchImportTriggers` (`src/lib/record-import.ts:167`). 진입점이 **두 곳**이다:

- `src/app/api/partitions/[id]/records/bulk-import/route.ts:67` (엑셀 업로드)
- `src/lib/scheduled-registration.ts:105` (예약 등록)

### 같은 파일의 더 위험한 코드

`record-import.ts:190-197` — 알림톡·일반 이메일·자동보강은 배치 제한조차 없이 3,000건을 `for` 루프에서 한꺼번에 던진다(`await` 없음). AI 이메일보다 유실 위험이 크다.

**이번 사이클은 AI 개인화 이메일만 큐로 옮긴다.** 나머지는 트리거 규칙을 쓰는 조직이 있는지 먼저 확인하고 별도 사이클로 판단한다. 한 번에 다 바꾸면 회귀 원인이 여러 개가 된다.

### 하지 않는 것

- 미발송분 재발송 (별도 작업, `scripts/resend-unsent.ts` 존재)
- 알림톡/일반 이메일/보강 경로 큐 이전
- followup·repeat 큐 구조 변경

## behaviors

`behaviors.json` 참조. 요약:

1. 업로드는 큐에 INSERT만 하고 즉시 응답한다 (그 자리에서 발송하지 않는다)
2. cron이 `pending`을 꺼내 발송하고 `sent`로 표시한다
3. 워커가 중간에 죽어도 미처리분은 `pending`으로 남는다
4. 동시 실행돼도 같은 레코드를 두 번 보내지 않는다
5. AI 호출이 매달리면 타임아웃으로 그 건만 실패하고 루프는 계속된다
6. 실패한 건은 재시도되며, 무한 재시도하지 않는다

## 설계 확정 필요 (DESIGN에서)

1. **중복 발송 방지** — `processing` 상태 + `FOR UPDATE SKIP LOCKED` vs 조건부 UPDATE. cron 주기가 겹치거나 인스턴스가 2개일 때 같은 행을 두 번 집으면 실제 메일이 두 번 나간다
2. **cron 주기와 1회 처리량** — 3,000건 소진 시간과 CloudType 요청 타임아웃 사이의 균형
3. **stuck 복구** — `processing`에서 죽은 행을 어떻게 되돌릴지 (오늘 배포가 정확히 이 케이스)
4. **재시도 상한** — 몇 회까지, 실패 사유를 남길지
5. **테이블 신설 vs 기존 재사용** — `email_automation_queue`는 "발송 성공 후 반복 예약" 전용이라(`email-automation.ts:234`, `if (success && link.repeatConfig)`) 의미가 다르다. 데이터 0건이지만 재사용은 부적절해 보인다
6. **기존 즉시 발송과의 관계** — 단건 생성(`dispatchAutoTriggers`)도 큐로 보낼지, 대량만 큐로 갈지

## 검증

- 순수 로직(상태 전이·재시도 판정)은 TDD로 고정
- 로컬에서 3,000건 업로드 → 워커 중간 강제 종료 → 재시작 시 이어서 발송되는지 측정
- 동시 워커 2개 실행 → 중복 발송 0건 확인
- 운영 DB는 **조회만** 한다
