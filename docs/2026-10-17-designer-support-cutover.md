# 디자이너하이어 사이트 상담 전환

디하 홈페이지의 상담 버튼과 하단 상담창을 샌드비 수신함에 연결한다. 비회원은 이름을 입력해 문의하고, 로그인한 기업 고객과 디자이너는 자신의 회원 상담으로 연결된다. 사이트 내 기업·디자이너 업무 채팅은 기존 기능을 유지한다.

## 회원 연결

사이트는 Firebase ID 토큰을 `POST /api/messenger/<channelKey>/site-identity`로 전달한다. 샌드비는 설정된 Firebase 프로젝트의 Google Auth REST `accounts:lookup`으로 동일 토큰을 검증한 뒤, **같은 고객 토큰**으로 Firestore `users/<확인된 UID>`의 필요한 필드만 조회한다. Firestore Security Rules가 적용되며 관리자 키·서비스 토큰·운영 DB 직접 접속은 사용하지 않는다.

이름·이메일·고객 ID를 요청 본문으로 받아 본인으로 인정하지 않는다. 현재 UID를 해당 상담 채널의 워크스페이스에만 연결하며, 만료·비활성·철회·다른 프로젝트 토큰과 관리자 역할은 거절한다. 기존 직원 전용 속성은 해제하지 않는다. 기존 리드는 명시된 회원 식별 필드가 하나만 일치할 때 연결한다.

사이트의 카카오(`kakao-…`)·네이버(`naver-…`) 회원 번호를 그대로 사용한다. 네이버 등 Base64 문자가 포함된 회원 번호도 잘라내거나 정규화하지 않고 하나의 문서 경로로 URL 인코딩한다. 경로 구분자·상대 경로·제어 문자는 거절한다.

새 상담과 본인이 인증한 샌드비 상담은 이어 볼 수 있다. 이전 채널톡에서 가져온 상담은 검증되지 않은 고객에게 자동 공개하지 않으며 직원의 ‘이전 상담 기록’에서 확인한다. 내부 메모는 고객 화면에 표시하지 않는다.

## 설정

- 샌드비: `INBOX_FIREBASE_SITE_PROVIDERS`는 `channelKey`, `projectId`, Firebase 공개 웹 `apiKey`를 가진 배열이다. 중복·누락·잘못된 설정은 회원 연결을 차단한다. 비밀 관리자 키를 넣지 않는다.
- 디하: `NEXT_PUBLIC_SUPPORT_PROVIDER=sendb`, `NEXT_PUBLIC_SENDB_SUPPORT_API_BASE`, `NEXT_PUBLIC_SENDB_SUPPORT_CHANNEL_KEY`, `NEXT_PUBLIC_SENDB_SUPPORT_IDENTITY_URL`을 빌드에 지정한다. 회원 인증 URL은 위 샌드비 경로다.
- 상담 채널에 설치 도메인을 정확한 origin으로 등록하고 사용을 켠다. 임의 도메인 와일드카드는 사용하지 않는다.

## 검수

단위 테스트는 Google 검증 실패, 다른 프로젝트, 철회, UID 불일치, Firestore 권한 거절, 역할, 비공개 필드 제외를 확인한다. `node --import tsx scripts/check-firebase-site-identity.cjs`는 소유한 loopback PostgreSQL의 가상 DB에서 실제 인증 API·CORS·반복 로그인·계정 및 채널 분리를 검수한다. Google 및 실제 고객에게 테스트 요청을 보내지 않는다.

사이트 SDK 검수는 비회원 문의, 로그인 병합, 같은 화면 재시도와 초안 보존, 늦게 도착한 계정 A 응답의 계정 B 적용 방지, 로그아웃 시 상담 분리를 포함한다. 실제 배포 검수 결과와 Hosting 이전 버전은 로컬 비공개 배포 기록에 보관한다.

초기 프레임이 준비 제한 시간 뒤 로드되면 같은 프레임에서 자동으로 설정을 교환해 복구한다. 옛 프레임·설정 ACK는 수락하지 않으며, 사이트도 현재 고객의 설정을 시작한 뒤의 준비 완료만 반영한다. 추가 실제 SDK 검수는 전체 26개, 사이트 어댑터 교차 검수는 7개다. Chrome 활성 화면 검수는 별도 운영 배포 기록을 따른다.

## 디하 사이트 내부 상담 화면 (SDK 1.6.0)

디하는 고객 전용 UI와 SDK를 같은 사이트의 정적 파일로 제공하고 SDK가 `srcdoc` 프레임으로 실행한다. 상담 API·파일·회원 인증은 계속 샌드비 서버가 처리한다. Chrome에서 원격 프레임이 빈 화면이 되는 현상을 실제 화면에서 확인한 뒤 이 방식의 문의 전송·직원 답변·새로고침 복구·내부 메모 제외를 검수했다.

`pnpm build:cloudtype` 후 `pnpm build:messenger -- --outdir <절대경로> --api-base https://sendb.kr --channel <공개키>`로 고객 UI만 번들링한다. 생성된 JS·CSS·SDK·HTML을 사이트 public에 넣고 manifest를 보관한다. 빌드 도구는 서버 모듈 혼입을 거절하며 파일 해시·소스 해시·커밋·작업 트리 변경 여부를 기록한다. 비밀 키나 고객 토큰을 정적 HTML에 넣지 않는다.

사이트 SDK 설정의 `messengerPath`는 같은 사이트의 HTML 경로만 허용한다. HTML 로드 실패 후 재시도, 늦게 도착한 이전 계정 HTML 무시, 현재 프레임의 origin·설정 ACK, 기존 원격 설치 호환성을 실제 배포 JS 30개 검사로 확인했다. API 경로 재작성은 `/api/messenger/<키>`에만 적용하며 직원 API는 바꾸지 않는다.

다른 사이트의 채널을 생성하기 전에 정적 파일을 준비하려면 빌드 도구에 `--channel runtime`을 지정할 수 있다. 이 모드는 HTML에 특정 사업 키를 넣지 않고 SDK의 확인된 설정에서 받는다. 기존 고정 키 빌드의 HTML·JS·CSS·SDK 바이트는 유지한다. 백오랩 실제 controller/loader와 이 고객 UI/SDK의 격리 Chrome 검수에서 두 가상 사업의 표시 분리·준비 ACK와 설정 누락 거절을 확인했다. API 응답만 가상이며 CSP로 운영 통신을 차단하고 쓰기 요청을 거절했다. 이 결과는 백오랩 운영 송수신이나 실제 고객 인증 검수가 아니다.

기존 과거 상담·내부 메모·파일의 공개 권한, DB 스키마와 AI 설정은 이 UI 배포에서 변경하지 않는다.

2026-10-17 추가 운영 검수: 현재 브라우저의 기존 Firebase 기업 회원 세션으로 로그인 페이지→회원 대시보드 이동, 회원 상담 인증, 새 문의→직원 답변→문의 목록의 이전 검수 대화 열기→새로고침 복구를 확인했다. 직원 수신함은 ‘연결된 회원’과 기존 CRM 연결을 표시했으며 새 검수 문의를 종료했다. 직원 전용 메모를 저장한 뒤 고객 화면의 최신 종료 상태와 답변을 확인했고 내부 메모는 표시되지 않았다. 새 로그인 자격 증명을 입력하거나 생산 DB에 직접 접속하지 않았다.

이 결과는 이미 로그인된 기업 회원 1계정의 실제 운영 검수다. 새 비밀번호·소셜 로그인 과정, 실제 다른 계정 전환·파트너 계정 검수는 수행하지 않았다. 계정/채널 격리의 가상·격리 API 검사와 구분한다. 이전 채널톡 원본 고객 4,259명은 현재 가져오기 어댑터에서 확인된 외부 회원 ID가 0개로 판정되었으므로 이름/이메일만으로 고객 공개로 승격하지 않는다.

## 운영 사용과 복구

고객은 디하 사이트 하단 상담 버튼을 누른다. 직원은 샌드비 → 고객 상담 → 디자이너하이어 → 전체 상담에서 새 문의를 확인하고 답한다. 과거 채널톡 상담은 이전 상담 기록에 있다. AI 자동 답변 여부는 기존 상담 AI 설정을 따르며 이번 연결 작업에서 자동 응답을 켜지 않는다.

사이트 장애 시 저장한 Firebase Hosting 이전 버전을 복구하면 기존 채널톡 설치 버전으로 돌아갈 수 있다. 새 샌드비 상담 자료는 삭제하지 않는다. 제공자 설정을 수정하려면 공개 환경 설정을 바꿔 다시 빌드한다. Firebase Functions·결제 API·Firestore 스키마는 이 배포에 포함하지 않는다.
