# 샌드비 고객 여정 카드

메일 링크를 클릭해 사이트를 방문한 고객의 한 방문을 Google Chat 카드로 정리한다. 회사·담당자, 유입 메일, 페이지 이동 순서, 페이지별 체류 추정, 영역별 체류 측정, 누른 버튼, 마지막 도달 단계와 CRM 링크를 담는다.

사업별 전용 스페이스:

- [디자이너 하이어 고객여정](https://chat.google.com/app/chat/AAQASH-gyo4)
- [백오피스랩 고객여정](https://chat.google.com/app/chat/AAQAbqhHk2A)

## 표시와 발송 기준

- 메일 열람은 기존 서비스에서 수집하지 않는다. 카드에 `메일 열람 여부: 수집하지 않음 · 링크 클릭 확인`을 표시한다.
- 명시적으로 허용한 워크스페이스의 활성 사이트에서, 해당 워크스페이스의 발송·클릭·CRM 고객과 직접 연결된 방문만 처리한다.
- 최근 48시간의 방문 중 마지막 활동 후 10분이 지난 방문을 정리한다. 기존 사람/기계 방문 판정 함수를 재사용한다.
- 페이지별 시간은 다음 페이지 이동 또는 측정된 세션 종료까지의 간격이다. 마지막 페이지의 측정값이 없으면 `측정 없음`으로 남긴다.
- 영역별 시간은 `SECTION_VIEW.properties.dwell_ms` 합계다. 영역이 함께 노출되면 시간은 겹칠 수 있다.
- 신청·구독·구매 완료 신호가 있으면 완료 카드로 표시한다. 그 외에는 마지막 도달 단계와 `이탈 추정`을 표시하며 이탈 이유를 단정하지 않는다.
- 방문당 카드 한 장이다. 같은 고객의 재방문은 새 카드로 같은 Chat 스레드에 모은다. 이미 정리한 동일 방문의 뒤늦은 이벤트는 기존 카드를 수정하지 않는다.
- 전송 실패는 재시도 가능한 오류에 한해 10분 뒤 다시 시도하며 최대 5회다. 응답 시간 초과는 이미 도착했을 수 있으므로 `uncertain`으로 남기고 자동 재전송하지 않는다. 24시간 넘게 대기한 카드는 닫는다.
- 실제 연결 시험에서 수신 웹훅이 `requestId`를 400으로 거절함을 확인했다. 새 워커에서는 이 옵션을 쓰지 않는다. 같은 방문의 반복 처리는 DB 고유 키로 막는다.

## 현재 작업 환경과 검토 상태 (2026-10-12)

정재훈 님의 개발 전용 작업 지시에 따라 `dev`에서 작업하고 `sendb-dev` / `sendb-dev-db`에서 확인한다. CloudType 프로젝트 URL의 `project:main`은 Git 브랜치명이 아니다. 자세한 작업 규칙은 루트 `AGENTS.md`를 따른다.

- 잘못 병합했던 PR #2·#3은 [PR #4](https://github.com/pjk0007/salesflow/pull/4)로 취소했다. 원격 `main`의 전체 파일이 병합 전 `41c8307`과 같음을 확인했다.
- Claude 복원 작업과 고객 여정·정기 실행 코드는 `dev`에 보존했다. `dev`에서 만든 검토 PR은 초안으로 두고 자동 병합하지 않는다.
- 운영 배포와 고객 여정 자동 전송은 활성화하지 않았다. 기존 운영 환경 변수와 DB는 이 복구 작업에서 변경하지 않았다.
- 개발 DB에도 실제 고객 데이터가 있다. 실제 고객 메일·알림톡·고객 여정 카드를 전송하지 않고, 공유 R2 파일 삭제를 시험하지 않는다.
- 개발 배포는 `sendb-dev`의 브랜치가 `dev`, DB가 `sendb-dev-db`인 것을 확인한 뒤 한다. 배포 완료 여부는 실제 CloudType 배포 결과로 확인해야 한다.

## 개발 검증과 향후 운영 검토

아래는 기능 동작을 이해하기 위한 설정 설명이다. 현재 운영 반영 절차가 아니며, 운영 연결은 개발자 검토와 별도 운영 반영 요청 이후에 진행한다.

1. 배포 시 `0077_customer_journey_alerts.sql`을 기존 마이그레이션 절차로 적용한다.
2. 개발 확인에서는 외부 전송을 끄고 격리된 시험 데이터와 대체 전송 함수를 사용한다. 두 스페이스와 웹훅은 이미 만들었지만 개발 고객 데이터를 실제 스페이스로 보내도록 연결하지 않는다. 웹훅 주소는 저장소·문서에 기록하지 않는다.
3. 허용할 워크스페이스 ID는 해당 환경에서 확인해야 한다. 과거 운영에서 읽은 ID를 개발 DB 확인 없이 재사용하지 않는다. 개발 설정의 기본값은 아래와 같다.

```dotenv
JOURNEY_ALERT_MODE=off
JOURNEY_ALERT_SCHEDULER=off
NEXT_PUBLIC_BASE_URL=https://port-next-sendb-dev-1ru12mlw8nvyar.sel5.cloudtype.app
```

4. 격리된 로컬 시험에서 `dry_run` 카드와 대상을 검증했다. `dry_run`으로 기록한 방문은 나중에 `live`로 바꿔도 소급 전송하지 않는다. 기본값은 `off`다.
5. 정기 실행은 운영 서버 판정과 `JOURNEY_ALERT_SCHEDULER=on` 등 조건을 모두 만족해야 시작한다. 개발 서버에서 꺼져 있는 것이 정상이다. 향후 운영 연결 시 마이그레이션 완료 후 첫 회차는 20초 뒤, 다음 회차는 이전 완료 후 5분 뒤 실행한다. 서버 재시작 시 다시 시작하며 프로세스당 한 번만 등록하고 겹쳐 실행하지 않는다. `GET /api/tracker/journey-alerts/process`는 `CRON_SECRET`으로 인증하면 최근 자동 실행 상태를 반환한다. 같은 경로의 POST와 기존 `POST /api/tracker/deep-alerts/process`는 새 워커를 호출하며 DB 잠금과 방문별 고유 키로 중복을 막는다.

`live`는 기존 운영 서버 판정을 통과해야 한다. 로컬 통합 검증에서만 `JOURNEY_ALERT_TEST_SERVER_LIVE=1`을 쓰며 운영 설정에는 넣지 않는다. 기존 깊이 방문 알림의 설정과 발송 기록은 별개다.

사업별 주소 목록을 지정한 경우 주소 없는 사업은 대기하고 다른 사업의 주소나 공통 웹훅으로 대체하지 않는다. 주소 목록 자체가 잘못되면 `configurationError`를 반환하고 발송을 중단한다. 목록의 키만으로 허용 사업이 늘어나지 않으며, 주소가 있는 사업부터 대기 카드를 조회하므로 연결되지 않은 사업 때문에 발송이 밀리지 않는다. 기존 단일 `JOURNEY_ALERT_WEBHOOK_URL`은 사업별 목록을 지정하지 않은 배포에만 호환용으로 남아 있다.

## 검증

- 기존 main의 발신자 검색·페이지 이동을 보존하고 사업별 발송 경로 및 자동 실행을 통합한 개발 코드에서 전체 단위 시험 921개 통과. 고객 여정 카드 시험 9개와 사업별 주소 설정 시험 6개를 포함한다.
- TypeScript 검사 및 변경 코드 ESLint 통과.
- 자동 실행의 시작 지연, 완료 후 예약, 오래 걸리는 회차의 겹침 방지, 실패 후 재예약, 실행 중 정지 및 운영 설정 조건을 검증하는 시험 5개를 추가했다.
- 격리된 로컬 PostgreSQL에서 가상 고객으로 발송, 같은 방문 중복 방지, 완료/이탈 구분, 기계·진행 중 방문 제외, dry run, 실패 후 재시도, 웹훅의 요청 ID 미사용, 응답 불명확 시 자동 재전송 중지, 두 사업의 스페이스 분리, 연결 누락 사업 대기, 잘못된 주소 목록 중단 등 13항목을 검증했다. 각 실행마다 별도 시험 조직·사업을 만들며 외부 발송은 대체 함수로 수행했다.
- 최적화 프로덕션 빌드 통과. 두 전용 스페이스 각각에 가상 고객 카드를 실제 전송해 성공 응답을 확인했고, 디하 스페이스에서 카드 표시를 확인했다.
- 검증 결과와 가상 카드 JSON/텍스트: `F:/Dev/sendb-recovery-20261011/customer-journey/`.
