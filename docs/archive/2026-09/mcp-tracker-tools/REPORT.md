# REPORT — MCP 트래커 툴 추가

- **사이클 ID**: `2026-09-01-mcp-tracker-tools`
- **track**: Full (PLAN → DESIGN → DO → GAP → REVIEW)
- **완료일**: 2026-09-01

## 한 일

MCP 서버에 **트래커 축**을 노출해 Claude가 퍼널 전환·이탈과 방문자 행동을 직접 조회할 수 있게 했다.

발단은 사용자 질문이었다 — "MCP에 회사·도메인별 행동 지표가 있나?" 확인해보니 기존 툴 10개는 전부 레코드·발송로그·기본 집계뿐이었고, 트래커 데이터는 웹 UI에만 있었다. 실제로는 **"구독신청 과정"·"구독 전환"·"구독 전환 흐름"** 퍼널이 정의돼 있고 이벤트도 4만 건 넘게 쌓여 있었는데 MCP에서 못 봤다.

최종 behavior **15/15 통과**, 테스트 169개 GREEN.

## 실제로 나온 답

PLAN의 발단 질문("구독신청 과정에서 어디서 이탈해?")에 대한 답:

```
방문                3,405명
디자이너 분야 선택      40명  (1.2%)   ← 3,365명(98.8%) 이탈
기본 정보 입력          37명  (92.5%)
요구사항·스킬 지정      34명  (91.9%)
일정·플랜 선택          21명  (61.8%)
신청 내용 확인          19명  (90.5%)
전체 전환율 0.6%
```

**일단 시작하면 90%씩 넘어가는데 시작 자체를 안 한다.** 신청 폼 진입이 병목이다. `biggestDropOff` 필드 하나가 이 결론을 바로 준다.

## 핵심 설계 결정

**(a) 집계 로직을 복제하지 않는다.** 웹 route 안에 있던 것을 `src/lib/tracker/`로 꺼내 웹과 MCP가 공유한다. 이번 작업의 실제 비용은 MCP 툴 작성이 아니라 이 추출이었다.

**(b) `overview` 588줄 중 `aggregateRange`만 뽑는다.** 262줄짜리 `Promise.all` 13갈래까지 빼면 diff가 커지는 게 문제가 아니라 **검증이 불가능해진다** — 13개 위젯 × 세그먼트 조합을 대조할 자동화 수단이 없다. **검증할 수 없는 추출은 하지 않는다.**

**(c) 커밋을 물리적으로 가른다.** 추출(MCP 코드 0줄) → 스코프 해석기(기존 코드 참조 0) → MCP 툴(웹 route 수정 0줄). 커밋 1 직후 회귀를 검증하면 **원인이 반드시 추출**이다.

**(d) 권한은 워크스페이스 축으로 매핑.** 트래커는 도메인 단위라 파티션과 축이 안 맞지만 `tracker_sites.workspaceId`가 있고 워크스페이스당 사이트가 1개(unique 제약)다. folder/partition 스코프는 상위 워크스페이스로 타고 올라간다(사용자 결정).

## 회귀 방어 — 이번 사이클의 실질

추출한 함수를 웹 대시보드와 MCP가 공유하므로, 추출하다 동작이 미묘하게 달라지면 **기존 화면이 조용히 틀린 수치를 보여준다.**

세 겹으로 막았다:

1. **mechanical move** — 함수 본문을 한 글자도 안 고친다. 고치고 싶은 게 보여도(leads 불일치 등) 이번엔 안 건드린다
2. **커밋 분리** — 커밋 1에는 MCP 코드가 0줄이라 수치가 틀리면 원인 후보가 하나뿐이다
3. **jq -S 실데이터 대조** — 추출 전후 웹 API 응답 14건을 키 정렬해 diff

결과: **14건 전부 바이트 단위 동일.** 기간은 2026-05-18~06-29 고정 구간을 써서 새 이벤트 유입 위양성을 배제했고, journey의 `daysSince`는 `Date.now()` 의존이라 제외했다.

## Gap·Review가 잡아낸 결함 3건

### 🔴 1. 직전 기간이 웹과 하루씩 달랐다

**내가 `previousRange`를 "추출"이라고 커밋 메시지에 썼는데 사실이 아니었다.** 웹 어디에서도 쓰이지 않던 것을 새로 작성했고, 그래서 mechanical move의 보호를 못 받았다.

웹은 직전 기간을 route 안에서 인라인 계산하고 있었는데 `toDate`에 `.999`가 없어 `Math.round`가 길이를 1일 크게 잡았다:

| 조회 기간 | 웹(수정 전) | 정확한 값 |
|---|---|---|
| 2026-08-01~08-31 | 2026-**06-30**~07-31 | 2026-**07-01**~07-31 |

즉 **웹이 직전 기간을 하루 넓게 보는 기존 버그**였다. 사용자 판단으로 웹도 `previousRange()`를 쓰도록 고쳤다 — 양쪽이 같은 함수를 부르므로 구조적으로 일치가 보장된다.

**B7의 evidence가 이를 못 잡은 이유**: 대조 대상을 `current`로 잡았는데 그건 진짜 mechanical move라 당연히 일치한다. `previous`·`deltaPct`가 범위 밖이었다.

### 🔴 2. 분모 조사를 지시해놓고 실행하지 않았다

DESIGN §4.3이 스스로 적었다 — *"`Grep "T00:00:00+09:00"`를 돌려 4건 이상이면 조사가 틀린 것이므로 즉시 보고"*. 실제로 돌리니 **6건**이었고, 그중 누락된 `overview/route.ts:52`가 정확히 위 불일치를 만든 지점이었다.

`rangeBounds(...)` 호출 형태만 세고 `new Date(\`...T00:00:00+09:00\`)` 인라인 생성을 놓쳤다.

### 🔴 3. `get_record_journey`가 파티션 경계를 넘었다

`buildRecordJourney`의 `merge` 기본값(true)이 visitor 링크를 타고 다른 파티션 레코드까지 통합하는데, 검사한 것은 진입 레코드의 파티션 하나뿐이었다. 파티션 A 스코프 토큰이 파티션 B 레코드의 이력까지 볼 수 있었다.

`merge: false`로 고정했다. 실피해는 partition 스코프 토큰에 한정되지만, **격리를 코드가 아니라 운영 관행이 지탱하는 상태**였다.

## 배운 것

**1. 교훈을 문서에 적는 것과 실행하는 것은 다르다 — 두 사이클 연속.**

선행 사이클 REPORT가 "분모는 그 값으로 분기하는 모든 표기로 잡는다"고 적었고, 이번 DESIGN이 그에 대응해 값 기반 grep을 **명시적 산출물로 지시**했다. 그런데 그 grep을 실행하지 않았고, 누락된 1건이 정확히 결함을 만들었다.

→ **DESIGN이 "구현 시 재조사하라"고 적은 지시는 체크리스트로 만들어 실행 여부를 기록해야 한다.** 문장으로 남기면 안 돌린다.

**2. "추출했다"와 "새로 만들었다"를 커밋 메시지에서 구별해야 한다.**

`previousRange`를 "4곳 중복이던 것"으로 적었는데 사실이 아니었다. 이 한 줄의 부정확함이 **mechanical move의 보호 범위를 착각하게** 만들었고, 회귀 검증 설계에서 그 함수를 대조 대상에서 빠뜨리는 결과로 이어졌다.

→ 추출 커밋에서 **"옮긴 것"과 "새로 쓴 것"의 목록을 분리해 적는다.** 새로 쓴 것은 mechanical move가 아니므로 별도 검증이 필요하다.

**3. 같은 함수를 웹과 MCP가 공유하면 인증 축의 차이가 권한 구멍이 된다.**

`buildRecordJourney`의 `merge`는 웹(세션 유저)에서 옳은 기본값이지만 MCP(파티션 스코프 토큰)에서는 우회가 됐다. **공유 함수의 기본값은 가장 엄격한 호출자를 기준으로 정하거나, 호출자마다 명시해야 한다.**

**4. 검증 가능성이 추출 범위를 정한다.**

`overview` 588줄 중 `aggregateRange`만 뽑은 것은 diff 크기 때문이 아니라 **13갈래 위젯을 대조할 수단이 없어서**였다. 이 판단은 결과적으로 옳았다 — 만약 전부 뽑았다면 이번에 발견한 직전 기간 불일치가 13개 위젯 어딘가에 섞여 찾지 못했을 것이다.
