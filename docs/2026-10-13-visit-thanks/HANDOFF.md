# 방문 감사 메일 전환 및 구글챗 고객여정 60초 발송 기준

## 재훈님 검토 요약

메일 링크를 클릭하고 사이트 체류가 5초 이상 확인되면 그 사업·이메일의 일반 AI/템플릿 후속과 반복 발송을 멈춥니다. 대신 이름을 넣은 고정 방문 감사 메일을 고객별 한 번만 예약합니다. 사용자가 선택한 발송 시점은 **방문 확인 후 30~60분 사이의 무작위 시각, 평일 한국 시간 09~18시**입니다.

검토 우선순위는 `email-visit-ack.ts`의 대상·중단·한 번 예약, `email-visit-ack-delivery.ts`의 전송 직전 재확인·결과 미확인 처리, `0081` 마이그레이션입니다. 기존 메일 클라이언트·발신 한도·서명·수신거부와 후속 큐를 재사용합니다.

**방문 감사 메일의 기본 설정은 off입니다. 이 작업에서 운영/개발 DB 접근, 실제 고객 메일 전송, 운영 환경 변수 변경 또는 운영 배포는 수행하지 않았습니다.** 저장소의 개발자 검토·운영 반영 절차를 따릅니다.

## 추가 요청: 구글챗은 1분 이상 체류만 발송

- 디자이너 하이어·백오피스랩 고객여정 카드와 담당자 태그, 후속 대응 재알림 모두 **해당 방문의 측정 체류 60초 이상**이어야 발송합니다. 마지막 활동 후 10분 대기는 유지합니다.
- 59초·59.999초·체류 미확인은 제외합니다. 정수 `duration=60`이라도 실제 종료까지 59.999초면 보내지 않습니다. 유효한 종료 시각만 있는 경우에는 그 차이로 확인합니다. 페이지별/영역별 시간을 합산하거나 여러 방문을 합쳐 60초를 만들지 않습니다.
- 기존 대기 카드와 재알림도 전송 전에 같은 기준을 다시 확인합니다. 이미 보낸 카드는 삭제하지 않고 과거 제외 방문을 소급 발송하지 않습니다.
- CRM의 방문·관심도 판정은 유지합니다. 기본 판정은 유효하지만 Chat 기준만 충족하지 못한 방문은 `customer_journey_alerts.status=suppressed`로 보관하며, 현재 CRM 조회는 이를 포함합니다. 별도 DB 마이그레이션이나 환경 변수는 필요 없습니다.
- 방문 감사 메일의 **5초** 기준과 30~60분 예약은 유지합니다. 두 기능은 활성화 조건도 별개입니다.
- 검토 파일: `customer-journey-card.ts`, `customer-journey-alert.ts`, `customer-journey-followup.ts`. 체류 측정은 기존 감사 메일의 계산을 공통 `tracker-session-duration.ts`로 옮겨 재사용합니다.

이름이 없으면 `안녕하세요.`로 인사합니다. AI가 본문을 바꾸거나 고객의 체류 시간·관심 페이지를 언급하지 않습니다. 기존 서명 설정과 수신거부 링크를 붙입니다. 원본 발신 주소·프로필이 삭제되거나 바뀌었으면 다른 주소로 대체하지 않고 미룹니다. 발신 일일 한도·웜업·발송 시간대·명단 보류·규칙 활성 상태도 지킵니다.

## 동작 범위

- 명시적으로 허용한 사업에서 메일 클릭에 직접 연결된 활성 사이트 방문만 판별합니다. 단순 클릭·체류 미확인·5초 미만·봇 클릭·내부 직원/identify·공유 브라우저는 대상이 아닙니다.
- 세션의 측정 체류 또는 종료 확인값을 사용합니다. 페이지 이동 간격·영역 시간 합계로 5초를 만들지 않으며, 반올림된 5초가 실제로는 4.9초인 경우도 제외합니다. 방문 신호가 수집되고 다음 스케줄러가 확인한 시점에 조건이 확정됩니다.
- 같은 사업의 같은 이메일은 중복 CRM 레코드·재방문에도 한 번입니다. 사업과 조직은 분리합니다. 감사 메일 재클릭으로 감사 메일을 다시 만들지 않습니다.
- 이미 있는 대기/보류/처리 중 일반 후속과 반복 큐를 중단하고, 나중에 생긴 후속도 AI 생성 전·HTTP 전·다음 단계 등록 시 재확인합니다. 새 첫 메일과 수동 메일을 임의로 막지 않습니다.
- 답장·수신거부·전환 완료 고객은 감사 메일을 보내지 않습니다. 감사 메일은 저장된 사람 회신을 회신 동기화 모드와 관계없이 확인합니다.
- 예약 시각은 DB에 보관합니다. 업무시간 밖·주말은 다음 평일로 넘깁니다. 발신 한도/보류 등으로 늦어질 수 있으며 5분 넘게 놓친 예약은 다시 분산해 재시작 후 몰아서 보내지 않습니다. 7일 넘게 밀리면 닫습니다. 고객이 다시 활동 중이면 미룹니다.
- 요청 전에 결과 미확인 상태와 발송 로그를 저장합니다. 타임아웃·네트워크 오류·불명확 응답은 자동 재전송하지 않습니다. 확정 거절은 실패로 남기며 자동 재발송하지 않습니다. 필요하면 담당자가 발송 이력을 확인해 수동 대응합니다.
- 기존 후속 목록에서 `방문 감사 / 1회`, 일반 후속의 `(사이트 방문)` 중단 사유와 `결과 미확인` 상태를 볼 수 있습니다. 대기 중 감사 예약을 취소해도 기존 일반 후속이 되살아나지 않습니다.

## 배포·활성화

1. `dev` → `main` 초안 PR에서 검토합니다. 마이그레이션 **0081_email_visit_acknowledgements**를 기존 배포 절차로 적용합니다. 기존 고객/메일 데이터를 소급 변경하지 않습니다.
2. 개발 검증은 기본 `off` 또는 격리 가상 데이터 `dry_run`으로 합니다. 실제 고객 데이터가 있는 개발 환경에서 live를 켜지 않습니다.
3. 운영 반영 승인 후 `sendb`의 환경 변수에 아래 세 항목을 설정합니다. 사업 ID는 **디자이너 하이어·백오피스랩의 실제 ID를 확인**해 넣고, 시작 시각은 **활성화 시점**으로 정합니다. 예시 시험 ID를 운영 설정에 복사하지 않습니다.

| 변수 | 값 |
| --- | --- |
| `EMAIL_VISIT_ACK_MODE` | `live` |
| `EMAIL_VISIT_ACK_WORKSPACE_IDS` | 승인한 두 사업의 ID를 쉼표로 연결 |
| `EMAIL_VISIT_ACK_START_AT` | 활성화 시각의 timezone 포함 ISO 문자열 |

`NEXT_PUBLIC_BASE_URL=https://sendb.kr`, 운영 Node 환경, 메일 스케줄러가 꺼져 있지 않아야 자동 실행됩니다. 새 검사 작업은 기존 AI 준비/예약 전송과 독립적으로 실행하며 겹쳐 실행하지 않습니다. 시작 시각 이전 클릭은 감사 메일로 소급 발송하지 않습니다.

중단 시 `EMAIL_VISIT_ACK_MODE=off`로 바꾸면 새 판별/전송이 멈춥니다. 이미 취소된 일반 후속은 자동 복구하지 않습니다. 기존 데이터를 삭제하거나 대기열을 일괄 되살릴 필요가 없습니다.

## 검증

- TypeScript 및 변경 파일 ESLint.
- 최신 main의 아카이브 증빙 TS 파일이 개발자 개인 PC의 절대 경로를 import해 앱 빌드를 막는 문제가 있어, `tsconfig.json`에서 `docs/archive`만 제외했습니다. 앱 소스의 타입 검사 범위와 strict 설정은 유지합니다.
- 관련 단위 테스트 **462개**: 새 5초/60초 경계·업무시간·문구·명시적 활성화, 독립 스케줄러와 기존 여정/발신 한도/회신/봇 판정 회귀 검사.
- `node --import tsx scripts/check-email-visit-ack.cjs`: 격리 PostgreSQL **17개 시나리오**. 실제 후보/예약/중단 SQL, 중복·조직/사업 격리, 내부/공유/봇, 회신/완료/거부, 선점 전후 취소, 타임아웃/확정 거절, 시간대/지연/기한, 제외 대상 50건 초과, off/dry_run, 마이그레이션 재실행.
- `node --import tsx scripts/check-customer-journey-priority.cjs`: 여정·태그·후속 대응 PostgreSQL **22개 시나리오**. 두 사업 60초 경계·미측정, CRM 보존, 대기 카드 재확인, 재알림 선점 전후 체류 정정도 통과.
- 실제 DB·실제 고객·Google Chat 외부 시험 전송 0건. 운영 DB는 접근하지 않았습니다.
