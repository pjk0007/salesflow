# 조직 전체 이메일 수신거부

## 변경 내용

기존에는 백오피스랩에서 수신거부해도 같은 조직의 오피오에서는 발송할 수 있었다. 이번 변경은 `org_id`를 공통 차단 범위로 사용한다. 다른 조직의 목록은 공유하지 않는다. 기존 `email_unsubscribes`의 모든 사업별 기록이 즉시 공통 차단 기준이 되며, 기록을 삭제하거나 새 표로 복사하지 않는다.

- 사이드바 **수신거부 목록** → `/email/unsubscribes`. 일반 직원도 검색·목록·일괄 조회를 사용할 수 있다.
- 이메일 또는 도메인을 최대 50개씩 조회한다. 이메일은 정확 일치, 도메인은 해당 도메인의 등록된 이메일 기록만 반환한다. 하위 도메인·유사 도메인을 포함하거나 도메인 전체 차단으로 해석하지 않는다.
- 관리자는 정확한 이메일 한 개와 선택 사유를 수동 등록할 수 있다. 등록은 조직 전체에 적용되며 해제 기능은 제공하지 않는다.
- 발송 이력의 NHN **거부**와 수신거부를 화면에서 구분해 설명한다.
- 이메일 대소문자와 앞뒤 공백을 모든 조회·발송 경로에서 동일하게 정규화한다.

## 발송 검사

일반·자동·AI·후속·방문 감사 메일의 사전검사와 대기열 일괄 검사를 조직 기준으로 통일했다. NHN의 `sendEachMail` 직전에도 새로 검사해 AI 생성이나 대기 중 추가된 수신거부를 반영한다. 같은 발송 요청에 여러 수신자가 있으면 한 주소라도 차단된 경우 전체 요청을 보내지 않는다. 조직 정보 누락 또는 조회 오류가 발생해도 외부 제공자에 전달하지 않는다.

공통 검사에는 시험 발송·발신주소 확인·조직 초대·고객 상담 알림/인증·전자서명 메일도 포함된다. Gmail 상담 답장은 등록·인출·발송 승인 시 To/Cc를 재검사하며, 차단되면 취소 상태와 사유를 표시한다.

## 수신거부 링크

주소 우선순위는 `EMAIL_PUBLIC_BASE_URL` → `NEXT_PUBLIC_APP_URL` → `NEXT_PUBLIC_BASE_URL`이다. 서버 실행 시 값을 읽는다. 개발 서비스의 APP 주소가 지정되어 있으면 과거 BASE 값이 운영 주소여도 개발 링크를 만든다. 경로·쿼리·인증정보가 섞인 주소는 오류로 처리한다. 로컬 HTTP는 localhost/loopback만 허용한다.

설정이 모두 없으면 기존 운영 기본값을 유지하되 `NODE_ENV=development`에서는 localhost:3000을 사용한다. 별도 호스트나 포트는 명시적으로 설정해야 한다. 이미 발송된 잘못된 링크의 토큰을 운영 DB로 옮기거나 자동으로 교차 조회하지 않는다.

2026-10-23 CloudType 콘솔에서 공개 주소 값만 읽어 확인했다. 운영은 APP/BASE 모두 `https://sendb.kr`, 개발은 APP만 개발 URL로 설정되어 있고 BASE는 없었다. 기존 코드의 BASE 미설정 시 운영 기본값 사용이 개발 링크 문제의 원인과 일치한다. 설정은 변경하지 않았다.

## DB 변경과 적용 절차

`0123_organization_email_unsubscribe`는 출처용 `workspace_id`를 nullable로 바꾸고 외래키를 `ON DELETE SET NULL`로 교체한다. 사업을 삭제해도 조직의 수신거부가 유지된다. `org_id`와 정규화 이메일 조회 인덱스를 추가한다. 모든 기존 기록·중복 출처·시각·사유를 보존한다. 잠금 대기는 5초로 제한한다.

1. 기능 브랜치 `codex/account-unsubscribe`를 검토한다. 기반은 운영 main의 `5b2737a`이며 dev 전체를 병합하지 않는다.
2. 검토한 변경만 main에 반영한다. Git 반영과 서버 배포는 별개다.
3. CloudType 운영 `sendb`가 Git main을 대상으로 하는지 확인하고 배포한다. 개발에는 운영 DB 설정을 복사하지 않는다.
4. 시작 마이그레이션 `0123` 완료, 적용 커밋, 모든 실행 인스턴스/기존 발송 워커 교체를 확인한다.
5. 직원 계정에서 새 목록과 조회를 확인한다. 실제 고객 대상 시험 발송은 하지 않는다. 운영 DB에서 가상 자료를 생성하거나 테스트하지 않는다.

롤백 시 과거 코드의 사업별 검사로 되돌아간다는 점에 유의한다. 새 인덱스·nullable 출처를 되돌리거나 기존 기록을 삭제하는 SQL은 제공하지 않는다.

## 검증

실제 DB·발송 API를 사용하지 않고 가상 자료/PGlite/가짜 transport로 검사했다.

- `node --import tsx scripts/check-email-unsubscribes.cjs`: 실제 0060→0123 SQL, 과거 기록 보존, 다른 사업 차단·다른 조직 격리, 사업 삭제, 중복 클릭, 원래 사업이 사라진 토큰, 공백 정규화, 큐/고객 여정.
- `node --import tsx scripts/check-email-suppression-transport.cjs`: NHN/Gmail 실제 호출 지점, To/Cc·복수 수신자, 대기 중 수신거부, 조직 누락·조회 실패, 제공자 호출 0건. 기존 플랫폼 11개·상담 이메일 14개 회귀도 포함한다.
- URL 4개, transport 정책 4개, 관리 API 8개, 관리 SQL 1개, 방문 규칙 93개 테스트 통과.
- TypeScript 및 변경 파일 ESLint 통과.
- 로컬 상위 폴더의 다른 lockfile로 standalone 서버 위치가 바뀌지 않도록 `outputFileTracingRoot`를 저장소 루트로 명시했다. Node 24.19.0와 가상 DB/JWT 값으로 배포 빌드·231개 페이지 생성·standalone 패키징 통과. 마이그레이션 125개 포함과 journal SHA-256 `de0a7b537b8547644dfab33dfbbb90bf21cb14d74efb5772e07714dc2ea2ee7f`를 확인했다. 로컬 검수 산출물을 그대로 운영에 올리지 않고 main을 서버에서 새로 빌드해야 한다.
- 실제 관리 페이지 컴포넌트로 가상 화면 검수: 이메일/도메인 결과 표시, 일반 직원 조회와 관리자 등록 폼의 권한 분리 확인. 검수 fixture는 저장소 밖이며 배포에 포함하지 않는다.

기준일: 2026-10-23. 운영 후보 주소 조회 결과는 별도 로컬 확인서에 보관한다. 이 문서는 운영 배포 완료를 뜻하지 않는다.
