# 샌드비 자체 전자서명 구현 계획

2026년 10월 18일 사용자 요청: 모두싸인의 사용 흐름을 REA로 분석하되 API에 의존하지 않고 샌드비가 직접 서명과 도장을 처리한다. 기존 템플릿과 건별 PDF 업로드를 모두 지원하며 이메일과 SMS 발송이 핵심이다. 기능을 추가하기 전에 기존 DB와 운영 구조에 주는 영향을 작게 설계하고 운영 반영 전에 충분히 검증한다.

## 사용자 흐름

1. 고객 상세 또는 전자서명 메뉴에서 서명 요청을 시작한다.
2. 저장된 템플릿을 선택하거나 PDF를 올린다. 같은 편집 화면에서 문서 미리보기와 서명·도장·이름·날짜·텍스트 입력란을 배치한다. 템플릿은 원본과 필드 배치를 함께 재사용한다.
3. 고객 연락처를 불러오고 서명자별 이름과 이메일·휴대폰 번호를 확인한다. 이메일, SMS, 두 채널 중에서 고른다. 두 채널을 골라도 계약과 서명자 링크는 하나다.
4. 발송 전 문서, 받는 사람, 채널, 필수 입력란과 만료일을 한 화면에서 확인한다. 누락이나 설정되지 않은 채널은 발송 전에 알려준다.
5. 받는 사람은 설치나 회원가입 없이 링크를 열고 해당 수신 채널로 받은 확인 코드를 입력한다. 문서를 읽은 뒤 직접 사인을 그리거나 이름으로 도장을 만들거나 자신의 PNG 이미지를 올린다. 빈 입력이나 다른 서명자의 칸에는 서명할 수 없다.
6. 최종 확인과 명시적인 서명 동의를 거쳐 제출한다. 서명 완료 후에는 제출한 내용을 수정하지 않는다.
7. 모든 서명자의 입력이 모이면 완료 PDF를 생성하고 저장·해시 검증을 마친 뒤 완료로 표시한다. 요청자와 서명자는 완료 문서와 확인 기록을 내려받는다.

초기 범위는 문서당 최대 5명, 병렬 및 순차 서명, 만료·거절·요청자 취소, 진행 상태와 발송 결과 확인이다. 대량 자동 계약 발송, 결재 조직도, 외부 공인인증서, 법인 실명 인증, 기존 계약서 마이그레이션은 이번 범위에 포함하지 않는다. 그려서 찍는 서명 이미지와 인증서 기반 디지털 서명을 같은 기능으로 표시하지 않는다.

## 기존 기능에 미치는 영향

모듈 경계는 `components/esign`, `lib/esign`, `/esign`, `/sign/[token]`, `/api/esign/*`다. 기존 CRM은 이름·연락처·고객 ID를 읽어 요청을 시작하는 진입점만 연결한다. 기존 고객, 영업 이메일 규칙, 고객여정, 상담 worker와 테이블은 수정하지 않는다.

전자서명 화면과 수신자 화면에서만 PDF 렌더러를 동적으로 불러온다. 메일·고객 목록·트래커의 공통 번들에는 PDF 라이브러리를 추가하지 않는다. 처리 기능은 기본적으로 꺼져 있으며 필요한 저장소·DB·발송 설정을 확인한 뒤 켠다. 기존 앱 부팅 시 전자서명 데이터 조회나 전체 문서 스캔을 추가하지 않는다.

새 마이크로서비스나 별도 메시지 브로커를 먼저 운영하지 않는다. 전자서명 전용 repository, storage, delivery, PDF 처리 인터페이스로 분리해 필요할 때 DB나 worker를 다른 프로세스로 옮길 수 있게 한다. 작업 중 외부 발송이나 PDF 변환을 기다리며 DB 트랜잭션을 유지하지 않는다.

## 저장과 작업 처리

| 자료 | 보관 방식 |
| --- | --- |
| 원본 PDF, 도장·서명 PNG, 완료 PDF | 계약 전용 비공개 객체 저장소. 개발 검수에서는 격리된 로컬 저장소 |
| 문서와 템플릿 | 원본 키·SHA256·크기·페이지 정보·필드 배치·버전 메타데이터 |
| 계약 요청 | 원본과 필드 버전 스냅샷, 만료일, 상태, 완료 파일 키·해시 |
| 서명자 | 발송 당시 연락처 스냅샷, 역할·순서, 링크 토큰 해시, 확인·서명 상태 |
| 진행 기록 | 요청·열람·인증·동의·서명·거절·취소·완료 시점과 문서 해시 |
| 작업 대기열 | 이메일·SMS·완료 PDF 생성 작업, 중복 방지 키, lease, 시도 횟수와 결과 |

전자서명 전용 메타데이터 테이블 5개를 별도 namespace로 추가한다. 기존 CRM 테이블에 계약 상태 컬럼이나 PDF bytes를 추가하지 않는다. 별도 DB 연결을 설정할 수 있게 하고 연결 수는 소수로 제한한다. 마이그레이션은 명시적인 전자서명 준비 단계에서만 수행한다.

PDF는 최대 10MB·30페이지, 서명 PNG는 크기·실제 형식·픽셀 수를 제한한다. 암호화·파싱 실패·빈 PDF는 업로드 단계에서 거부한다. 처음에는 완료 PDF 생성 동시 작업 1개, 작은 배치의 발송 작업만 처리한다. 동시 실행·작업 lease 만료·중복 완료 요청을 검사한다.

완료 PDF는 원본과 다른 불변 키에 저장한다. 기존 파일이나 완료 파일을 덮어쓰지 않는다. 저장 후 크기와 해시가 확인되기 전에는 계약을 완료로 바꾸지 않는다. 생성 실패 시 재시도 가능한 처리 상태를 표시한다.

## 발송과 수신자 확인

이메일은 기존 NHN 이메일 transport를 재사용하되 계약 전용 문구·결과를 전자서명 모듈이 관리한다. 영업 메일 큐와 후속 메일 규칙에 계약 발송을 섞지 않는다. SMS는 실제 SMS transport를 별도로 추가한다. 현재 코드의 알림톡을 SMS로 대신 표시하지 않는다.

발송 상태는 대기·접수됨·실패·확인 필요를 구분한다. 공급자 응답이 불확실한 요청을 무조건 다시 보내지 않는다. 이메일 성공/SMS 실패 같은 부분 성공을 사용자에게 보여준다. 실제 채널이 설정되지 않았는데 발송 성공으로 표시하지 않는다.

링크는 서명자와 계약에 묶이고 DB에는 해시만 저장한다. 만료·취소·거절·완료 및 순차 서명 대기 상태를 서버에서 확인한다. 확인 코드는 유효 시간, 재발송 대기 시간, 실패 횟수 제한을 갖는다. 링크를 열었다는 이유로 즉시 서명이 승인되지는 않는다.

직원의 문서 조회는 기존 조직·사업 권한을 재사용한다. 계약 파일은 공개 R2 URL을 발급하지 않고 권한을 확인하는 파일 API로 내려준다. 다른 사람의 도장을 자동으로 찍거나 직원이 상대방 대신 서명하는 기능을 만들지 않는다.

## 검수와 운영 반영 조건

가상 고객, 격리 DB, 로컬 파일 저장소, 캡처 전용 이메일·SMS 공급자로 검수한다. 운영 DB·고객·공유 R2 파일을 시험 자료로 사용하지 않는다. 실제 내·외부 수신자에게 보내는 시험은 대상과 목적을 정해 별도로 승인받는다.

필수 검수는 PDF 업로드 → 필드 배치 → 템플릿 저장/재사용 → 이메일·SMS 각각과 동시 선택 → 링크 확인 → 모바일 서명·도장 → 복수 서명자 → 완료 PDF 다운로드의 전체 흐름이다. 오류·만료·취소·중복·재시도와 회전된 PDF, 서로 다른 페이지 크기, 화면 확대/축소를 포함한다.

운영 전에는 타입·린트·관련 자동화 검사, 실제 PDF 시각 비교, 격리 DB 상태 전이·동시성, 브라우저 전체 흐름, PDF 작업의 시간·메모리 한도, 전자서명 모듈을 껐을 때 기존 기능이 동작하는 것을 확인한다. 비공개 저장소·SMS 계정과 등록 발신번호·이메일 발신 설정·서버의 작업 실행 경로가 확인되지 않으면 운영에서 기능을 활성화하지 않는다.

## 모두싸인 분석 근거와 경계

Chrome에서 사용자가 열어둔 모두싸인 작업공간을 읽었다. 사인 입력은 그리기·사인 만들기·업로드, 도장 입력은 일반 도장·법인 도장·업로드 탭으로 구성되어 있었다. 요청 방식에는 단건·대량·링크서명, 별도의 템플릿과 문서함이 있었다. 이 사용 흐름을 참고하되 화면 브랜드·도장 자산·소스 코드는 샌드비 구현에 복사하지 않는다.

이 분석은 선택한 프런트엔드 코드와 실제로 읽은 UI에 한정된다. 서버 구현·인증·법적 효력·전체 서명 처리의 완전한 재현을 입증하지 않는다. 현재 Chrome은 REA용 CDP endpoint를 노출하지 않아 UI 관찰은 CUA로 수행했고, REA는 실행하지 않은 코드의 정적 분석에 사용했다. 원본 코드와 전체 Evidence는 저장소 밖의 `.work/modusign-rea-20261018`에 분리해 보존한다.
