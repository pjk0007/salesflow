# 재훈님 검토용 — 샌드비 자체 전자서명

고객을 선택해 PDF 또는 저장한 템플릿으로 이메일·SMS 서명을 요청하고, 고객이 확인 코드와 서명·도장 입력을 거쳐 완료 PDF를 받는 기능이다. 모두싸인 사용 흐름은 REA와 실제 화면으로 참고했으며 API·계정·유료 요금제·소스·도장 자산은 사용하지 않는다.

## 바뀐 동작

- 전자서명 메뉴와 기존 고객 상세의 **서명 요청** 진입점을 추가했다.
- PDF에서 서명·도장·이름·날짜·텍스트 칸을 배치한다. 템플릿 재사용은 복사 방식이며 기존 계약은 발송 당시 문서 버전을 보존한다.
- 최대 5명에게 동시 또는 순차 요청을 보낸다. 이메일과 SMS를 모두 골라도 한 계약·한 서명자 링크를 사용한다.
- 고객은 회원가입 없이 확인 코드를 받고 직접 서명하거나 이름 도장·본인 PNG를 사용한다. 명시적 동의와 최종 확인 후 제출하며 제출 내용은 수정하지 않는다.
- 완료 파일을 생성·저장·해시 확인한 뒤 완료로 바꾸고 서명자에게 완료 알림을 보낸다. 직원과 확인된 서명자는 완료 PDF와 확인 기록을 내려받는다.
- 미설정 채널, 순차 대기, 만료·거절·취소, 부분 실패·접수 불명을 화면에 구분한다. 불확실한 발송은 자동 재전송하지 않는다.

## 기존 운영에 미치는 영향

기존 CRM·영업 이메일·고객여정 스키마와 발송 큐는 변경하지 않았다. 별도 `esign` namespace의 메타데이터 테이블 5개와 명시적인 `ESIGN_DATABASE_URL`을 사용한다. DB pool은 최대 2개다. PDF와 PNG는 DB에 넣지 않고 계약 전용 저장소에 암호화해 보관한다.

별도 마이크로서비스·브로커를 추가하지 않았다. PDF 처리는 한정된 worker thread로 격리하고 15초 제한을 둔다. DB lease로 완료 PDF는 동시에 1개만 처리하며 발송·저장·변환 중에는 DB 트랜잭션을 유지하지 않는다. PDF.js와 문자표·폰트 자료는 문서 미리보기에서만 읽는다.

기본 `ESIGN_ENABLED=off`이며 기존 앱 부팅에서 전자서명 DB를 조회하지 않는다. 켠 서버는 재시작 후에도 대기열을 이어 처리한다. 메인 마이그레이션 journal은 바꾸지 않았고 전자서명 SQL은 별도 준비 명령으로만 적용한다.

## 검수 근거와 활성화 조건

2026-10-18 실제 연결 준비: 코드 `bfc9b0a`를 `sendb-dev / dev`에 배포해 적용됨·실행 중(1/1)을 확인했다. 명시적인 dev DB 대상과 SQL 해시를 검사한 뒤 전자서명 스키마를 준비했다. 계약 발신 주소는 `ceo@matchesplan.com`으로 등록했고 확인 메일의 실제 수신까지 확인했다. 사용자 지시에 따라 새 계약 저장소는 Cloudflare 없이 기존 NHN Object Storage로 준비 중이며 새 접근 키 발급은 사용자 확인 대기다. SMS 계정은 유효하지만 지정 번호의 등록·명의 증빙이 남아 있다. 실제 계약 요청·OTP·완료 알림 전체 수신 검수 전이므로 전자서명 기능과 worker는 off다. 상세 상태는 [OPERATIONS.md](./OPERATIONS.md#2026-10-18-실제-연결-준비)를 따른다.

실제 발송 준비 변경까지 포함한 최신 자동 검수는 테스트 파일 107개·**1,370개 통과, 실패/건너뜀 0개**다. `ESIGN_EMAIL_SENDER`로 조직 기본 발신자와 별도로 계약 발신 주소를 지정하며, standalone에 명시적으로 실행하는 DB 준비 명령과 postgres 라이선스를 포함한다. 배포용 빌드·타입 검사·standalone 가상 전체 흐름도 통과했다. 승인된 내부 이메일의 발신 테스트는 실제 받은편지함 도착까지 확인했다. 실제 계약 전체 발송과 SMS 발신번호 승인은 별도 확인 대상이다.

최신 저장소 전체 검수는 Node.js 24.19.0에서 테스트 파일 106개, **1,366개 통과·실패/건너뜀 0개**다. 배포용 빌드·타입 검사·224개 페이지 생성, 전자서명 관련 53개 파일 린트도 통과했다. 이번 standalone 서버에서 가상 요청·OTP·서명·완료 PDF 다운로드를 다시 확인했다. 실제 이메일/SMS 수신과 실제 비공개 저장소 연결은 아직 미검수이며 [준비 절차](./OPERATIONS.md#실제-이메일sms를-켜려면)를 따른다. 자세한 실행 환경과 로그는 [최신 전체 검수](./QA.md#최신-저장소-전체-검수)에 기록했다.

Node.js 24.19.0에서 전자서명·격리 SQL·native PostgreSQL·HTTP·PDF worker·한국어 PDF 표시 자원·송신 전 경합 검사 총 77개를 통과했다. 실제 PostgreSQL의 다른 연결 두 개로 중복 서명·취소 경합·잠금·복구를 검사했다. 실제 드라이버 검수에서 발견한 JSONB 이중 직렬화 오류를 수정했다. 확인 코드를 일반 안내보다 먼저 처리하고 claim 이후 취소·만료·코드 변경도 송신 직전에 재검사한다.

PDF는 독립 Poppler 12회 렌더링·방향/위치 확인점 96개가 일치했고 입력란 밖 픽셀 변경이 없었다. 브라우저에서는 가상 자료만 사용해 템플릿 저장·복사, 두 채널 요청, 모바일 OTP·그리기·이름 도장·PNG·한글 입력·동의·완료 PDF/기록 다운로드를 확인했다. 상세 증거와 최종 빌드·한국어 CID 결과는 [QA.md](./QA.md)에 기록한다.

최종 운영용 빌드의 타입 검사와 224개 페이지 생성도 통과했다. 실제 standalone 실행에서 화면 자원·한국어 PDF 표시 자원과 기능 off 상태를 확인했다. 계약 전체 이미지 예산을 동시 서명 저장과 함께 검사하며, 브라우저도 최대 입력란 수에 맞춰 이미지를 정규화한다. 최신 서버 코드로 한글 계약서의 전체 화면 흐름과 완료 다운로드를 다시 검수했다.

운영 활성화에는 전용 메타데이터 DB·비공개 저장소·전용 비밀 값·NHN SMS 계정 및 등록 발신번호가 필요하다. 실제 수신은 아직 검수하지 않았으며 승인된 내부 이메일·휴대폰으로 요청·OTP·완료 알림을 확인한 뒤 실제 고객에게 연다. 이미지 전자서명 방식이며 공인 인증서·법인 실명 인증·대량 발송은 이번 범위에 포함하지 않는다.

2026-10-18 사용자 확인: SMS·발신번호와 계약용 비공개 저장소는 아직 준비되지 않았다. 운영 기능은 켜지 않으며 준비 요청 항목을 OPERATIONS 문서 첫 부분에 정리했다.
