# 자체 전자서명 운영 준비

구현 계획과 범위는 [PLAN.md](./PLAN.md), 검수 결과는 [QA.md](./QA.md)를 참고한다. 모두싸인 계정이나 유료 API를 연결하지 않는다. 문서·도장·서명·완료 PDF는 샌드비가 처리하고, 발송에는 기존 이메일·알림톡 공급자를 사용한다. 기존 SMS 구현은 선택 사항이다.

## 최신 발송 구성: 이메일 + 기존 알림톡

사용자가 이메일과 기존 알림톡 이용을 요청했다. **SMS 명의 인증·발신번호 등록은 이 조합의 필수 조건이 아니다.** 아래 과거 SMS 준비 이력과 구분한다.

디자이너하이어 채널의 전자서명 요청·인증·완료 템플릿 3종은 심사 신청을 마쳤고 모두 검수 중이다. `ESIGN_ALIMTALK=on`과 `ESIGN_ALIMTALK_SENDER_KEY`로 개발 서비스에 연결한다. 기존 조직 계정/활성화 값과 기존 자동화는 변경하지 않는다. 승인 전에는 이메일 단독으로 사용하며 알림톡은 요청 생성과 실제 송신 단계 모두 차단한다. 승인 상태·발신 채널을 화면에서 확인한다. 내용·설정·제한은 [ALIMTALK.md](./ALIMTALK.md)를 따른다.

## 현재 준비 상태와 재훈님 요청 항목

### 2026-10-18 실제 연결 준비

사용자 요청에 따라 새 계약 저장소에는 Cloudflare를 사용하지 않는다. 기존의 다른 샌드비 파일 설정은 변경하지 않았다. 실제 설정 작업은 `sendb-dev / dev`에서만 진행하며 `main`과 운영 DB에는 접근하지 않는다.

- 코드 `bfc9b0a`를 개발 서비스에 배포하고 적용됨·실행 중(1/1)을 확인했다. 명시적인 전자서명 DB 연결, 전용 비밀 값, 개발 서명 origin과 `ESIGN_EMAIL_SENDER=ceo@matchesplan.com`을 등록했다.
- DB 호스트가 `sendb-dev-db`이고 명시적인 두 dev 연결이 같은지 확인한 뒤, 승인된 SQL 해시와 배포 파일을 검사해 `esign` 전용 스키마 준비 명령을 실행했다. 완료 메시지를 확인했으며 고객 테이블은 조회하거나 변경하지 않았다.
- 계약용 발신 프로필을 dev에 저장하고 NHN 발신 확인 메일의 실제 받은편지함 도착을 확인했다. 조직 전체 기본 발신자는 바꾸지 않았다. 계약 요청·OTP·완료 알림 전체 수신 검수는 아직 남아 있다.
- 기존 NHN 프로젝트에 계약 전용 컨테이너 `sendb-esign-dev-20261018-21ba51`을 생성하고 `PRIVATE`를 확인했다. 사용자 승인 후 S3 키 1개를 발급해 개발 서버 비밀 설정에 준비했다. NHN은 조건부 객체 PUT을 지원하지 않아 `content-addressed` 저장 방식을 추가했다. 실제 암호화 저장·읽기·버전 분리·기존 암호문 보존·다른 내용의 덮어쓰기 차단을 통과했다. CloudType 앱의 현재 설정에는 영구 디스크 추가 옵션이 보이지 않아 임시 디스크를 계약 보관용으로 사용하지 않는다.
- 기존 NHN SMS 계정과 키는 유효하지만 지정한 발신번호는 공식 조회 API에서 등록되지 않은 상태다. 실제 등록 화면의 개인정보 수집 동의 단계까지 준비했다. 명의자 본인 인증과 번호 명의 증빙은 사용자가 완료해야 하며 문자 발송은 켜지 않았다.

코드 `399e914`를 `sendb-dev / dev`에 배포해 적용됨·실행 중(1/1)을 확인했다. NHN 저장소 설정과 `ESIGN_S3_WRITE_MODE=content-addressed`, `ESIGN_ENABLED=on`, `ESIGN_WORKER=on`을 개발 서비스에 반영했다. 실제 인증된 상태 API는 `enabled/emailReady/databaseReady/storageReady=true`, `smsReady=false`, `issues=[]`다. 재배포 전에 저장한 암호화 시험 파일도 다시 읽혔다. 기존 다른 발송 worker의 off 설정과 운영 `main`은 유지했다.

실제 계약 요청·OTP·완료 알림 전체 수신 검수는 아직 미완료다. 승인된 내부 주소만 수신하는 법적 효력 없는 시험 PDF를 준비했지만 Chrome 확장프로그램의 로컬 파일 URL 접근 권한이 꺼져 자동 파일 선택이 막혔다. 샌드비 업로드 API의 실패로 기록하지 않는다. 브라우저 도구는 `chrome://extensions` 열기도 정책상 거절해 사용자가 해당 권한을 직접 설정해야 한다. SMS는 대표자 개인 명의 번호로 확인했고 명의자 본인 인증·필요 서류 제출이 남아 있다. 개발 가상 체험은 계속 사용할 수 있다.

### dev에서 가상 자료로 먼저 체험하기

[dev 전자서명 체험](https://port-next-sendb-dev-1ru12mlw8nvyar.sel5.cloudtype.app/esign?preview=1)에서 로그인 후 디하·백오랩 가상 계약서와 이메일/SMS 발송함을 사용할 수 있다. **고객 서명 화면 열기 → 확인 코드 받기 → 표시된 체험용 코드 입력 → 도장·이름·날짜 입력 → 동의·제출 → 완료 PDF** 순서다. 새 요청은 준비된 한글 템플릿과 `customer@isolated.example.test`, `01000000001`을 사용한다.

`sendb-dev`에만 `ESIGN_PREVIEW=on`을 설정한다. 서버의 공개 주소가 지정된 dev origin과 정확히 일치할 때만 별도 `/api/esign-preview` 경로를 사용할 수 있다. 기존 `ESIGN_ENABLED`는 off로 유지한다. 체험용 런타임은 실제 상태 전이·파일 암호화·PDF worker를 재사용하지만 메타데이터와 파일은 메모리에만 두고 공급자 전송은 캡처만 한다. 고객 DB·S3·SMS 계정·등록 발신번호가 없어도 체험할 수 있으며 서버 재시작 시 초기화된다. 저장은 총 24MiB, 문서 80건·요청 40건·가상 사업 공간 20개로 제한한다. 실제 고객·계약서·본인 도장은 넣지 않는다.

이 개발 체험의 배포와 실제 고객 대상 운영 활성화는 별개다. 운영 준비 항목은 아래와 같다.

2026-10-18 사용자가 SMS 계정·등록 발신번호와 계약용 비공개 저장소가 아직 준비되지 않았다고 확인했다. 따라서 운영 활성화와 실제 발송 검수는 남아 있으며 기본 비활성 상태로 개발 검토한다.

1. SMS: NHN SMS 계정의 App Key·Secret Key와 등록을 마친 회사 발신번호를 준비한다. 기존 알림톡 키로 자동 대체하지 않는다.
2. 파일: 계약용 비공개 S3 호환 저장소와 읽기·새 객체 쓰기 자격증명을 준비한다. 기존 공개 파일 URL을 계약서 저장 방식으로 사용하지 않는다.
3. DB·키: 전자서명용 DB 연결과 32자 이상 전용 비밀 값을 서버 비밀 설정에 등록한다. 초기 스키마를 명시적으로 적용한다.
4. 실수신 검수: 사용자가 지정한 내부 이메일·휴대폰으로 서명 요청·확인 코드·완료 알림과 PDF를 확인한다.

등록할 정확한 변수 이름과 순서는 아래 표를 따른다. 비밀 값은 채팅이나 저장소로 전달하지 않는다. 위 항목 확인 전에는 실제 고객에게 서명 요청을 보내지 않는다.

### 실제 이메일·SMS를 켜려면

- 이메일은 샌드비 **이메일 → 설정**(`/email?tab=settings`)의 조직 NHN Email 계정을 재사용한다. `ESIGN_EMAIL_SENDER`를 지정하면 해당 조직에 등록된 주소로 계약 메일만 보내고, 미지정 시 조직 기본 발신자를 사용한다. 지정한 주소가 해당 조직에 없으면 다른 주소로 대체하지 않는다. 사업별 발신자를 따로 선택하는 화면은 없다. 이미 사용하는 계정도 계약 요청·확인 코드·완료 알림의 실제 수신 검수는 따로 한다.
- SMS는 NHN Cloud의 **SMS 서비스**에서 명의자 인증과 발신번호 사전 등록을 마쳐 승인된 회사 번호를 준비한다. App Key·Secret Key·발신번호를 아래 `ESIGN_SMS_*` 설정에 등록한다. [NHN 공식 등록 절차](https://docs.nhncloud.com/ko/Notification/SMS/ko/console-guide/)를 따른다.
- 두 채널 모두 계약용 DB·비공개 파일 저장소·전용 비밀 값과 worker가 필요하다. SMS 준비가 늦으면 이 공통 설정을 마친 뒤 이메일 단독으로 먼저 검수할 수 있다.
- 실제 요청은 `/esign`에서 보낸다. `?preview=1` 체험은 위 설정을 넣더라도 계속 가상 발송함만 사용하며 실제 이메일·SMS로 전환되지 않는다.
- 준비 상태의 **발송 가능** 표시는 설정 존재 여부를 검사한 결과다. 키의 유효성·공급자 승인·상대방의 실제 수신까지 보장하지 않는다. 승인된 내부 수신자에게 요청 → 확인 코드 → 서명 → 완료 알림·PDF 순서로 실수신을 확인한 뒤 사용한다.

## 사용자 사용 순서

1. **전자서명 → 서명 요청** 또는 고객 상세의 **서명 요청**을 연다.
2. PDF를 올리거나 템플릿을 선택한다. 서명자 번호를 지정해 서명·도장·이름·날짜·텍스트 칸을 놓는다. 템플릿을 선택하면 건별 문서를 복사하므로 원본 템플릿을 바꾸지 않는다.
3. 받는 사람의 이름과 연락처, 이메일·SMS·둘 다를 선택한다. 여러 명은 동시에 받기 또는 순서대로 받기를 선택한다.
4. 문서·필수 칸·받는 사람·만료일을 마지막으로 확인하고 요청한다. **접수됨**은 발송 공급자가 접수했다는 뜻이며, 상대방에게 실제 도착했다는 보장은 아니다. 채널별 실패·확인 필요를 상세에서 확인한다.
5. 수신자는 링크에서 확인 코드를 받아 문서를 연다. 직접 그린 사인, 이름으로 만든 도장, 본인의 PNG 중 하나를 넣고 필수 칸을 채운다. 서명 동의와 최종 확인을 거쳐 제출한다.
6. 모든 서명이 모이면 완료 PDF를 생성한다. 저장과 해시 확인 후 완료로 표시하고 서명자에게 같은 링크로 완료 알림을 보낸다. 요청자는 상세에서 완료 PDF와 확인 기록을 내려받는다.

확인 코드는 5분, 확인 후 문서 접근 세션은 30분이다. 재요청은 60초 이후이며 코드 오입력은 5회까지다. 문서당 서명자는 최대 5명이다. 국내 SMS 번호를 지원한다. 일반 전자서명 이미지 방식이며 인증서 기반 디지털 서명 기능은 이번 범위에 포함하지 않는다.

## 설정과 준비 순서

새 설정값은 비밀 관리 화면에서 주입한다. 값이나 DB URL을 Git·PR·메신저에 쓰지 않는다.

| 설정 | 용도 |
| --- | --- |
| `ESIGN_ENABLED=off` | 초기 기본값. 준비 전에는 기존 기능만 실행한다 |
| `ESIGN_DATABASE_URL` | 전자서명 메타데이터 전용 PostgreSQL 연결. 기존 `DATABASE_URL`을 자동 사용하지 않는다 |
| `ESIGN_SECRET` | 32자 이상 전용 비밀 값. 파일 암호화와 확인 코드 보호에 사용한다 |
| `ESIGN_S3_ENDPOINT`, `ESIGN_S3_BUCKET` | 계약 전용 비공개 객체 저장소. endpoint는 HTTPS |
| `ESIGN_S3_ACCESS_KEY_ID`, `ESIGN_S3_SECRET_ACCESS_KEY` | 해당 저장소의 읽기·새 객체 쓰기 권한 |
| `ESIGN_S3_REGION` | 공급자에 맞는 region. 기본 `auto` |
| `ESIGN_S3_WRITE_MODE` | 기본 `conditional`. NHN처럼 조건부 PUT이 없는 공급자에는 `content-addressed`를 명시한다 |
| `ESIGN_PUBLIC_ORIGIN` | 실제 서명 링크의 HTTPS origin. 운영 기본값 `https://sendb.kr` |
| `ESIGN_SMS_APP_KEY`, `ESIGN_SMS_SECRET_KEY`, `ESIGN_SMS_SENDER` | NHN Cloud SMS 계정과 등록 발신번호. 기존 알림톡과 별도 |
| `ESIGN_ALIMTALK=on` | 기존 조직 알림톡을 전자서명에 사용하는 전용 opt-in. 미지정 시 off |
| `ESIGN_ALIMTALK_SENDER_KEY` | 기존 카카오 발신 채널 고정. 미지정 시 조직 기본 채널. 템플릿 3종 승인 필요 |
| 기존 조직 이메일 설정 | 조직별 NHN Email 계정·발신 프로필을 재사용한다 |
| `ESIGN_EMAIL_SENDER` | 선택 사항. 해당 조직에 등록된 전자서명 전용 발신 주소. 기존 전체 메일의 기본 발신자를 바꾸지 않는다 |
| `ESIGN_WORKER=on` | 준비 완료 후 활성화. 재시작 때도 작은 전자서명 작업 배치를 이어 처리한다 |

로컬 검수에서만 `ESIGN_STORAGE_DIR`를 사용할 수 있다. 운영에서는 영구 비공개 객체 저장소가 필요하다. 비공개 저장소에도 암호문만 저장하며, 파일은 인증된 API로 내려준다. 파일 저장소와 메타데이터 DB, 비밀 값은 함께 백업해야 한다. 비밀 값을 임의로 바꾸면 기존 파일을 읽을 수 없으므로 키 교체는 별도 이관 작업으로 처리한다.

`content-addressed` 방식은 암호문 SHA256을 객체 이름 끝에 포함해 각 저장 버전을 별도 객체로 보관한다. 같은 주소에는 그 해시와 일치하는 암호문만 전송하며 읽을 때도 암호문 해시·AES-GCM·평문 해시를 확인한다. 같은 논리 경로를 다시 저장해도 이전 참조는 변경되지 않는다. 서명 재제출 판별은 파일 경로 대신 내용 해시를 사용하므로 재시도도 처리된다. 공급자 오류가 나면 기존 저장 방식을 자동으로 바꾸지 않는다. 이미 계약이 있는 저장소의 모드를 임의로 바꾸면 이전 주소 형식과 달라질 수 있으므로 별도 검수·이관 없이 변경하지 않는다. DB에는 파일이나 추가 테이블을 넣지 않는다.

1. `ESIGN_ENABLED=off`로 코드를 배포한다. 기존 고객·메일·트래커 동작을 확인한다.
2. 전자서명 전용 DB를 준비하고 `ESIGN_DATABASE_URL`만 명시한 상태에서 `pnpm esign:migrate`를 실행한다. `drizzle/esign/0001.sql`만 적용하며 기존 메인 마이그레이션 journal은 변경하지 않는다.
3. 전용 저장소·키·SMS·발신번호·조직 이메일 설정을 준비한다. 객체 읽기·불변 쓰기와 서버 재시작 후 보존을 격리 문서로 확인한다.
4. `ESIGN_ENABLED=on`, `ESIGN_WORKER=on`으로 켜고 서버를 재시작한다. 전자서명 화면의 준비 상태와 채널별 발송 가능 여부를 확인한다.
5. 사용자가 지정·승인한 내부 이메일과 휴대폰으로 요청·OTP·서명·완료 알림을 확인한다. 이 단계가 끝나기 전 실제 고객에게 열지 않는다.

`build`와 `build:cloudtype`은 PDF worker를 먼저 만들고 standalone 서버에 PDF worker·라이선스·전자서명 SQL·공개 화면 자원을 함께 넣는다. 서버는 Node.js 22.13 이상이 필요하다. PDF.js는 브라우저 미리보기에서만 동적으로 불러온다. 비내장 한국어 CID 폰트와 일부 PDF 이미지 형식에 필요한 공식 문자표·표준 글꼴·WASM 자료도 버전별로 보관한다(6.4.299 기준 약 3.36MiB). 이 공개 정적 자료 API는 DB 연결이나 서명 worker를 시작하지 않으며 필요한 파일만 브라우저에서 읽는다. 라이선스도 배포 자료에 보존한다.

CloudType 등의 standalone 컨테이너에서는 개발용 `scripts/`와 별도 postgres 패키지가 없으므로 배포에 포함한 `node .esign-runtime/migrate-esign.cjs`를 사용한다. postgres 드라이버와 라이선스를 함께 보관하며 `ESIGN_DATABASE_URL`이 없으면 연결하지 않고 종료한다. 준비 명령은 서버 시작이나 앱 요청에서 자동 실행되지 않는다. 별도 DB 서버가 필요하지 않다면 명시적으로 확인한 dev DB 안의 `esign` namespace에 5개 전용 테이블을 준비할 수 있다. 기존 고객 테이블은 변경하지 않는다.

현재 CloudType Standalone 배포의 터미널은 빌드 출력 디렉터리 `/app`에서 시작하며 실제 standalone 루트는 `/app/standalone`이다. 이 배포에서는 `node /app/standalone/.esign-runtime/migrate-esign.cjs`로 실행했다. 플랫폼 설정에 따라 경로가 달라질 수 있으므로 실행 전 파일 존재·SQL 해시·개발 DB 대상부터 확인한다.

## 운영 부담과 복구

메타데이터 연결 pool은 최대 2개이며 파일·발송·PDF 변환을 기다리는 동안 트랜잭션을 잡고 있지 않는다. 한 배치는 최대 4개 작업을 처리하고 15초 뒤 다시 확인한다. 요청 직후에는 같은 작은 배치를 바로 실행한다. 처리 순서는 확인 코드 → 완료 PDF → 완료 알림·서명 요청이며 같은 순위에서는 먼저 준비된 작업부터 처리한다. 대기 중 코드가 일반 안내 뒤에 계속 밀리는 것을 피한다. 송신 직전에 취소·만료·코드 변경을 재검사하지만 이미 진행 중인 공급자 요청을 취소하는 기능은 아니다. 만료 정리는 배치당 최대 5건이다. 완료 PDF 작업은 DB lease로 동시에 1개만 허용한다. PDF 업로드 검사는 프로세스 내 1개 실행·4개 대기로 제한한다.

PDF worker는 15초 제한, V8 old heap 128MB·young heap 16MB이며 실행 후 종료한다. 이 heap 설정은 프로세스 전체 RSS의 강제 상한을 뜻하지 않는다. 원본은 10MB·30페이지, PNG 한 장은 1MB·2백만 픽셀, 계약 전체의 고유 이미지는 8MiB·800만 픽셀, 완료 PDF는 25MB로 제한한다. 전체 이미지 예산은 서명을 저장할 때 원자적으로 확인하며, 브라우저 입력은 한 칸당 80,000픽셀·83,886bytes 이하로 정규화한다.

발송 중 응답이 유실되면 **확인 필요**로 남기며 자동으로 재발송하지 않는다. 완료 PDF는 최대 3회까지 제한적으로 재시도하며 검증 전에는 완료로 표시하지 않는다. 완료 파일을 덮어쓰거나 기존 고객을 삭제하는 복구 작업은 없다. 문제가 생기면 `ESIGN_ENABLED=off`, `ESIGN_WORKER=off` 후 재시작해 새 전자서명 처리를 중지한다. 이미 공급자에게 접수한 메일·SMS는 되돌릴 수 없다.

## 격리 검수 실행

일반 검사는 `node --import tsx --test src/lib/esign/*.test.ts`로 실행한다. native PostgreSQL 검사는 테스트 파일에 명시한 새 loopback 검수 DB에만 opt-in할 수 있다. 실제 운영·개발 DB URL을 넘기면 안 된다.

로컬 UX 검수는 `ESIGN_QA_ALLOW_FAKE=yes`를 명시한 `node --import tsx scripts/esign-local-qa.ts`로 실행한다. 이 서버는 `127.0.0.1:3158`만 듣고 3159의 실제 Next 화면을 보여준다. API는 격리 PGlite와 임시 암호화 파일을 사용하며, 이메일·SMS는 발송하지 않고 가상 outbox에만 쌓는다. `*.example.test` 이메일과 `01000000xxx` 전화번호 외에는 캡처 공급자도 거부한다. `/__qa/*` 경로는 이 로컬 스크립트에만 있고 운영 Next route에는 포함되지 않는다.
