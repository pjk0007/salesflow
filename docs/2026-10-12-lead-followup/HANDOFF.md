# CRM·구글챗 리드 기준 통일과 담당자 후속 대응

## 재훈님 검토용 요약

기존 핵심 리드 화면은 방문·체류·클릭 수 중 하나만 충족해도 리드로 분류해 구글챗의 행동 판정과 달랐습니다. 이제 화면과 챗이 같은 저장 판정의 등급·점수·근거를 사용합니다. 고객별로 미확인 → 연락 예정 → 연락 완료 → 상담 진행 상태와 예정 시각·메모·수정 이력을 관리할 수 있습니다. 강한 핵심 리드 중 미확인 24시간 경과 또는 연락 기한 초과 건만 지정 담당자에게 재알림합니다.

`dev` → `main` 초안 PR #6에서 검토합니다. 이 변경에는 **0079 마이그레이션**이 필요합니다. 앞서 같은 PR에 포함된 메일 예약 기능의 **0078**도 함께 확인해 주세요. 운영 병합·배포와 실제 고객 전송 시험은 수행하지 않았습니다.

## 사용자에게 보이는 동작

- 메일 대시보드의 **핵심 리드 · 후속 대응**: 사업·처리 상태·연락 기한 초과 필터, 등급·점수·행동 근거·담당자·연락 예정 시각, 상태 관리 창.
- 고객 여정 화면의 **리드 판정 · 후속 대응**: 같은 판정과 근거, 상태·예정 시각·메모 수정, 최근 20건의 수정자·시각·처리 이력.
- 구글챗 카드의 **처리 상태 관리** 링크에서 로그인한 샌드비 고객 여정 화면으로 이동합니다. 기존 웹훅 카드를 직접 수정하는 방식은 아닙니다. 새 방문/재알림 카드에는 그때의 상태·예정 시각을 표시하며, 과거 카드에서 현재 상태는 링크로 확인합니다.
- 예정 시각은 한국 시간으로 입력하고 UTC로 보관합니다. 연락 예정 상태에는 시각이 필수이며, 다른 상태로 바꾸면 예정 시각을 제거합니다.
- 대응 메모는 샌드비와 CRM 이력에 보관합니다. Google Chat 본문에는 메모를 보내지 않습니다.
- 같은 사업의 같은 수신 이메일은 중복 CRM 레코드·재방문에도 상태를 공유합니다. 사업·조직은 분리합니다. 담당자는 기존 승인된 스페이스 연결에 따라 디하 이효정 / 백오피스랩 양윤지입니다. 상태를 수정한 사람은 별도로 기록합니다.
- 동시에 수정하면 먼저 저장한 내용을 유지하고, 뒤의 저장에는 최신 상태를 다시 확인하도록 안내합니다. 저장 실패 시 작성한 입력을 유지합니다.

## 판정 통일

`customer_journey_alerts.message.journeyPriority`가 공통 판정 원본입니다. CRM API가 방문/클릭 수로 별도의 리드 점수를 만들지 않습니다. 같은 사업·고객의 최근 30일 최신 유효 방문 판정을 보여주며, 최신 방문이 일반 방문이면 과거 긴급 판정으로 계속 표시하지 않습니다. 기본 목록은 관심 높음·핵심 리드 최대 50명, API 한도는 200명입니다.

워커와 CRM은 `customer-journey-source.ts`의 동일한 후보·필드·이벤트·고객 구분 조회를 재사용합니다. 화면 조회 및 재알림 시 현재 내부자·공유 브라우저·기존 방문·거부·전환 완료·3초 미만 방문·활동 중 조건을 다시 확인합니다. 조회 중 표본 변화로 저장된 점수·순위를 임의로 재계산하지 않으며, 재알림 카드도 저장 판정을 사용합니다. 이 버전의 판정이 없는 과거 방문을 임의로 리드로 승격하지 않습니다.

`lead_followup` 이력은 고객 퍼널의 실제 전환이나 가입 이벤트와 분리합니다. 상태명이 퍼널 단계와 같아도 상담 진행으로 표시한 것만으로 고객이 전환되었다고 보지 않습니다.

## 재알림 조건

- **urgent 핵심 리드만** 대상입니다. 일반·관심 높음에는 자동 재태그하지 않습니다.
- 미확인은 첫 긴급 판정 또는 마지막 담당자 수정에서 24시간 경과, 연락 예정은 기한 경과 시 대상입니다. 연락 완료·상담 진행이면 멈추며 재방문으로 상태를 초기화하지 않습니다.
- 평일 KST 09:00 이상 18:00 미만에 기존 고객 여정 스케줄러가 확인합니다. 공휴일 별도 달력은 적용하지 않습니다.
- 최초 방문 태그·재방문 태그·재알림을 합쳐 같은 사업·고객에 최소 24시간 간격을 둡니다. 자동 재알림은 고객별 최대 **3회 시도**입니다.
- 전송 전 처리 상태 버전과 고객의 최신 활동·완료·내부 식별을 재확인합니다. 선점 직후 담당자가 처리해도 전송 전에 취소합니다.
- 한 회차에 최대 50건을 확인하고, 확인한 대상은 1시간 뒤 다시 검사합니다. 이미 제외된 과거 대상이 많이 쌓여 뒤의 정상 리드를 계속 막지 않게 합니다. 담당자가 상태를 수정하면 다음 검사 대기를 갱신합니다.
- 요청 전에 시도 시각·횟수·결과 미확인을 기록합니다. 타임아웃/프로세스 중단 시 즉시 재전송하지 않습니다. 확정 실패도 다음 날 이후 남은 시도에서만 다시 알립니다. 화면의 최근 재알림은 성공 여부를 단정하지 않는 **시도** 시각입니다.
- 승인된 웹훅·사용자 ID가 없거나 `off`/`dry_run`이면 전송하지 않습니다. 실제 개발 서버 live 설정은 변경하지 않았습니다.

## DB 및 API

- `0079_journey_lead_followups`: 처리 상태 테이블 1개, 고객 유니크 키·기한 색인, 판정 조회 색인. 기존 테이블/열 삭제 없음.
- 최근 30일의 유효한 저장 판정은 초기 상태로 준비합니다. 이미 존재하는 상태를 덮어쓰지 않습니다. 기존 urgent의 미확인 24시간은 마이그레이션 실행 시점부터 시작합니다.
- `GET /api/analytics/key-leads`: 기존 수치 임계값 기준을 제거하고 공통 판정 목록을 반환합니다. `workspaceId`와 `limit`을 지원합니다. 이 API의 기존 `minVisits/minDurationSec/minClicks` 사용자화는 더 이상 적용하지 않습니다.
- `GET/PATCH /api/records/:id/lead-followup`: 조직 내 유효 판정과 처리 이력 조회/저장. PATCH는 상태·예정·메모·현재 revision을 전달합니다. 409는 다른 담당자의 먼저 저장한 변경입니다.
- 상태 갱신과 `record_events` 이력 추가를 같은 SQL 문장으로 확정합니다. 담당자 처리 권한은 기존 로그인한 조직 사용자입니다.

## 검증과 검토 순서

1. 마이그레이션 `0078`과 `0079`를 개발 환경에서 확인합니다. 고객 데이터가 있는 개발 서버는 여정 `off` 유지 또는 별도 가상 데이터에서 `dry_run`으로 검토합니다.
2. 가상 메일 유입을 판정한 뒤 CRM과 챗 예시의 등급·점수·근거를 비교합니다. 내부·완료·3초 미만 방문이 제외되는지 확인합니다.
3. 상태 창에서 한국 시간 예정·메모 저장 → 다른 담당자/중복 레코드에서 같은 상태 확인 → 연락 완료/상담 진행 → 새 방문에도 상태가 유지되는지 확인합니다.
4. 재알림의 24시간·기한·근무시간·최대 3회 조건과 완료/활동 중 취소를 격리 검사로 확인합니다. 실제 고객에게 시험 알림을 보내지 않습니다.
