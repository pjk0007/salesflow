# 고객 자동화 · 모의 실행과 사람의 게시

직원/API 키 권한은 [사업별 역할 기준](ACCESS.md)을 따른다. 이 문서의 설정 관리자는 해당 사업의 운영 관리 역할 또는 조직 관리자이며, 일반 직원은 배정받은 사업 역할에 맞는 업무를 사용한다.

R10 기본 구현이다. 두 사업의 고객·회사·상담·영업 이벤트를 공통 실행 대기열에 연결한다. 관리자가 버전을 저장하고 같은 사업의 이벤트로 모의 실행한 뒤 게시한다. 기본 워커는 꺼져 있으며 이번 검증은 가상 고객·격리 DB에서만 수행했다.

## 사용 순서

1. **고객 관리 → 고객 자동화**, 또는 **고객 상담 → 사이트 상담창 → 고객 자동화 설정**을 연다. 사업을 선택하고 **새 자동화**를 만든다.
2. 시작 이벤트를 선택한다. 고객 행동 이벤트는 `plan_viewed` 같은 이름으로 좁힐 수 있다. 기본 공개 메시지 규칙은 고객의 메시지에만 반응하도록 시작 조건을 제공한다. 이벤트 종류를 바꾸면 기존 조건도 함께 확인한다.
3. 실행할 단계를 순서대로 추가한다. 각 단계의 **실행 조건**에서 모두 일치/하나 이상 일치를 선택한다. 조건에 맞지 않거나 연결 대상이 없으면 그 단계를 제외하고 사유를 기록한다.
4. **검토할 새 버전 저장 → 모의 실행 이벤트 선택 → 저장한 버전으로 모의 실행** 순서로 예상 행동과 제외 사유를 확인한다. 고객·이벤트 원본도 펼쳐 볼 수 있다. 모의 실행은 고객 답변·업무·태그 등을 실제로 변경하지 않는다.
5. 예상 행동을 검토한 뒤 **검토한 버전 게시·활성화**를 누른다. 고객 자동 안내가 있으면 문구와 발송 조건 확인도 필요하다. 이후 새 이벤트부터 적용하며 과거 이벤트를 소급 실행하지 않는다.
6. **실행·예약 이력**에서 게시 버전, 처리한 단계, 예약 시간, 제외/실패 사유를 확인한다. 만든 업무와 연결 상담을 직접 연다. 실패하면 **실패한 단계부터 재시도**, 대기 중에는 **이 실행 중단**을 사용할 수 있다.

저장은 새 버전을 만들며 기존 적용 버전은 계속 유지한다. 새 버전을 게시하면 이전 버전의 대기 실행을 취소한다. **자동화·대기 실행 중단**은 새 이벤트 등록과 남은 단계를 중단한다. 이미 완료한 태그·업무·답변은 되돌리지 않는다. 처리 중인 DB 단계가 먼저 커밋됐다면 그 단계 이후부터 중단된다. 게시한 버전을 다시 사용하려면 새 버전으로 복사·저장하고 검토한다.

## 제공하는 행동과 조건

| 행동 | 처리 |
|---|---|
| 예약 대기 | 1분~30일. 해당 단계 처리 시점부터 예약하고 대기 이후 단계는 최신 정보로 조건을 재평가 |
| 상담 태그 | 태그 추가/제거 |
| 담당자 배정 | 같은 조직의 활성 팀원 배정 또는 기존 배정 해제 |
| 상담팀 배정 | 같은 사업의 활성 팀으로 분류. 기본은 기존 팀/개인 보존, 명시 선택 시 교체. 팀의 수동/자동 설정과 현재 권한을 따름. [사용·API·검수](WORKFLOW-ROUTING.md) |
| 상담 상태 | 진행중/보류중/종료됨 변경 |
| 사람에게 이관 | 사람 응대·진행중·중요 상담으로 변경. 담당자 지정은 별도 배정 단계 |
| 후속 업무 | 같은 고객·회사·딜과 연결한 업무, 담당자와 마감 시각 설정. 상담이 있으면 업무 내용에 원래 상담 링크 보존 |
| 고객 단계 | 리드/잠재 고객/고객/비활성 변경 |
| 딜 단계 | 시작 이벤트에 연결된 딜의 같은 파이프라인 내 유효한 단계 변경 |
| 고객 자동 안내 | 검토한 문구와 제한된 이름 변수를 사용한 공개 답변. AI 생성이 아닌 ‘자동 안내’로 표시 |
| 고객 이벤트 | 새 고객 행동 기록을 기존 활동·웹훅 계약으로 전달 |

시작 조건과 단계 조건은 `event`, `contact`, `company`, `conversation`, `deal`, `task`의 필드를 사용한다. 같음/다름/포함/값 있음·없음/숫자 이상·이하를 제공한다. `event`는 시작 이벤트 원본이며 다른 객체는 처리 시점의 현재 값이다. 값이 없는 필드를 ‘다름’ 조건으로 임의 통과시키지 않는다. 사용자 코드·정규식·스크립트를 실행하지 않는다.

개인화 변수는 `{{contact.name}}`, `{{company.name}}`, `{{conversation.name}}`, `{{deal.title}}`, `{{task.title}}`로 제한한다. 모르는 변수·잘못된 괄호·너무 긴 개인화 문구를 거부한다. 회사가 여러 개 연결되어 대표 회사를 특정할 수 없으면 임의로 하나를 선택하지 않는다.

내부 고객 표시와 같은 조직의 활성 팀원 이메일을 제외한다. 고객 자동 안내는 고객의 공개 메시지에만 응답하며, 첨부 자료·새 공개 문의/답변·사람 응대·비활성 상담창·종료/보류·24시간 지난 문의에는 보내지 않는다. 전송 직전 대화를 잠근 상태로 최신 메시지를 확인한다. 실제 서비스 고객 대상 문구는 적용 전에 별도로 검토한다.

## 실행·중복·복구 계약

- 원본 이벤트 저장과 같은 트랜잭션에서 게시 버전·설정 세대·시작 이벤트를 고정한 실행을 등록한다. `(workflowId,eventId)`로 재시도 중복을 막는다. 모의 실행은 별도 검토 기록이다.
- 단계의 원본 변경, 활동·웹훅 outbox, 처리 결과와 다음 실행 위치를 같은 트랜잭션으로 커밋한다. 업무·공개 답변·고객 이벤트도 실행/단계에서 파생한 고정 번호를 사용한다. 실패한 트랜잭션은 행동과 결과를 함께 롤백한다.
- 워커 lease는 60초다. 끊긴 작업을 복구할 때 새 lease를 발급하며 이전 워커의 결과를 채택하지 않는다. 명시적으로 재시도 가능한 SQL 오류는 5/20/60/300초 간격으로 최대 5회 시도하고 이후 실패 이력으로 남긴다. 수동 재시도는 완료한 앞 단계를 다시 실행하지 않는다.
- 대화/업무/고객 변경 시 기존 저장 함수와 감사·공통 활동을 재사용한다. 워크스페이스를 먼저 직렬화하고 설정·실행·대상 잠금 순서를 유지한다. 중단/버전 변경/단건 취소와 다음 단계의 경계를 확인한다.
- 자동화에서 만든 이벤트에는 원인 실행 번호를 저장하고, 다른 고객 자동화를 다시 시작하지 않는다. 파생 고객 이벤트·업무·공개 답변은 기존 웹훅으로 전달할 수 있다. 연쇄·반복 자동화는 별도 기능으로 남긴다.
- 버전의 이름·설명·정의·지문과 게시자를 보존한다. 현재 관리자의 권한, 활성 담당자, 사업별 고객/회사/딜 관계를 확인한다. 게시자의 권한이 철회되면 실행을 실패 상태로 중단한다.

## API와 서버 SDK

사업 범위 API 토큰을 사용한다. 조회는 read, 생성은 관리자 발급 토큰의 create, 편집/모의 실행/게시/중단·재시도는 update 권한을 요구한다. native 화면도 같은 현재 직원 권한을 확인한다.

| API | 동작 |
|---|---|
| `/api/v1/workflows?workspaceId=...&before=...` GET | 자동화 50개씩, 시작 이벤트/행동 목록과 워커 상태 |
| `/api/v1/workflows` POST | workspaceId/version=0/name/description/definition으로 첫 버전 저장 |
| `/api/v1/workflows/{id}` GET / PATCH | 최근 버전 50개와 적용 버전, 최근 감사 100개 / 현재 version으로 새 버전 저장. 충돌 시 409 |
| 위 경로 POST action=preview | revisionId/eventId로 모의 실행·검토 기록 저장 |
| 위 경로 POST action=publish | version/revisionId/previewId/allowCustomerReplies. 동일 버전의 유효한 검토 결과와 최신 설정 필요 |
| 위 경로 POST action=disable | version을 확인해 자동화와 대기 실행 중단 |
| `/api/v1/workflows/events?workspaceId=...&before=...` GET | 같은 사업의 원본 이벤트 50개씩. 고객 이름·이벤트 내용으로 선택 |
| `/api/v1/workflows/{id}/runs?before=...` GET | 실행/예약/실패 요약 50개씩 |
| `/api/v1/workflows/{id}/runs/{runId}` GET / POST | 고정 버전·시작 원본·단계 결과·최근 복구 감사 100개 / action=cancel 또는 retry |

`SendbClient`: `workflows`, `workflow`, `saveWorkflow`, `workflowEvents`, `previewWorkflow`, `publishWorkflow`, `disableWorkflow`, `workflowRuns`, `workflowRun`, `changeWorkflowRun`. 기존 이벤트/상담/CRM 계약을 그대로 사용하며 서비스 토큰은 사이트 서버에만 둔다.

## 검증과 남은 범위

마이그레이션 `0095_customer_workflows.sql`은 자동화/버전/모의 실행/실행/단계/감사와 이벤트의 원인 실행 번호를 추가한다. `CUSTOMER_WORKFLOW_WORKER=on` 및 production 런타임에서 자동 워커를 시작한다. 기본은 꺼짐이고, 사업별 게시가 별도로 필요하다. 사업당 활성 100개, 정의당 20단계·조건 그룹당 12개, 정의 요청은 250,000자까지다.

`scripts/check-customer-workflows.cjs`의 격리 SQL/API 15개 시나리오를 통과했다. 두 사업의 독립 실행·현재 관리자 권한·미게시 차단·모의 실행 무변경·멱등·트랜잭션 롤백·조건/예약·중단/새 버전·실패/수동 복구·중복 워커/늦은 lease·내부 고객·딜/담당 참조·공개 답변 최신성·100건 초과 커서를 확인한다. 단위 검사 1,051개, 기존 상담·플랫폼·영업·활동·첨부·웹훅·상담 AI 회귀 검사도 유지한다.

Chrome에서는 디하 문의→태그·담당 업무→실제 1분 대기→고객 단계 변경→업무의 고객/회사/담당/상담 링크, 백오랩 관심 이벤트→별도 업무 생성과 사업 격리를 확인했다. 모든 고객·모델 응답·DB는 가상이며 실제 고객·메일·Google Chat·외부 서버 전송과 운영 DB 접근은 없다.

현재는 순차 단계와 조건에 따른 실행/제외 방식이다. 이후 [조건별 팀 배정](WORKFLOW-ROUTING.md), [수용량](CAPACITY.md), [사업 업무시간](BUSINESS-HOURS-ROUTING.md)을 연결했다. 팀 배정 모의 실행은 현재 후보와 대기 사유를 보여주고, 실제 실행은 그때의 권한·접속·수용량·달력을 다시 확인한다. 기본 응대 목표·앱 알림은 [운영 기능](OPERATIONS.md)에 구현되어 있다.

복잡한 그래프/반복/동시 분기, 이벤트를 기다리는 단계, 자동화의 외부 발송 채널 어댑터와 여러 SLA 정책을 이용한 고급 분기는 남은 개발 범위다. 실제 다중 인스턴스·대규모 부하·장기 장애 검수도 남아 있다. 현재 사용하지 않는 외부 채널이나 고급 규칙을 사업 요구 없이 필수로 추가하지 않으며, 전체 대체 완료로 표시하지 않는다.

설계 참고는 고정 커밋의 [Dittofeed 사용자 여정 실행](https://github.com/dittofeed/dittofeed/blob/91277939a9afcee797ab2562025f6b02d823b00c/packages/backend-lib/src/journeys/userWorkflow.ts)에서 본 워크스페이스·고객·여정·이벤트 키 구분과 기존 REA/공개 계약 분석이다. 일반 소스 분석이며 Temporal 도입이나 해당 코드 복사를 의미하지 않는다.
