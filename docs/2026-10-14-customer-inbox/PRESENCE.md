# 상담원 응대 상태와 공동 작성 표시

2026-10-15 · `dev` / 초안 PR14. 마이그레이션 `0107_inbox_agent_presence.sql`을 추가했으며 실제 DB·서버 설정·배포에는 적용하지 않았다.

## 사용하는 흐름

상담 상단의 **내 응대 상태**에서 ‘자리 비움’ 또는 ‘응대 가능’을 선택한다. 상태는 사업별 개인 설정이며 기본은 자리 비움이다. 다른 사업으로 이동해도 그 사업의 상태를 덮지 않는다. 현재 사업의 응대 권한이 있는 직원만 자신의 상태를 바꿀 수 있다. 열람 직원도 상담을 보고 있다는 표시는 공유하지만 응대 상태 선택기와 답변 입력은 제공하지 않는다.

**상담팀 → 접속 중이며 응대 가능한 직원에게만 자동 배정**을 켜면 해당 팀의 현재 응대 권한·접속·개인 상태를 함께 확인한다. 접속한 직원이라도 자리 비움이면 제외하고, 응대 가능으로 남겨두었더라도 접속이 만료되면 제외한다. 후보가 없으면 팀 대기열에 남는다. 자동 배정과 이 옵션은 기본 꺼짐이며 옵션을 끈 팀은 이전의 권한/진행중 상담 수/마지막 배정 기준을 유지한다.

이 옵션은 자동 배정 후보에만 적용한다. 사람이 담당자를 명시적으로 지정할 수 있고, 상태를 바꿔도 이미 맡은 상담을 일괄 이관하지 않는다. 팀 대기열도 상태 변경만으로 소급 배정하지 않는다. 조건별 자동화와 AI 사람 이관의 팀 자동 배정은 같은 후보 함수를 사용한다. 모의 실행의 예상 담당자가 자리 비움으로 바뀌면 실제 처리 시점에 다시 확인한다.

같은 상담을 보는 다른 직원은 입력창 위에 이름과 활동이 표시된다. **고객 답변 작성 중**이면 답변이 겹치지 않도록 최신 대화를 확인하라는 안내를, **내부 메모 작성 중**이면 메모 표시를 제공한다. 보는 중/작성 중은 구분하며, 자신의 여러 탭은 자기 활동으로 중복 표시하지 않는다. 다른 직원의 여러 탭도 직원 한 명으로 합쳐 답변 작성→메모 작성→조회 순으로 표시한다.

작성 문장·첨부 초안·키 입력 내용은 접속 API에 보내지 않는다. 답변/메모는 기존 전송 버튼으로만 저장한다. 작성 표시가 있어도 전송을 강제로 잠그지 않는다. 네트워크 지연과 동시 클릭의 최종 발송을 막는 잠금 기능은 아직 구현하지 않았다.

## 접속과 최신성

탭마다 무작위 세션 번호를 사용한다. 화면이 보일 때 처음 접속/약28초 간격으로 갱신하고 작성 중에는 최대4초 간격으로 활동을 갱신한다. 작성 입력을 멈추면 클라이언트가 보는 중으로 바꾸며 서버의 작성 표시는 갱신 후12초 만료된다. 선택 상담의 다른 직원 활동은 약3초 간격으로 조회한다. 즉시 동기화되는 잠금/웹소켓을 의미하지 않는다.

접속은 서버 수신 시각부터90초 유효하다. 탭이 숨겨지거나 화면을 떠나면 종료를 전달하고, 갑자기 종료되거나 전송이 끊기면 서버 만료를 따른다. 다른 탭이 계속 보이는 상태라면 접속을 유지한다. 화면을 떠나며 보내는 종료 요청은 실패할 수 있으므로 순간적인 연결 해제를 곧바로 확정하지 않는다. 고객 상담 화면 밖에서도 직원이 온라인이라고 가정하지 않는다.

요청의 증가 순번이 이전 값 이하이면 접속/활동/종료를 덮지 않는다. 최근 종료 기록도 남겨 지연된 작성 요청이 접속을 되살리지 못하게 한다. 하루 이상 지난 자기 사업의 자기 세션은 다음 갱신에서 정리한다. 영구 이력/보존 정책은 별도 범위이며 전체 직원의 오래된 세션을 정기 파기하는 워커는 아직 없다.

개인 응대 상태 변경은 버전 CAS를 사용한다. 다른 창에서 먼저 바꿨으면 충돌을 표시하고 최신 상태를 조회한다. 단순 접속 갱신은 개인 상태를 바꾸지 않으므로 여러 창이 자리 비움/가능 선택을 서로 되돌리지 않는다. 권한 회수는 다음 조회/배정에서 즉시 제외하며 열람으로 낮아진 직원의 옛 작성 표시는 보는 중으로 바꾼다.

## API와 데이터

직원 화면의 접속 조회/갱신/상태 변경은10초 시간 제한을 사용한다. 조회가 실패하면 캐시된 작성/접속 표시를 숨기고 상태 변경을 잠시 제한하며 복구 안내를 보여준다. 재조회가 성공하면 표시를 복원한다. 쓰기 응답이 끊겼을 때는 최신 버전을 다시 조회하므로 이전 상태로 무조건 되돌리거나 자동으로 같은 변경을 반복하지 않는다.

| 경로 | 계약 |
|---|---|
| `/api/inbox-presence?channelId=…&conversationId=…` GET | 현재 직원의 사업 열람 권한. 현재 접근 가능한 직원의 이름·접속·응대 상태·선택 상담 활동, 자신의 응대 상태/버전 |
| `/api/inbox-presence` POST | 직원 자신의 탭 접속 갱신/종료. 조회 활동은 read, 답변/메모 작성 활동은 respond 권한 필요 |
| `/api/inbox-presence` PATCH | 직원 자신의 사업별 응대 상태를 version으로 변경. respond 권한 필요 |
| `/api/v1/inbox/presence?channelId=…&conversationId=…` GET | 사업 read 서비스 키와 발급자의 현재 역할 교집합으로 조회. 쓰기는 제공하지 않음 |
| 기존 팀 생성/수정 | `requireAvailable:boolean` 추가. 생성 기본false, 부분 수정에서 생략하면 보존. 팀 감사/버전 계약 유지 |

POST는 `{channelId,sessionId:uuid,sequence:int,conversationId:uuid|null,activity:"viewing"|"reply"|"note",leave?:boolean}`이다. `conversationId`와 `activity` 기본값은 null/viewing, `leave`는 false다. 작성 활동에는 현재 사업의 상담이 필요하고 병합된 원본/과거 이력 상담에는 작성 표시를 허용하지 않는다. 클라이언트 직원 ID·초안·임의 만료 시각을 받지 않으며 추가 필드를 거절한다.

PATCH는 `{channelId,version,state:"available"|"away"}`다. 최초 version0, 저장 후1부터 증가한다. 기존 상태와 같은 값은 중복 버전을 만들지 않는다. 서비스 API 키로 다른 직원을 접속/작성 중이라고 등록할 수 없다. 고객용 messenger API에는 직원 활동 조회를 추가하지 않았다.

`SendbClient.inboxPresence(channelId,conversationId?)`와 `sdk/presence-types.ts`를 제공한다. 팀 API/SDK의 `requireAvailable`도 동일하다. 접속 응답에는 다른 직원의 세션 번호·갱신 순번·작성 만료 원본을 포함하지 않는다.

0107은 팀의 `require_available` 기본false와 사업/직원의 응대 상태·탭별 세션/순번/상담/활동/만료 테이블을 추가한다. 실제 설치 전 앱보다 먼저 검토/적용해야 한다. 현재 작업은 SQL 파일만 추가했으며 실제 DB에 실행하지 않았다.

## 검수와 남은 범위

`node --import tsx scripts/check-inbox-presence.cjs`: 신규 SQL/API14개 + 기존 플랫폼11개. 스키마·기본값·native/서비스 계약·사업/권한·위조 입력/초안 제외·응대 CAS/멱등·정확한90초/12초 만료·다중 탭/순번/종료·접속과 상태의 교집합·권한 회수·자동/수동 계약·자기 세션 정리/롤백·백오랩 분리·자동화 예상/처리 사이 상태 재평가를 검사했다.

기존 상담팀18·조건별 분류12·회원 연결12 회귀와 전체 단위1,095·기능 lint·타입을 포함한 격리 전체 Next 빌드가 통과했다. Chrome의 두 가상 직원 iframe에서 실제 InboxPage 컴포넌트로 답변 작성 경고·메모 작성 표시·초안 비공유, 자리 비움 교대 후 자동 담당 변경·모두 자리 비움일 때 미배정 큐를 확인했다. 사업 변경 시 별도 상태와 열람 직원의 제어 제한도 검수했다. 조회503 모의에서 오래된 작성 표시를 숨기고 상태 선택을 제한한 뒤 자동 재조회 복구도 확인했다. 시간 초과 한국어 안내·원래403 권한 안내 보존의 단위2개를 추가했다. 두 iframe의 서로 다른 가상 인증 전달은 `.testenv` 시험 전용이며 제품 코드에 포함하지 않았다.

증거는 `evidence-manifest.json`의 `presenceQa`에 기록한다. 모든 직원/고객/DB는 가상·PGlite/loopback이며 실제 고객 발송·서버 설정·운영 DB·main/master 병합·배포는 수행하지 않았다. 실제 다중 서버/다수 직원 부하·개인별 수용량·근무시간·강제 작성/발송 잠금·웹소켓·OS/외부 알림·세션 전체 보존/파기와 실제 업무/전체 전환은 남아 있다. 전체 목표는 [REPLACEMENT.md](REPLACEMENT.md)를 유지한다.
