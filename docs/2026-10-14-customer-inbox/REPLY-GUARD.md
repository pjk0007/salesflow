# 고객 답변 작성 잠금과 중복 전송 방지

2026-10-15 · `dev` / 초안 PR14. 0110 SQL을 추가했다. 운영/개발 고객 DB·서버 설정·키·실제 사이트·main/master 병합·배포는 변경하지 않았다.

## 사용하는 흐름

1. 사업 운영 관리자가 **고객 상담 → 답변 충돌 방지**에서 사용을 켠다. 기본 꺼짐이며 웹·이메일·서버 SDK의 직원 공개 답변에 적용한다. 외부 직원 응대 도구는 아래 작성 권한 API까지 연결한 뒤 켠다. 고객의 사이트 문의 API에는 추가 권한을 요구하지 않는다.
2. 상담원은 **답변 작성 시작**으로 현재 창의 권한을 확보한다. 다른 직원/다른 탭이 작성 중이면 고객 답변 입력·첨부 선택·전송을 제한하고 작성자 이름을 표시한다. 각 창의 문장은 기존 로컬 초안에 보존하며 다른 직원에게 공유하지 않는다. 내부 메모는 함께 작성할 수 있다.
3. 관리자는 현재 작성자와 **인계 사유**를 확인한 뒤 **답변 작성 인계받기**를 누를 수 있다. 이전 창은 전송할 수 없고 작성 문장은 남는다. 인계 사유·이전/새 직원 이름을 감사에 기록한다. 일반 상담원은 다른 사람의 활성 권한을 강제로 가져오지 못한다.
4. 작성 중 새 공개 메시지나 회원 이력 병합이 생기면 전송을 막는다. 메시지와 초안을 검토하고 **최신 대화 확인·초안 유지**를 눌러야 한다. 화면보다 더 새 메시지가 서버에 도착했으면 확인도 거절한다. 권한 갱신만으로 초안을 승인하지 않는다. 이미 보관된 초안은 **대화 확인·초안으로 작성 재개**로 명시적으로 재개한다.
5. 공개 답변 저장과 동시에 권한을 해제한다. 화면을 떠나거나 내부 메모로 바꾸거나 브라우저 탭이 숨겨지면 해제를 시도한다. 연결 끊김에서는 마지막 갱신 후90초에 만료한다. 열린 작성 창은20초마다 갱신하며 실제 서버 검사에서 만료·인계·현재 직원 역할을 다시 확인한다. **작성 권한 해제**로 직접 넘길 수도 있다.

잠금 설정은 버전/CAS로 저장한다. 충돌 시 선택을 유지하고 **최신 설정 불러오기**를 명시적으로 누를 때 현재 설정으로 바꾼다. 설정을 껐다 켜도 옛 권한을 재사용하지 못한다. 설정 변경은 이후 서버 검사부터 적용하며 이미 검사를 마친 진행 중 요청을 취소하지 않는다. 실제 고객 문장의 내용이 적절한지는 상담원이 검토한다.

## 저장·재시도·자동화

작성 권한 확보/인계와 공개 답변 저장은 상담 행을 잠가 직렬화한다. 답변은 현재 직원·창·권한 ID·만료·설정 버전과 공개 대화 변경 순번을 확인한다. 답변/첨부/메일 큐·원본 이벤트 저장이 실패하면 권한 소비와 순번 변경도 함께 롤백한다.

공개 대화 순번 `replyRevision`은 고객 메시지와 직원/자동 답변에서 증가하며 내부 메모에서는 증가하지 않는다. 회원 이력 병합도 증가시키므로 낮은 ID의 옛 메시지를 추가한 경우를 놓치지 않는다. 기존 상담의 최초 값은0이며 이후 변경부터 추적한다. 메시지 `clientId` 중복 검사는 잠금 검사보다 먼저 수행한다. 이미 성공한 요청은 권한 만료 뒤에도 같은 결과를 반환하므로 응답 유실 재시도로 답변/메일 큐를 중복 생성하지 않는다.

상담원이 작성하는 동안 시스템의 공개 답변도 거절한다. AI 워커는 이 경우 생성 결과를 `ready` 초안으로 보존하고 자동 전송하지 않는다. 권한이 해제됐다고 자동으로 다시 발송하지 않으며 상담원이 근거/대화와 초안을 확인하고 전송한다. AI가 사람에게 넘기는 안내도 작성 중에는 공개 전송하지 않는다. 일반 자동화의 공개 안내는 기존 실행 오류/재시도 이력에서 충돌을 확인하고 검토 후 다시 처리한다. 자동화 전체를 잠그거나 메모·CRM 작업을 중단하는 기능은 아니다.

직원 역할을 회수하면 그 직원의 권한을 유효한 작성자로 보지 않는다. 종료·과거 상담·병합 원본에는 새 권한을 만들지 않는다. 지연된 옛 갱신/해제와 다른 상담의 권한 ID는 현재 작성자를 바꾸지 못한다. 상담 담당자와 일시적인 작성 권한은 다른 개념이며 잠금 확보로 개인 담당을 자동 변경하지 않는다.

## API와 SDK

| 계약 | 내용 |
|---|---|
| `/api/inbox-reply-guard` GET | `channelId`, 선택 `conversationId`/`sessionId`. 설정 버전·현재 manage 여부·공개 대화 순번·현재 작성자/이 창 소유/만료 |
| 같은 경로 PATCH | `{channelId,version,enabled}`. 현재 사업 운영 관리 권한과 CAS 필수 |
| 같은 경로 POST | `conversationId,sessionId,action`. `acquire`는 관찰한 `revision`, `renew/release`는 `leaseId`, `acknowledge`는 둘 다 필수 |
| acquire의 선택 takeover | `{leaseId,reason}`. 현재 작성 권한 ID와3~300자 사유·현재 사업 manage 권한 필수 |
| `/api/v1/inbox/reply-guard` | 같은 계약. GET read, 설정 PATCH update, 작성 POST create 키 범위와 발급자의 현재 역할을 함께 확인 |
| 기존 직원 메시지 POST | 공개 답변에 선택 `replyGuard:{leaseId,sessionId,revision}` 추가. 사업 설정을 켰으면 필수, 내부 메모에서는 금지 |

SDK는 `replyGuard`, `saveReplyGuard`, `updateReplyLease`와 `reply`의 마지막 선택 인수를 제공한다. 타입은 `sdk/reply-guard-types.ts`에 있다. 화면에서 실제로 확인한 대화의 순번으로 시작하고, 서버가 더 새 상태를 알려주면 대화부터 다시 표시한다.

```ts
const sessionId = crypto.randomUUID(); // 창별로 구분
const { conversation } = await client.inboxConversation(conversationId);
// 최신 대화를 표시하고 사람이 확인한 뒤 시작한다.
const page = await client.updateReplyLease({
  action: "acquire", conversationId, sessionId,
  revision: conversation.replyRevision,
});
const lease = page.conversation!.lease!;
await client.reply(conversationId, body, clientId, "reply", [], undefined, undefined, {
  leaseId: lease.id, sessionId, revision: lease.baseRevision,
});
```

실제 설치 전0088~0110을 앱보다 먼저 검토해야 한다.0110은 채널 설정/버전, 공개 대화 순번, 상담당 하나의 만료 가능한 작성 권한 테이블/인덱스를 추가한다. 기존 채널은 꺼짐이며 이번에는 가상 시험 DB에만 실행했다.

## 근거와 검수

- `node --import tsx scripts/check-inbox-reply-guard.cjs`: 가상 PGlite/native API/SDK20개와 플랫폼 기본11개.
- 같은 명령의 `--postgres`: 별도 loopback PostgreSQL17.11/postgres-js에서22개와 기본11개. 독립 연결의 동시 확보와 같은 권한의 동시 전송은 각각 하나만 성공했다. 실제 다중 서버/대규모 부하를 증명하는 검수는 아니다. 가상 DB와 소유한 시험 서버를 정리했다.
- 기본 호환·권한/사업/키·설정 CAS/멱등·다른 탭/직원 충돌·답변/메일 큐 멱등·새 문의/명시 확인·메모 독립·만료/지연 요청·관리자 인계·역할 회수·설정 전환·감사/메시지 실패 롤백·자동 답변·제외 대상·사업 독립·이메일 큐·낮은 메시지 ID의 회원 병합·실제 AI 워커의 초안 보존/사람 전송을 확인했다. 모델 응답은 가상이며 실제 공급자를 호출하지 않았다.
- 기존 상담22·메일14·메일 참여자16·파일11·회원 연결12·AI16·자동화15·업무시간14·멘션19·운영23의10개 회귀 묶음, 단위1,095·타입/기능 lint·격리 전체 Next 빌드 통과. 실제 드라이버 시험은 지식 승인 등의 명시 트랜잭션에도 제품과 같은 예약 연결을 쓰도록 공통 가상 시험 어댑터를 보완했다.
- Chrome의 두 가상 직원에서 B 작성→A 사유 인계→B 입력 차단/초안 보존·내부 메모→새 고객 문의→A 전송 제한/초안 검토→단일 공개 답변/권한 해제→B의 명시 재개/해제를 확인했다. 고객 위젯에는 내부 메모가 없고 답변은 한 번 도착했다. 두 설정 창의 충돌·선택 보존/최신 복구, 일반 상담원의 설정 제어 제한도 확인했다.

[Chatwoot 공식 충돌 방지 설명](https://www.chatwoot.com/features/collision-detection)의 작성 표시·담당 구분을 참고했다. 서버의 명시 작성 권한/공개 대화 순번/관리자 인계는 샌드비의 독립 구현이다. 새 비공개 SaaS 실행을 REA로 관찰한 증거가 아니며 기존 아티팩트 근거는 [ANALYSIS.md](ANALYSIS.md)를 유지한다.

증거는 `evidence-manifest.json`의 `replyGuardQa`에 기록한다. 직원별 교대표·외부/OS 알림·실제 계정/사이트/채널 설치·자료 이전·실제 다중 서버/부하·전체 업무 전환은 남는다. 전체 목표는 [REPLACEMENT.md](REPLACEMENT.md)를 유지한다.
