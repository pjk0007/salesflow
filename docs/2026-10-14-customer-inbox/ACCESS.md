# 사업별 직원 권한 · 사용과 검토

제공 리서치의 공통 조직·멤버·역할 모델을 고객 상담/CRM 플랫폼에 적용했다. 디자이너하이어와 백오피스랩의 담당 직원과 역할을 각각 지정한다. 조직의 일반 직원이라는 이유만으로 두 사업 전체에 접근하지 않는다.

## 사용하는 방법

1. 조직 관리자가 **고객 상담 → 직원 권한**을 연다. 상담창이 없는 사업도 목록에서 선택할 수 있다.
2. 사업을 선택하고 기존 조직 직원에게 역할을 지정한 뒤 그 직원 행의 **저장**을 누른다. 실제 직원 초대는 기존 조직 관리에서 한다.
3. **권한 변경 이력**에서 변경한 관리자·직원·이전/이후 역할·시각을 확인한다. 같은 직원의 다른 사업 역할은 별도로 지정한다.
4. 일반 직원은 배정된 사업만 선택한다. 열람 화면은 답장 입력창과 수정 동작을 제한하지만 고객·거래 상세·활동/변경 이력은 조회할 수 있다.
5. 담당 업무를 옮길 때 해당 직원의 역할을 **접근 없음**으로 저장한다. 상담·거래의 기존 담당 ID와 과거 기록은 보존하며, 현재 응대 가능한 직원으로 다시 배정한다. 배정 불가한 기존 담당은 선택 상자에서 구분한다.

| 역할 | 사용할 수 있는 업무 |
|---|---|
| 접근 없음 (`none`) | 해당 사업의 상담·고객·영업·메일함·AI·자동화·성과/API 조회 불가 |
| 열람 (`viewer`) | 상담·내부 메모·보호 첨부·고객·회사·거래·할 일·성과 조회, 본인의 읽음/알림 확인 |
| 응대·편집 (`agent`) | 열람 + 답장·내부 메모·파일 업로드·담당/상태/태그/CRM 연결·고객/회사/딜/할 일 편집·수신 파일 재요청·답장 재시도/취소 |
| 운영 관리 (`manager`) | 응대·편집 + 상담창·메일함/Google 연결·AI/지식 승인·자동화 게시/중단·파이프라인·외부 웹훅·자료 이전·업무시간/응대 목표 설정 |
| 조직 소유자/관리자 | 모든 사업의 운영 관리 + 직원의 사업 역할 배정/회수. 조직 역할은 기존 조직 관리에서 변경 |

사업 운영 관리자는 조직 관리자로 승격되지 않으며 다른 직원의 사업 권한을 배정할 수 없다. 일반 직원의 기본값은 접근 없음이다. 기존 레코드용 `member_scopes`의 추가 허용 정책을 바꾸지 않고, 고객 플랫폼에 별도의 사업 역할을 둔다. 기존 마케팅 메일/F06·F08 전체와 일반 레코드 관리의 권한을 이 기능으로 교체한 것은 아니다.

## 요청과 작업 처리 기준

- 직원 HTTP 요청은 현재 조직 멤버십·활성 계정·세션 버전을 확인한다. JWT에 과거 관리자 역할이 남아 있어도 현재 DB 역할과 사업 배정으로 판정한다.
- 서비스 API 키는 **토큰의 사업/읽기·생성·수정 범위와 발급자의 현재 사업 역할의 교집합**으로 허용한다. 일반 직원 발급 키에도 적용하며, 설정 변경에는 발급자의 사업 운영 관리 역할이 추가로 필요하다. API 키를 이용한 직원 권한 배정은 제공하지 않는다.
- 기본/필터/검색/집계/커서/본문/첨부/고객 타임라인/메일함/AI/워크플로/외부 연동/이전/응대 운영 API에 같은 기준을 사용한다. 자체 직원 화면의 bootstrap도 접근 가능한 사업과 응대 가능한 담당 후보를 반환한다.
- 개인 알림의 목록·미확인 건수·커서·읽음 처리와 새 수신 대상도 현재 사업 역할을 확인한다. 열람 직원에게 새 응대 알림을 배분하지 않는다. 권한을 잃은 담당자 대신 현재 응대 가능한 직원에게 새 알림을 배분한다.
- 자동화는 각 실행 단계에서 게시자의 현재 사업 운영 관리 역할을 확인한다. Google 자동 수신은 연결한 직원의 역할을 처리 단계 시작에 확인한다. Google 승인 도중 권한을 잃으면 토큰 교환 전에 중단하고, 연결을 저장하기 직전에도 재확인한다.
- 수동 AI 초안은 요청자의 응대 역할이 없어지면 이후 최신성 검사에서 사용을 중단한다. 기존 사업 AI 설정과 웹훅은 사업에 속한 설정으로 유지되며 작성자의 역할 회수만으로 자동 삭제하지 않는다.
- 이메일 대기/준비 상태는 다음 claim 때 작성자의 현재 응대 역할이 없으면 취소한다. 공급자 발송 시작(`begin`) 직전에도 확인한다. 이미 공급자 요청이 시작된 작업/진행 중 요청을 소급 취소한다고 보장하지 않는다. 발송 결과 확인은 유지한다.

권한 변경은 이후 요청/처리 단계에 반영한다. 이미 허용된 요청이 진행 중인 순간까지 동기화하는 전역 잠금, 이미 받은 브라우저 데이터의 원격 삭제, 이미 전달된 웹훅/메일의 회수는 구현하지 않았다.

## API와 저장

조직 직원 세션으로만 사용한다. `Origin` 검사는 기존 직원 API와 동일하다.

- `GET /api/customer-platform/access?workspaceId=8&before=<audit-id>`: 기존 조직 직원, 현재 사업 역할/버전, 변경 이력 50건과 `hasMore`. `before`는 선택 사항이다.
- `POST /api/customer-platform/access?workspaceId=8`: `{ "userId": "<uuid>", "role": "agent", "version": 0 }`. 배정이 없으면 버전 0, 저장한 버전을 다음 요청에 전달한다. 응답은 `{ success: true, data: { role, version } }`.
- 조직 관리자 역할은 이 경로에서 변경할 수 없다. 타 조직 직원과 비활성 직원의 새 배정을 거절한다. 비활성 직원의 기존 배정을 회수할 수는 있다.
- 오래된 버전은 409, 권한 없음은 403, 세션/멤버십 만료·계정 비활성은 401이다. 회수도 행을 삭제하지 않고 `none`과 새 버전을 저장해 과거 버전으로 재배정하는 요청을 차단한다. 같은 역할 저장은 감사 이력을 추가하지 않는다.
- `customer_workspace_access`: 사업/직원 유일 배정·역할·버전·변경 관리자/시각.
- `customer_access_audit`: 사업·대상 직원·변경자·이전/이후 역할·버전·시각. 배정 저장과 같은 트랜잭션에 기록한다. 조직에서 탈퇴해도 과거 변경 이력은 보존한다.

## 배포 검토와 기본값

마이그레이션 **0102_customer_workspace_access.sql**을 앱보다 먼저 적용한다. 자동으로 모든 직원에게 역할을 부여하는 데이터 이전은 없다. 조직 관리자가 기존 직원과 서비스 키 발급자의 필요한 사업 역할을 확인·배정한 뒤 실제 팀 업무를 검수해야 한다. 관리자가 발급한 기존 키도 기존 토큰 범위는 계속 적용된다.

이번 작업은 `dev`와 초안 PR의 코드다. 실제 dev/운영 DB 마이그레이션·직원 배정·서비스 키 변경·운영 배포는 수행하지 않았다. 메일·고객 여정·웹훅·AI·Google·응대 초과 검사 워커의 기존 꺼짐 기본값을 유지한다.

## 검증과 근거

`node --import tsx scripts/check-customer-access.cjs` — PGlite에 실제 0088~0102 SQL을 적용하고 가상 직원·고객으로 SQL/API **18개**를 검증한다. 기본 접근 차단, 역할별 허용/거절, 사업 간 본문·첨부·설정·성과 격리, 담당 후보, CAS/무변경/회수, 알림과 미확인 집계, JWT 현재 역할/세션/비활성, API 키 교집합, 이메일 전송 전 차단, 사업 관리자 자동화 실행과 회수, Google 승인 중 회수, 조직 탈퇴 후 감사 보존, DB 제약과 같은 시각 50건 커서를 포함한다.

기존 단위 **1,075개**, 상담22·플랫폼11·영업13·공통 활동7·첨부18·웹훅14·상담 AI16·자동화15·회원 연결12·이전15·이메일14/첨부11·Google19·응대 운영23 회귀, 타입·기능 lint·격리 빌드를 확인했다. 단위/SQL/API 건수는 서로 다른 검사군이며 단순 합계로 제품 완료율을 계산하지 않는다.

Chrome에서는 실제 제품 컴포넌트를 격리 PGlite에 연결해 디하 열람→거래 상세 조회→관리자 역할 저장/감사→응대 직원 답장·배정→사업 운영 관리자 설정 표시/직원 배정 버튼 없음→권한 회수와 사업 목록 제거를 확인했다. 백오피스 직원은 백오피스 상담과 담당 후보만 표시되는 것을 확인했다. 이름/계정/고객/이메일/HTTP 모두 가상이며 실제 고객·Google 승인·운영 DB 접근은 없다. 조직의 실제 업무 검수, 모바일 별도 크기 검수는 남아 있다.

근거: 제공 리서치의 [Opencom 데이터 모델 `workspaceMembers`](https://github.com/opencom-org/opencom/blob/bf928a43bf75baee793886efe9cfa68d4f39b659/docs/data-model.md)는 사업 멤버와 owner/admin/agent/viewer 역할을 명시한다. 샌드비에서는 기존 조직 소유자/관리자를 유지하고 사업 역할에 viewer/agent/manager를 독립 구현했다. 외부 코드를 복사하거나 타 서비스의 비공개 권한 엔진을 관찰한 것으로 주장하지 않는다. 원본 확인/고정 소스 근거는 [RESEARCH-APPLIED.md](RESEARCH-APPLIED.md), 파일/스크린샷/검사 로그 해시는 `evidence-manifest.json`의 `accessQa`에 있다.
