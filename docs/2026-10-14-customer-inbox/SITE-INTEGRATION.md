## 디하 서버 경로

기존 Firebase HTTPS 함수의 Express 앱에 `POST /support/identity`를 추가했다. 프런트는 Firebase 클라이언트 ID 토큰을 `Authorization: Bearer …`로 전달한다. 서버는 `verifyIdToken(token,true)`와 `users/{검증 uid}`의 `userType=client`를 확인한다. 요청 본문의 uid/이메일/사업 번호를 사용하지 않는다. 파트너·관리자·회수/비활성 로그인·미등록 사이트는 거절한다.

이름·이메일·전화·회사명은 확인한 회원 문서에서 읽어 서버에 고정한 사업으로 동기화한다. 회사명만으로 회사 ID의 동일성을 추정하지 않는다. 서버 서비스 토큰으로 샌드비 고객 API와 `/api/v1/inbox/sessions`를 호출하며 응답은 짧은 인증·만료·공개 채널 키다. no-store, 제한 시간, 리다이렉트 거절과 응답 검증을 적용한다. 모든 설정은 `SENDB_SUPPORT_*`에 명시하며 운영 주소 기본값은 없다.

두 HTTP 호출은 하나의 트랜잭션이 아니므로 동기화 후 인증 발급만 실패할 수 있다. 같은 uid의 재시도는 같은 고객을 재사용한다. CRM 보관은 계정 정지가 아니라는 기존 정책에 따라 보관 고객도 같은 상담을 이어갈 수 있고 CRM 보관은 해제하지 않는다. 내부 표시를 false로 임의 덮어쓰지 않는다.

## 확인한 증거

- 서버 신규 검사15: 설정/출처·헤더·회수 오류·회원 역할·서버 문서/uid·위조 본문 무시·no-store·공급자 오류/응답·HTTP·실제 라우터의 Firebase 회수 확인 조립.
- 기존 포함 서버 단위95, 전체 TypeScript 컴파일, 신규 기능 ESLint 통과.
- 샌드비 교차 SQL/API8: 실제 고객 upsert/JWT/프로필·빈 상담 없음, 갱신 멱등, 같은 Firebase uid의 두 사업 격리, 읽기 키·타 사업 채널 차단, 실제 회원 문의의 동일 고객 저장, CRM 보관/상담 이력 보존, 꺼진 채널 차단. 기존 플랫폼 API11도 함께 통과했다.
- Firebase/Firestore 로그인 문서와 공급자는 가상 대체했다. 샌드비 저장 로직은 실제 API/SQL을 PGlite에서 실행했다. 실제 Firebase/운영 DB·실제 고객/메일/SMS·실제 서버는 호출하지 않았다. `evidence-manifest.json`의 `siteIdentityQa`에 파일/로그 해시를 기록한다.

교차 검사는 디하 서버에서 `pnpm exec tsc --outDir lib-test --module commonjs --skipLibCheck`로 컴파일한 뒤 샌드비 저장소에서 실행한다. 인자는 컴파일한 서버 저장소의 절대 경로다. 원본 Firebase entrypoint나 환경/credential 파일을 실행하지 않고 순수 어댑터에 가상 API transport를 주입한다.

```sh
node --import tsx scripts/check-designer-hire-identity.cjs F:/Dev/sendb-sites/designer-hire-server
```

## 실제 페이지 조립 추가 검수

디하 실제 `_app`·FireAuthProvider를 조립한 검수에서 A→B 인증 이벤트 뒤 B 문서가 오기 전 이전 A 문서/상담이 남는 결함을 재현했다. 현재 UID를 즉시 상태로 전달하고 이전 문서·늦은 callback을 차단한다. 상담 인증 구독은 본문의 로그인 대기 gate 밖에서 유지한다. 기존 회원은 즉시 종료하지만 첫 비회원 로그인 대기에는 익명 iframe·초안을 숨겨 보존하고 확인된 고객 문서 뒤 병합한다. 같은 UID 정상 갱신은 초안을 지우지 않는다.

로컬 Chrome에서 인증17개, 실제 CTA/가이드/라우터9개를 확인했다. 공개/비공개 페이지 대기·오류/삭제/ID 불일치·로그아웃/비고객 역할·늦은 토큰을 검사했고, A 토큰이 끝나기 전 B가 연결된 뒤 늦은 A 응답이 반영되지 않았다. 실제 푸터/설정/지원 알림/모바일 문의 버튼, 실제 가이드와 `/main/chat`의 양방향 중첩 숨김·초안 복원을 확인했다. 390px 프레임의 내부 viewport는389px이며 실제 반응형 CSS의 모바일/데스크톱 표시를 확인했다. Firebase·고객/업무/결제/AI 데이터와 외부 부수 효과는 가상 대체다. 실제 Firebase나 전체 사업 업무 인수로 확대 해석하지 않는다. 소스27개·화면·원본 snapshot 해시는 `pageBoundaryQa.designer`에 기록한다.

디하 전체 단위90·관련40·실제 SDK 최초 boot/재연결 timeout→회원 병합 교차VM2·앱/테스트 타입·격리30페이지 빌드를 통과했다. 기존 전체 lint 경고와 수정 파일의 기존 방문 기록 경고1은 보존했다. 이전67/75개와 단순 세션 주입 검수는 당시의 근거이며 이 실제 조립 검수로 보완한다.

## 승인 이후 검토할 설치·인수 순서

1. 네 저장소 commit·0112 SQL 해시·SDK1.4/위젯·빌드 ID·도메인·한계를 한 묶음으로 고정한다. 함께 배포될 기존 여정/메일 변경도 검토한다.
2. 기존 채널톡 빌드/설정·상담 담당 절차, DB/첨부/키 관리 위치의 복구 가능성과 전환 뒤 신규 자료 보존을 확인한다.
3. 미적용 선행 SQL과0112를 포함한 호환 샌드비 API/SDK/위젯을 먼저 검증한다. 실패하면 사이트 공급자를 전환하지 않는다. 신규 워커는 기본 꺼짐을 유지한다.
4. 실제 사업·직원 역할/서버 토큰·채널 origin을 확인하고 디하 서버의 인증 교환을 검수한 뒤 프런트 공개 설정을 준비한다. 공개 값은 브라우저 빌드에 묶인다.
5. 원본 미리보기→사람 실행→첨부 보충 후 건수/관계/해시·실패 목록과 늦게 들어온 원본 자료를 대조한다.
6. 승인한 한 사업/관찰 범위부터 새 빌드를 전환하고 두 위젯을 동시에 시작하지 않는다. 진행 중 채널톡 상담은 합의한 경로에서 마친다.
7. 현업 인수 뒤 AI/자동화/외부 웹훅/자동 배정은 각 품질·발송·설정 승인 범위에서 따로 켠다. 현재 사용하지 않는 Gmail/외부 채널은 필수 게이트로 요구하지 않는다.
8. 관찰·자료 대조·부하 목표·복구 리허설을 통과한 사업만 전환 완료로 판정한다. 남은 고급 요구를 지우거나 구독 해지·원본 삭제를 자동 수행하지 않는다.

## 실패 시 복귀 준비

잘못된 이력 노출, 접수/답변/첨부 실패, 중복 신청, 자료 누락, 의도하지 않은 발송이나 합의한 오류 목표 초과가 복귀 검토 조건이다.

1. 확대를 멈추고 범위·시각·버전·처리 ID를 기록한다. 완료한 전송을 회수했다고 표시하지 않는다.
2. 관련 사업의 새 자동 동작만 중지하고 queued/running/unknown/sent 결과를 대조한다. 기존 메일/여정 설정을 일괄 바꾸지 않는다.
3. 검증해 둔 채널톡 프런트 빌드로 접수 경로를 되돌리고 한 위젯만 시작하는지 확인한다. 환경값 변경만으로 이미 열린 탭까지 바뀐다고 가정하지 않는다.
4. 기존 샌드비 탭을 채널 비활성화로 차단할지, 기존 상담만 마칠지 결정한다. `shutdown()`/새로고침은 탭 메모리의 미전송 문장·선택 파일·백오랩 신청 대기 요약을 지울 수 있다.
5. 새 상담/첨부 blob·CRM·감사·이전 지문·outbox/AI/자동화·0112 복수 문의/읽음을 보존한다. 전환 전 DB 백업으로 덮어써 신규 자료를 없애는 방식은 복귀안이 아니다.
6. 상담별 한 응대 서비스·담당·마지막 처리 메시지를 정해 중복 답변을 막는다. 내부 clientId 멱등은 채널톡과 샌드비 사이의 전역 멱등이 아니다. 결과 미확인 요청을 새 ID로 무조건 재생성하지 않는다.
7. 원인에 맞는 최소 회귀·자료 대조·승인 후 재전환한다. 꺼진 기간 이벤트를 무조건 재전송하지 않는다.

0112 down migration이나 pre0112 서버로의 자동 downgrade는 검증하지 않았다. 현재 호환 서버와 신규 자료를 유지하고 사이트 접수 경로를 복귀시키는 안을 우선 검토한다. 양방향 자동 자료 역이전, 교차 서비스 전역 중복 방지, 열린 모든 탭의 원격 초안 보존/위젯 교체, 완료된 외부 발송 회수, 미확정 보존/영구 파기·선택 복구는 현재 구현됐다고 주장하지 않는다.
