# 상담 알림·업무시간·응대 목표·성과

직원/API 키 권한은 [사업별 역할 기준](ACCESS.md)을 따른다. 이 문서의 설정 관리자는 해당 사업의 운영 관리 역할 또는 조직 관리자이며, 일반 직원은 배정받은 사업 역할에 맞는 업무를 사용한다.

2026-10-15 dev 구현/격리 검수. 두 사업이 같은 API·SDK와 상담/CRM 고객 정보를 사용한다. 실제 서비스 설치·운영 활성화·팀 업무 검수는 별도 단계다.

## 사용하는 순서

1. **고객 상담 → 운영·성과 → 업무시간·응대 목표**에서 현재 사업을 확인한다. 관리자가 시간대, 요일별 구간, 휴무일과 고객 안내를 정한다. 평일 09~18시·매일 24시간 미리 설정을 제공하며 점심은 같은 요일의 구간을 나눈다.
2. 첫 답변·추가 답변·해결 목표를 업무시간 분으로 입력한다. **AI 자동답변도 응답으로 집계**, **보류 시간 제외**를 선택하고 **운영 설정 저장**을 누른다. 목표는 기본 꺼짐이고 설정 전 소요시간은 24시간 기준이다. 비현실적으로 긴 목표/매우 짧은 업무시간 조합은 저장 전에 거절한다.
3. **알림**에서 새 문의·담당 배정·AI 사람 이관·회원 이력 연결·목표 초과를 본다. 각 카드에 사업명을 표시하며 누르면 해당 사업의 상담으로 이동한다. 미배정 문의는 조직의 활성 직원, 배정된 문의는 활성 담당자가 받는다. 담당자가 비활성화/조직에서 제거되면 활성 직원에게 미배정처럼 전달한다.
4. 상담 상세의 **응대 목표**에서 기다리는 질문과 첫/추가 답변·해결 시한을 본다. 보류 중에는 해당 설정에 따라 시간을 제외한다. 답변을 보내도 보류 상태 자체를 자동 해제하지는 않으며, 고객의 새 메시지나 진행중 선택으로 재개한다.
5. **응대 성과**에서 날짜·웹/이메일 매체를 고른다. 시작/진행/종료, 첫 답변/해결 중앙값과 표본, 목표 준수/초과, 미응답을 남긴 종료, 일별·담당자별 결과를 확인하고 개별 상담으로 이동한다.

고객 안내는 설정한 근무 구간의 현재 상태와 다음 시작 시각이다. 업무시간 밖에도 문의를 접수한다. 목표를 켜는 것과 서버의 자동 초과 알림 검사를 켜는 것은 별도이며, 서버가 꺼져 있으면 화면에서 안내한다. 새 문의/담당 배정 등 앱 내 알림은 원본 저장 때 등록하므로 초과 검사 워커와 독립적이다. OS 권한·푸시·메일·Google Chat 전송은 추가하지 않았다.

## 집계 기준

- 첫 실제 고객 문의가 응대 사례를 만든다. 방문/빈 상담 생성은 지표 시작이 아니다. 해결 후 고객이 다시 문의하면 같은 대화에서도 새 사례가 된다. 수동으로 다시 열기만 한 상태에서는 다음 고객 문의부터 새 사례를 시작한다.
- 답변 전 연속 질문은 같은 대기 의무로 묶어 최초 질문의 시한을 유지한다. 답변 후 다음 질문은 추가 답변 의무다. 회원 이력을 병합하면 두 사례와 기존 시한을 보존하며 연결된 상담에서 응대한다. 따라서 사례 수와 고유 고객/대화 수는 다를 수 있다.
- 기본은 상담원이 보낸 공개 답변 기준이다. 상담원이 AI 초안을 검토해 보낸 답변은 포함한다. 내부 메모는 집계하지 않는다. AI 자동답변은 해당 사례의 설정이 허용할 때 포함하며 응답자를 따로 기록한다.
- 이메일 답장을 대기열에 넣은 시각은 응답 완료가 아니다. Gmail의 접수 확인 시각을 사용한다. 본문을 준비한 뒤 도착한 새 질문은 이전 답장이 나중에 접수돼도 대기로 남긴다. 공급자 접수는 고객 도착/열람과 다른 상태다.
- 시한과 소요시간은 해당 사례가 시작할 때의 설정/시간대/휴무일을 고정해 계산한다. 설정 변경을 기존 사례에 소급하지 않는다. 보류를 제외하도록 정했다면 실제 보류 구간의 업무시간을 차감하고 아직 지나지 않은 시한을 이동한다. 보류 전에 이미 초과한 목표는 그대로 초과다.
- 늦게 수신한 과거 이메일은 확인된 최신 답장 이전의 질문이면 새 대기로 재개하지 않는다. 더 이른 최초 질문이 확인되면 시작점·소요시간을 보정한다. 설정 적용 이전 질문이었다면 목표 적용을 해제하고 그 사례의 기존 초과 알림을 읽음 처리한다. 일반 메시지 미확인 표시는 유지한다.
- 미응답을 남기고 종료한 사례를 답변 목표 준수로 간주하지 않는다. 표본이 없으면 중앙값은 `—`다. 준수/초과는 목표가 있는 응대, 대기/미응답 종료와 시간 표본은 전체 응대 기준이다. 초과 상태의 미답변은 대기 수에도 포함된다.
- 보고서는 선택한 시간대의 시작일 00:00 이상 ~ 종료일 다음 날 00:00 미만에 **시작한 사례**를 집계한다. 최대 1년 범위다. 응답/해결 시점만 해당 기간에 있는 옛 사례를 다른 코호트로 섞지 않는다. 종료 담당자는 종료 당시 담당자, 진행 사례는 현재 담당자 기준이다.
- 확인된 CRM 내부 고객, 과거 서비스에서 가져온 보관 상담은 제외한다. 입력한 이메일만으로 내부 직원이라고 추정하지 않는다. 나중에 내부로 분류되면 해당 고객의 알림/성과도 숨긴다. 지표 도입 전의 과거 처리 시각을 추정해 채우지 않으며, 아직 사례가 없는 과거 문의 수를 화면에 표시한다.

알림을 읽음 처리하는 것과 상담의 고객 메시지를 읽는 것은 별도 동작이다. 상담을 읽으면 확인한 customerSeq까지의 고객 문의 알림도 읽음으로 표시한다. **표시된 미확인 모두 읽음**은 목록에 받은 ID만 처리하므로 그 뒤 도착한 알림은 남는다. 50개 알림·100개 사례 커서로 이전 항목을 확인한다.

## API/SDK

관리자 화면:

- `GET/POST /api/inbox-operations/channels/:id`: 설정/서버 준비 상태 조회, `{version,policy}` CAS 저장. 변경은 현재 관리자만 가능하다.
- `GET /api/inbox-operations/reports?channelId=&from=YYYY-MM-DD&to=YYYY-MM-DD&medium=all|web|email&before=UUID`: 전체 기간 집계·일별·담당자·100개 사례. 커서는 목록에만 적용하고 집계를 줄이지 않는다.
- `GET /api/inbox-operations/conversations/:id`: 최근 10개 사례, 현재 대기/시한·초과·보류 상태.
- `GET /api/inbox-notifications?channelId=&unread=true&before=UUID`: 로그인 직원 본인 알림, 개인 미확인 수, 50개 커서.
- `POST /api/inbox-notifications`: `{action:"read",ids:[...]}` 최대 100개/호출. UI는 여러 페이지를 확인한 경우 묶음 처리하며 다른 직원/조직 ID를 거부한다.
- 공개 상담 설정 응답의 `businessHours`: 선택 공개한 시간대·현재 열림·다음 시작·안내 문구만 포함한다. 내부 목표나 개인 알림은 공개하지 않는다.

서비스 서버 API는 `/api/v1/support/channels/:id/settings`, `/api/v1/support/reports`, `/api/v1/support/conversations/:id`, `/api/v1/support/notifications`에 같은 계약을 제공한다. 채널의 사업 토큰 범위를 검사한다. 개인 알림 API는 발급 직원 본인만 조회/확인하며 channelId를 필수로 받는다. 설정 변경은 관리자 발급+update 권한이 필요하다.

`sdk/server.ts`: `supportSettings`, `saveSupportSettings`, `supportReport`, `supportConversation`, `supportNotifications`, `readSupportNotifications`. DTO는 `sdk/support-types.ts`다. 두 사업은 자기 토큰과 채널 ID를 사용한다.

```ts
const report = await client.supportReport(channelId, {
    from: "2026-10-01", to: "2026-10-31", medium: "all",
});
console.log(report.summary, report.coverage);
// 다음 페이지에서도 summary는 전체 기간 값이다.
if (report.hasMore) {
    const next = await client.supportReport(channelId, {
        from: "2026-10-01", to: "2026-10-31",
        before: report.rows.at(-1)!.id,
    });
}
```

마이그레이션 **0101**은 운영 설정·개인 알림·응대 사례·답변 의무를 추가한다. 기존 트랜잭션 outbox를 재사용해 원본과 같은 트랜잭션에서 등록한다. 실패하면 메시지·이벤트·알림·사례가 함께 롤백된다. 과거 import origin은 건너뛴다. 앱 시작 시 기존 마이그레이션 절차 후 스케줄러를 등록한다.

초과 검사 스케줄러는 배포 런타임 production 모드와 `CUSTOMER_INBOX_OPERATIONS_WORKER=on`을 모두 요구하며 기본 꺼짐이다. 15초마다 제한된 양을 조회하고 대화→사례→답변 의무 잠금과 고유 이벤트 키로 중복/완료/보류/정책 중지를 재검사한다. 외부 네트워크 호출은 없다. 격리 QA는 이 플래그를 켜거나 개발 환경을 운영으로 위장하지 않고 함수에 가상 DB/시각을 주입했다. 실제 dev/운영 서버 설정은 활성화하지 않았다.

팀별 라우팅/구독·모바일/OS push·외부 채널 알림, 우선순위/고객 등급별 여러 SLA 정책, 과거 지표 정밀 복원·전체 내보내기/고급 분석, 실제 팀 업무/부하/워커 장애 모니터링·보존/삭제/전환 검수는 남아 있다. 전체 대체 완료나 운영 배포를 의미하지 않는다.

참고 근거는 [Chatwoot의 개인 알림 모델](https://github.com/chatwoot/chatwoot/blob/develop/app/models/notification.rb), [Intercom의 첫/추가/해결 SLA와 업무시간](https://www.intercom.com/help/en/articles/6546152-set-slas-for-conversations-and-tickets), [응대 지표 설명](https://www.intercom.com/help/en/articles/7022438-reporting-metrics-attributes)이다. 공개 문서/도메인 구조를 참고해 기존 샌드비 이벤트에 구현했다. 설정 고정·AI 포함 선택·코호트/표본 표시 등은 두 사업에 맞춰 정한 샌드비의 동작이며 원제품과 완전히 같은 계산이라고 주장하지 않는다.
