# 고객 플랫폼 외부 연동

## 사용 방법

고객 관리 → **고객 플랫폼 외부 연동**(`/customer-webhooks`)에서 사업을 선택한다. 두 사업은 수신 주소·구독 이벤트·서명 키·전달 이력을 별도로 관리한다. 선택한 사업은 URL에 보존한다.

1. **새 웹훅**에서 이름, 공개 HTTPS 수신 주소, 전달할 이벤트를 등록한다. 새 연동은 꺼진 상태로 만든다.
2. 발급 화면의 **서명 키 복사**로 수신 서버에 키를 저장한다. 키는 목록·조회 API에서 다시 보여주지 않는다. 분실하면 새로 발급한다. 키 원문을 문서·로그·저장소에 넣지 않는다.
3. **웹훅 전송 켜기 → 설정 저장**으로 활성화한다. 이후 선택한 이벤트부터 대기열에 모은다. 등록 이전 또는 꺼진 기간의 이벤트를 자동으로 소급 전송하지 않는다.
4. **가상 이벤트 전송**으로 고객 데이터 없는 연결 확인 이벤트를 준비한다. 서버 자동 워커가 꺼져 있으면 화면에 안내하며 대기열만 만든다.
5. **전달 이력**에서 상태·HTTP 응답·시도별 시각/수신 주소·원본 이벤트를 확인한다. 실패/취소 항목은 **이 이벤트 다시 전달**로 명시적으로 재시도한다. 완료된 이벤트는 이 버튼으로 다시 보내지 않는다.

이름 변경은 대기 전달을 보존한다. 주소·구독 이벤트·활성화 상태·서명 키 변경은 이전 설정의 대기/재시도를 취소한다. 이미 진행한 HTTP 요청은 회수할 수 없으며 늦은 응답을 별도 시도 기록에 남긴다. 취소 후 새 설정으로 재전달할 때는 같은 이벤트 ID와 원본을 사용한다. 설정 version 충돌은 저장을 거절하고 초안을 보존한다. 관리자는 최신 설정을 불러와 다시 편집한다.

## 이벤트와 전달 계약

고객/회사 생성·변경, 고객 행동, 상담 생성/상태/담당/고객 프로필 변경, 공개 메시지, 파이프라인/딜/할 일 생성·변경과 `platform.test`를 지원한다. 고객·회사 upsert는 값이나 관계가 실제 바뀌었을 때만 이벤트를 남긴다. 메시지/행동/영업 생성의 기존 멱등 번호를 재사용한 재시도는 이벤트와 대기열을 중복 생성하지 않는다. 내부 메모와 메모 첨부는 웹훅에서 제외한다. 공개 파일은 메타데이터만 보내고 원본은 기존 인증 파일 API로 읽는다.

원본 변경·`platform_events`·구독별 `platform_webhook_deliveries`는 같은 DB 트랜잭션이다. 원본을 롤백하면 전달도 없다. HTTP 호출은 이 트랜잭션 밖에서만 한다. 이벤트 본문은 생성 당시의 스냅샷이며 재시도 때 변경하지 않는다.

```json
{
  "id": "이벤트 UUID",
  "sequence": "DB에서 발급한 순번 문자열",
  "type": "message.created",
  "apiVersion": "2026-10-14",
  "workspaceId": 8,
  "occurredAt": "2026-10-14T00:00:00.000Z",
  "data": { "conversationId": "상담 UUID", "message": {} }
}
```

`sequence`는 원본이 바뀌는 순서를 비교할 때 사용한다. 전달 순서는 보장하지 않는다. 수신기는 같은 고객/딜 등 엔티티의 현재 상태를 갱신할 때 기존보다 낮은 순번의 스냅샷으로 덮어쓰지 않아야 한다. 순번은 롤백 때문에 연속하지 않을 수 있다.

헤더는 `X-Sendb-Id`(이벤트 ID), `X-Sendb-Timestamp`(전송 Unix 초), `X-Sendb-Signature`(`v1=` + HMAC-SHA256 hex), `X-Sendb-Delivery`(구독별 전달 UUID), `X-Sendb-Attempt`(누적 시도 수)다. 서명 원문은 `이벤트ID.전송시각.원본JSON`이고 키는 발급된 `whsec_` 뒤의 base64url을 디코딩한 값이다. 재시도 때 이벤트 ID/내용은 유지하고 전송시각/서명은 새로 만든다.

수신 서버는 JSON으로 파싱하기 전 원본 UTF-8 문자열로 검증한다. `sdk/webhooks.ts`의 `verifySendbWebhook`은 서명, 헤더/본문 ID 일치, 전송시각 ±5분을 검사한다. 이 함수 자체는 중복 처리를 막지 않는다. 수신기의 영구 DB에 이벤트 UUID 고유 제약을 두고, 수신 기록과 업무 변경을 같은 트랜잭션으로 처리한 뒤 2xx로 응답한다. 메모리 Set만으로 운영 멱등 처리를 구현하지 않는다.

## API와 SDK

직원 경로의 접두어는 `/api/customer-platform`, 서비스 서버는 `/api/v1`이다. 고객 브라우저용 messenger API에서 웹훅 설정·전달 이력을 공개하지 않는다.

| 경로 | 동작 |
|---|---|
| GET/POST `/webhooks` | 사업별 조회(`workspaceId`) / 꺼진 연동 생성 |
| GET/PATCH `/webhooks/{id}` | 설정·최근 감사 조회 / 조회한 version으로 설정 변경 |
| POST `/webhooks/{id}` | `action:test,clientId` 가상 이벤트 / `action:rotate,version` 새 키 |
| GET `/webhooks/{id}/deliveries` | 최대 100건·state 필터·before UUID 커서 |
| GET/POST `/webhook-deliveries/{id}` | 원본/시도 상세 / `action:retry` |

일반 성공/오류는 기존 JSON envelope다. 생성/회전만 `{endpoint,secret}`를 한 번 반환하며 조회는 cipher/원문을 제외한다. 관리 작업은 현재 DB 역할의 관리자만 가능하다. 서비스 API도 발급자의 현재 관리자 역할과 사업 create/update 권한을 함께 검사한다. 읽기는 사업 read 권한이다. 토큰을 폐기해도 별도로 등록한 웹훅 설정은 남으므로 전송을 중단하려면 해당 웹훅을 끈다.

`SendbClient`에 `webhooks`, `createWebhook`, `updateWebhook`, `webhookDeliveries`, `retryWebhookDelivery`를 추가했다. 서비스 토큰은 각 사이트 서버에만 두고 수신 서버에서 검증할 서명 키와 구분한다.

## 워커와 운영 검토

`0093_platform_webhooks.sql`은 이벤트, 수신 설정, 전달, 시도, 설정 감사 테이블을 추가한다. 기존 메일 대기열·고객 여정 전송 정책은 변경하지 않는다. 이벤트/전달 원본은 현재 영구 보존하며 삭제·보존 정책은 R14에서 확장한다. 사업마다 최대 20개 수신 설정을 지원한다.

자동 워커는 production 런타임에서 `CUSTOMER_WEBHOOK_WORKER=on`일 때만 시작한다. 기본은 꺼짐이다. `CUSTOMER_WEBHOOK_ENCRYPTION_KEY`를 안정적인 전용 값으로 설정하며, 없으면 JWT_SECRET에서 용도별 키를 파생한다. 암호화 키를 바꾸면 기존 서명 키 복호화가 불가능하므로 임의로 교체하지 않는다. 이 작업에서 실제 서버 환경을 바꾸거나 실제 고객 이벤트를 외부에 전송하지 않았다.

워커는 DB 행 잠금/skip locked와 60초 lease를 사용하고, 각 시도를 HTTP 전에 기록한다. 죽은 워커의 미확인 시도는 보존하고 새 lease로 재시도한다. 동일 전송이 수신 서버에서는 성공했지만 응답을 잃을 수 있으므로 전달 보장은 **적어도 한 번**이다. 새 lease나 취소 상태를 늦은 워커가 덮어쓸 수 없다.

회차당 기본 5건, 최대 20건을 순차 처리하고 다음 회차는 5초 뒤다. HTTP는 DNS를 포함해 최대 10초, 리다이렉트를 따르지 않으며 응답 본문을 저장하지 않는다. 공개 HTTPS 호스트만 받고 전송 때 모든 DNS 결과를 검사한 뒤 확인한 IP로 연결한다. 기본 TLS 검증을 유지한다.

비2xx/연결 실패는 총 8회까지 시도한다. 간격은 1분·5분·15분·1시간·3시간·6시간·12시간이고 Retry-After가 더 길면 최대 하루까지 따른다. 이후 dead 상태에서 관리자 재시도를 기다린다. 수동 재시도는 자동 한도를 새로 시작하되 누적 시도 이력과 이벤트 ID를 유지한다.

검증: 단위 1,042개, 상담 SQL 22개, 플랫폼 11·영업 13·공통 활동 7·첨부 18개와 웹훅 API/SQL/워커 14개. 가상 두 사이트의 문의/행동 → 실제 outbox → 서명된 POST를 격리 HTTP 수신기로 보내 503→재시도→서명 검증→204를 브라우저에서 확인했다. 외부 HTTPS 전송은 검사한 transport 구현이며 실제 운영 호스트와의 TLS/방화벽/대규모 부하·두 사이트 운영 설치는 아직 검수하지 않았다.

참고 계약: [Intercom Webhooks](https://developers.intercom.com/docs/webhooks)의 구독/토픽/알림 구분과 [HubSpot 웹훅 설정](https://developers.hubspot.com/docs/apps/developer-platform/add-features/configure-webhooks)의 외부 동기화·이벤트 POST/2xx 응답 흐름을 확인했다. 비공개 SaaS 서버 구현을 REA로 복원했다는 뜻은 아니며, 기존 SDK REA 증거는 ANALYSIS.md를 유지한다. 서명·재시도 계약은 샌드비 자체 계약으로 세 서비스의 API와 자동 호환한다고 주장하지 않는다.
