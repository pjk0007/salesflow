# 조건별 상담팀 분류

2026-10-15 · `dev` / 초안 PR14. 샌드비 서버와 두 사이트의 운영 설정·DB·배포에는 적용하지 않았다. 기존 상담팀0106과 자동화0095 계약을 사용하며 새 마이그레이션은 없다.

## 사용하는 순서

1. **고객 상담 → 상담팀**에서 사업별 팀을 만든다. 자동 배정은 팀마다 선택하며 기본 꺼짐이다.
2. **고객 자동화 → 사업 선택 → 새 자동화**에서 시작 이벤트와 조건을 설정한다. 예를 들어 공개 메시지의 보낸 쪽이 고객이고 본문에 ‘디자인’이 포함되면 디하 도입팀으로, 백오랩의 ‘경리’ 문의는 경리 도입팀으로 보낼 수 있다. 조건 분류이며 LLM 의도 분석은 아니다.
3. 단계 행동에서 **상담팀 배정**을 선택한다. 같은 사업의 팀만 표시하며 보관된 팀은 선택할 수 없다. 사용할 팀이 없으면 먼저 팀을 만들라는 안내를 표시한다.
4. 기본값 **팀·담당자가 없는 상담에만 배정**은 현재 팀 또는 개인 담당이 있으면 그 단계를 건너뛴다. 대기 중 사람이 배정했거나 재문의가 와도 기존 담당을 유지하고 실행 이력에 사유를 남긴다.
5. 꼭 이관할 규칙은 **기존 팀·개인 배정을 선택한 팀으로 교체**를 선택한다. 다른 팀으로 이동할 때 개인 담당이 해제된다. 수동 팀은 대기열에, 자동 팀은 현재 응대 가능한 팀원 중 진행중 상담 수/마지막 배정 순으로 보낸다. 같은 팀이면 현재 개인 담당을 유지하며 다시 추첨하지 않는다. 접속 필터를 선택한 팀은0107의 [현재 접속/응대 상태](PRESENCE.md)도 확인한다. 팀원이 없으면 팀 대기열에 남긴다.
6. **검토할 새 버전 저장 → 모의 실행 → 사람이 검토 후 게시**한다. 자동 배정 예상 담당자를 보여주지만 실제 배정/순서를 변경하지 않는다. 실행 시점의 설정·권한·상담 수에 따라 담당자는 달라질 수 있다. 다음 단계 조건도 모의 실행의 예상 값으로 비교하며 확정된 결과가 아니다.
7. **실행·예약 이력**에서 실제 팀/개인 이름과 연결 상담을 확인한다. 모의 실행의 예상 결과와 실제 처리 결과를 구분한다. 기존 자동화의 중단·재시도·버전 고정 계약을 그대로 사용한다.

팀 배정은 기존 개인 배정·앱 알림·상담 감사·웹훅 outbox 저장 함수를 사용한다. 새 문의를 전부 받는 기본 팀을 자동 생성하지 않는다. ‘상담 시작’ 이벤트에 팀 단계를 게시하면 해당 사업에서 새로 시작하는 상담을 분류할 수 있다. 사람에게 이관하는 단계와 팀 배정은 별도 행동이며 팀 변경만으로 AI 응대 방식을 바꾸지 않는다.

## API/SDK

기존 `/api/customer-workflows`와 `/api/v1/workflows`, `SendbClient.saveWorkflow`를 사용한다. 정의의 단계에 다음 계약을 추가한다.

```json
{
  "id": "00000000-0000-4000-8000-000000000001",
  "label": "디자인 문의를 도입팀으로",
  "kind": "team",
  "teamId": "00000000-0000-4000-8000-000000000002",
  "onlyUnassigned": true,
  "when": {
    "mode": "all",
    "rules": [{"path":"event.data.message.body","op":"contains","value":"디자인"}]
  }
}
```

UUID는 예시다. 팀 API로 만든 실제 같은 사업의 활성 팀 ID를 사용한다. `onlyUnassigned`를 생략하면 저장 시 `true`로 정규화한다. `false`는 명시 이관이다. 팀 제거/개인 배정 해제는 기존 상담 PATCH/담당자 단계에서 관리하며 이 단계의 `teamId`는 필수 UUID다. 화면의 조건 목록에 `conversation.teamId`, `conversation.assigneeId`도 추가했다.

저장·모의 실행·게시에서 같은 조직/사업의 활성 팀·상담창을 확인한다. 실행 때는 대화를 잠근 최신 값으로 보호 조건을 다시 확인하고 기존 배정 함수의 팀 행 잠금·권한/소속 확인·CAS를 따른다. 게시 후 대상 팀을 보관하면 실제 이관을 실패로 표시하며 상담과 배정 순서/단계 결과를 함께 롤백한다. 모의 실행에서 팀 뒤에 팀 밖 개인을 지정하는 불일치도 검토 오류로 표시한다. 앞 단계 조건이 달라질 수 있으므로 실제 실행에서도 검사는 반복한다.

단계 결과는 `{conversationId,channelId,teamId,teamName,assigneeId,assigneeName}`이다. 팀/개인 이름은 처리 시점의 값으로 남기며 이후 팀 이름이 바뀌어도 당시 결과를 읽을 수 있다. 업무를 처리할 직원의 접근 권한을 새로 부여하지 않는다. 외부 고객 메일/Google Chat을 보내는 행동도 추가하지 않았다.

## 검수

`node --import tsx scripts/check-workflow-routing.cjs`: 새 SQL/API12개 + 플랫폼 기본11개. 기본값·native/서비스 계약·사업/키/보관 참조·모의 실행 무변경·조건 분류/후속 조건·이미 배정된 상담 보호·명시 교체/같은 팀 유지·자동 부하 분산/실제 결과·게시 후 보관·잘못된 후속 개인·배정과 단계 원자성/수동 재시도·대기 중 수동 배정·권한 회수/빈 대기열·백오랩 독립 실행을 확인했다.

기존 자동화15개·상담팀18개 회귀와 전체 단위1,093개, 기능 lint, 실제 환경 파일을 쓰지 않는 전체 Next 빌드(타입 포함)가 통과했다. Chrome에서 디하 가상 사이트의 디자인 문의→모의 실행/사람 게시→수동 팀 대기열, 백오랩 경리 문의→예상 담당 표시→사람 게시→실제 자동 담당/이력, 담당자 수동 변경 뒤 재문의→기존 담당 유지/제외 사유를 검수했다.

증거는 `evidence-manifest.json`의 `workflowRoutingQa`와 로컬 `artifacts/sendb-replacement-20261014/workflow-routing-*`에 기록한다. 모든 데이터는 가상이며 loopback/PGlite만 사용했다. UI 시험용 워커를 직접 구동했으며 제품의 자동 워커 기본 꺼짐 설정은 바꾸지 않았다. 수용량0의 모의 실행/사람 게시 후 실제 한도 재확인은 PGlite/별도 PostgreSQL에서 추가 검수했다([CAPACITY.md](CAPACITY.md)). 실제 다중 서버 부하·전체 사이트 설치·실제 업무 검수·근무시간·고급 분기·전체 채널 전환은 남아 있다. 전체 대체 완료는 [REPLACEMENT.md](REPLACEMENT.md)의 기준으로 따로 검증한다.
