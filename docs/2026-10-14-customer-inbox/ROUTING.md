# 상담팀과 담당 배정

2026-10-15 · `dev` / [초안 PR14](https://github.com/pjk0007/salesflow/pull/14). 마이그레이션 `0106_inbox_teams.sql`과 접속 필터의 `0107_inbox_agent_presence.sql`을 추가했다. 실제 DB 적용·팀/직원 권한 설정·main 병합·운영 배포는 수행하지 않았다.

## 사용하는 흐름

관리자는 고객 상담의 **상담팀**에서 사업별 팀 이름·담당 업무·팀원·자동 배정·사용 여부를 저장한다. 팀원은 그 사업의 응대 권한이 있는 직원 중 선택하며 팀 구성 자체가 접근 권한을 부여하지 않는다. 회수된 기존 팀원은 설정에 남겨둘 수 있지만 새로운 배정 후보에서는 제외한다. 새 팀의 자동 배정은 기본 꺼짐이다.

상담 오른쪽 **상담팀**에서 팀을 바꾸면 기존 개인 담당을 해제하고 팀 설정에 맞춰 배정한다. 수동 팀이면 대기열에서 팀원을 선택한다. 자동 팀이면 현재 응대 권한이 있는 활성 팀원 중 같은 사업의 진행중 상담이 적은 사람을 고른다. 부하가 같으면 마지막 자동 배정이 오래된 순, 직원 ID 순으로 결정한다. 팀 행 잠금으로 선택을 직렬화하고 배정 순서 기록도 상담 변경과 같은 트랜잭션에 저장한다. 0107의 `requireAvailable`을 켠 팀은 현재 접속과 개인의 응대 가능 상태도 확인한다. 기본 꺼짐이며 [PRESENCE.md](PRESENCE.md)를 따른다. 0108의 개인별 수용량과 대기열 재처리는 [CAPACITY.md](CAPACITY.md)를 따른다. 기본 무제한이며 같은 사업의 여러 팀을 합산한다. 사업 업무시간별 배정은0109의 [BUSINESS-HOURS-ROUTING.md](BUSINESS-HOURS-ROUTING.md)를 따른다. 직원별 교대표는 후속이다.

응대할 팀원이 없으면 담당자를 비운 채 팀 대기열에 남긴다. 팀 설정 저장만으로 기존 대기열을 소급 배정하지 않는다. 배정 수용량의 수동 재처리 또는 별도로 활성화한 큐 워커에서 빈 슬롯을 확인한다. 새 문의의 기본 팀을 자동 생성하지 않는다. 조건별 분류는 [고객 자동화의 상담팀 배정](WORKFLOW-ROUTING.md)으로 설정하고 사람이 검토 후 게시한다. 자동 배정은 수동/자동화 팀 이관 또는 AI의 사람 이관 과정에서 실행한다. API에서 팀과 개인을 함께 지정하면 유효한 명시적 개인 배정을 우선하며 팀 밖 직원은 거절한다.

왼쪽 **팀 대기열**은 모든 팀/팀 없음/각 팀으로 검색·상태·집계를 제한한다. **내 팀 상담**은 현재 직원의 팀 구성으로 서버에서 필터링한다. 팀은 대기열·담당 후보·알림 범위를 정하고 상담 열람은 기존 사업 권한을 따른다. 열람 직원도 허용된 사업의 팀 대기열을 볼 수 있으며 응대·설정 변경은 기존 역할이 필요하다.

개인 담당이 있으면 그 담당자에게, 개인이 없는 팀 상담은 응대 가능한 팀원과 사업 운영 관리자에게 앱 알림을 전달한다. 다른 팀 직원에게 일반 팀 이관 알림을 보내지 않는다. 기존 멘션은 명시적으로 선택한 같은 사업 직원에게 전달하는 계약을 유지한다. 외부 이메일/Google Chat 알림을 새로 보내는 기능은 아니다.

## 보존과 재시도

- 팀 사용을 끄면 보관한다. 기존 상담·담당자·구성원·감사를 보존하고 새 팀 배정은 막는다. 보관 팀도 대기열에서 조회/정리하고 다시 사용할 수 있다. 같은 이름의 보관 팀은 새로 만들지 않고 기존 팀을 복구한다.
- 팀/구성원을 바꿔도 이미 맡은 개인 담당을 일괄 교체하지 않는다. 현재 팀/응대 권한과 맞지 않는 기존 담당은 이름과 상태를 표시하며 새 배정에는 사용할 수 없다.
- 설정 편집은 버전을 확인한다. 충돌하면 작성 문장을 유지하고 **최신 설정 불러오기**를 눌렀을 때 서버의 최신 설정으로 바꾼다. 저장/배정 중에는 해당 컨트롤을 잠가 겹친 변경을 막는다.
- 비회원→회원 연결은 기존 회원에게 팀 또는 개인 담당이 있으면 그 조합을 우선한다. 회원 쪽 담당이 없으면 비회원 쪽 조합을 이어받는다. 고객의 공개 조회에는 내부 팀 정보를 내보내지 않는다.
- AI의 지정 이관 직원도 현재 팀원/응대 권한을 확인한다. 팀 밖 지정 직원이면 그 사람에게 배정하지 않고 팀의 자동 설정 또는 수동 대기열을 따른다.

## API와 서버 SDK

| 경로 | 계약 |
|---|---|
| `/api/inbox-routing/teams?channelId=…` | 직원 GET 목록 / POST 생성 |
| `/api/inbox-routing/teams/{id}` | 직원 GET 상세 / PATCH 부분 수정 |
| `/api/v1/inbox/teams?channelId=…` | 서비스 키 GET 목록 / POST 생성 |
| `/api/v1/inbox/teams/{id}` | 서비스 키 GET 상세 / PATCH 부분 수정 |
| 기존 상담 PATCH | `teamId:uuid|null`, `assigneeId:uuid|null`과 상담 `version`. 기존 상태/태그/CRM 계약 유지 |
| 기존 상담 GET 목록 | `teamId=uuid|none`, `filter=myTeams` 추가. native `view=list`의 집계도 같은 팀 조건 사용 |

생성은 `{channelId,name,description?,memberIds?,autoAssign?,requireAvailable?,enabled?}`다. 팀 이름은 사업 안에서 대소문자를 구분하지 않고 유일하며100자, 업무 설명500자, 팀원100명 이내다. PATCH는 `version`이 필수이고 생략한 필드를 보존한다. 직원은 사업 운영 관리, 서비스 키는 read/create/update 범위와 발급자의 현재 사업 역할을 함께 확인한다. 구성원 추가가 직원 권한을 복구하거나 생성하지 않는다.

`SendbClient.inboxTeams(channelId)`, `createInboxTeam(input)`, `updateInboxTeam(id,input)`과 기존 `updateConversation(id,{version,teamId,assigneeId})`를 사용한다. 타입은 `sdk/routing-types.ts`에 있다. 팀과 다른 사업 상담의 연결은 서비스 검사에 더해 DB의 `(team_id,channel_id)` 복합 관계로 막는다. 직원 지정 자동화와 조건별 팀 이관 단계/편집 UI는 동일한 배정 검사에 따른다. 팀 단계의 기본값은 기존 팀/담당자를 보존하며 명시 선택 시 교체한다.

설정 감사는 상담창 변경 이력, 상담의 팀/담당 변경은 해당 상담 변경 이력과 outbox에 기록한다. 같은 설정 저장은 버전/감사 중복을 만들지 않는다. 실제 설치 전에는0106~0109를 앱보다 먼저 검토/적용해야 한다. 이번 작업에서는 적용하지 않았다.

## 근거와 검수

[Chatwoot 공식 팀 가이드](https://www.chatwoot.com/hc/user-guide/articles/1677492970-adding-teams)의 팀/개인 담당 구분과 수동/자동 배정 개념을 참고했다. 샌드비는 기존 사업별 권한과 단일 사업 상담창 구조에 맞춰 독립 구현했다. 이 문서 참고는 비공개 SaaS 내부 실행을 REA로 관찰한 증거가 아니다. 기존 REA 아티팩트 근거는 [ANALYSIS.md](ANALYSIS.md)를 유지한다.

`node --import tsx scripts/check-inbox-routing.cjs`: 격리 PGlite/실제 API18개(기존 플랫폼API11 포함). 사업/직원/키 경계·부분 수정/멱등/충돌·수동/자동/빈 팀·부하 분산·역할 회수/보관·복합 DB 관계·팀 알림/다른 팀 제외·AI 이관·두 사업 회원 병합과 감사/배정 순서 롤백을 검사한다. 동시 요청 검사는 PGlite의 격리 실행이며 실제 다중 서버 부하를 증명하지 않는다.

기존 단위1,093·타입/기능 lint·실제 환경 파일 없는 전체 Next 빌드가 통과했다. 상담22·회원 연결12·운영23·AI16·자동화15·직원 권한18·멘션19 회귀도 확인했다. Chrome에서 두 사업 팀 설정/수동·자동 배정/팀과 내 팀 필터, 두 가상 문의의 서로 다른 담당자, 설정 충돌/초안 보존/최신 복구, 보관/복원과 열람 직원의 변경 제한을 확인했다. 보관된 팀의 기존 담당자도 이름을 유지해 표시한다.

코드·마이그레이션·로그·화면 해시는 `evidence-manifest.json`의 `routingQa`에 기록한다. 모두 가상 고객/직원·loopback/PGlite이며 실제 팀 구성·운영 DB·실제 고객/외부 알림은 변경하지 않았다. 조건별 팀 분류의 SQL/API12·모의 실행·사람 게시·실제 배정/보존 Chrome QA를 추가했다. 접속·응대 상태/작성 표시와 선택 접속 필터는 [PRESENCE.md](PRESENCE.md)의 SQL/API14·두 가상 직원 Chrome 검수로 추가했다. 수용량/큐의 PGlite12·격리 PostgreSQL15와 Chrome 검수는 [CAPACITY.md](CAPACITY.md)에 추가했다. 사업 업무시간 배정은0109의 PGlite14·격리 PostgreSQL14·Chrome 검수로 추가했다([BUSINESS-HOURS-ROUTING.md](BUSINESS-HOURS-ROUTING.md)). 직원별 교대표/기본 팀 설정·팀별 성과와 실제 업무/부하/전체 전환은 남아 있다. 전체 목표는 [REPLACEMENT.md](REPLACEMENT.md)를 따른다.

고객 공개 답변의 서버 작성 잠금·인계·새 대화 재검토·초안 보존은0110의 [REPLY-GUARD.md](REPLY-GUARD.md)에 추가했다. 내부 메모는 함께 작성할 수 있다.
