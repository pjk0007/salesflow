# 구글 챗 알림 QA — 찾은 것과 고친 것 (2026-10-11)

> 대표 요청: "구글챗으로 이슈사항 쏘는거 qa좀 해볼래?"
> 범위: 샌드비가 구글 챗 수신 웹훅으로 보내는 모든 알림 — 공통 보내기(`src/lib/google-chat.ts`), 깊이 들어온 사람 카드, 회신 카드, 회신 읽기 운영 알림, 발송 건강(회차 묶음·매일 보고·풀림·NHN 결과 확인), 그리고 새로 만든 웹훅 문제 알림.
> 상태: dev 작업 트리, **커밋 전**. 실제 구글 챗·Gmail·NHN으로는 아무것도 보내지 않았다 (가짜 구글 챗 `.testenv/mock-fetch.mjs`와 하네스 안 가짜 층, 시험 DB `127.0.0.1:54329/salesflow_test`).

## 1. 한눈에

- 하네스 9묶음이 찾은 항목 중 확인된 것(CONFIRMED)을 모두 앱 코드에서 고쳤다. 반박된 것(CT-10, DV-11·13·14·16·17, RC-13, RO-11, HB-6, HS-13, HD-06·08·12, HR-11)은 손대지 않았다.
- 세 가지는 **플래그로 꺼 둔 채** 넣었다. 구글 공식 문서에 수신 웹훅이 받는다고 적혀 있지 않아, 개발 스페이스에서 한 번 확인한 뒤 켠다 (4절).
  - `GOOGLE_CHAT_REQUEST_ID=on` — 줄마다 고정 `requestId`. 응답이 10초를 넘겨 다시 보내도 같은 글이 두 번 올라가지 않는다
  - `GOOGLE_CHAT_THREADS=on` — 같은 레코드·같은 고객·같은 운영 문제를 한 스레드로
  - `DEEP_ALERT_TEST_SERVER_LIVE=1` — 시험 서버에서 깊이 카드를 일부러 보낼 때만 (운영·개발 서버에는 넣지 않는다)
- 플래그가 꺼져 있어도: 시간 초과는 그 회차에 다시 보내지 않고 두 번째 시간 초과에서 멈춘다. 같은 카드가 최대 2통이다 (예전에는 최대 6통).
- 고친 뒤 모든 글을 구글 챗 모양으로 펼친 갤러리(`F:/Dev/sendb-testenv/chat-qa/gallery.html`)에서 하네스가 못 잡은 7가지(N1~N7)를 더 찾아 고쳤다 (3절 끝 "갤러리 점검 뒤 고친 것").
- 대표가 정할 것 3가지 (6절).

## 2. 공통으로 바뀐 것

| 무엇 | 예전 | 지금 |
|---|---|---|
| 같은 스페이스 동시 보내기 | 깊이·회신·건강·풀림이 각자 1.1초 간격 → 합치면 초당 1통 넘어 429 | 프로세스 전체가 스페이스마다 1.1초 줄을 함께 쓴다 (`SPACE_INTERVAL_MS`). 서버 인스턴스가 여러 개면 인스턴스 사이는 아래 429 백오프로 버틴다 |
| 429 | 1.5초 뒤 한 번 | 2초·4초(+무작위) 뒤 두 번 더. `Retry-After`가 있으면 따름(최대 10초) |
| 5xx·연결 오류 | 1.5초 뒤 한 번 | 1.5초(+무작위) 뒤 한 번 |
| 응답 시간 초과(10초) | 1.5초 뒤 다시 보냄 → 중복 | 다시 보내지 않음(`uncertain`). 워커는 다음 회차에 — requestId 켜면 같은 값으로, 꺼져 있으면 두 번째에서 `failed` "두 번 모두 응답이 없어 그만 보냄 (스페이스에 올라갔는지 확인해 주세요)" |
| 느린·막힌 스페이스 | 한 줄에 최악 21.5초, 뒤 사업 카드가 5분 늦음 | 다시 보내도 실패한 워크스페이스는 그 회차에 건너뛰고 다른 사업을 먼저 보냄 |
| 웹훅 주소 확인 | `https`로 시작하면 아무 호스트로나 | `https://chat.googleapis.com/v1/spaces/…/messages`만. 오타 도메인으로 고객 정보가 나가지 않음 |
| 마지막 방어 | 없음 | 보내기 직전 `<users/`를 `‹users/`로 (전체 멘션 막음) |
| 오류 글 | 영어 원문·HTML | 할 일을 한국어로 먼저, 원문은 괄호: "웹훅을 고칠 때까지 기다림 — Workspace 관리자가 웹훅을 막았거나 … (구글 챗 403: The caller does not have permission)". HTML은 `<title>`만 |
| 비밀값 가림 | `key=`·`token=` 원문만 | URL 인코딩된 것(`key%3D`)·주소 전체도 가림 (`[웹훅 주소]`, `***`) |
| 사용자 값 | `< >`만 바꿈 (깊이·회신), 발송 건강은 그대로 | 모든 패밀리 공통 `chatSafe`: `< >`→`‹ ›`, `* _ ~ \``→전각(메일 주소의 `_`는 그대로), 줄바꿈→공백, 맨 URL은 `hxxps://`·`www[.]`(회신·발송 건강·깊이 카드 모두, 깊이 카드는 N1에서 더함), 코드 포인트로 자름 (`src/lib/chat-text.ts`) |
| 웹훅 고장·없음 | 줄에 `last_error`와 로그만, 24시간 뒤 조용히 닫힘 | 받는 곳(환경 변수 이름)마다 `chat_webhook_status`에 상태. 운영 스페이스에 6시간에 한 번 알림(아래), 매일 보고 한 줄, 발송 건강 카드 "알림 전달 (구글 챗)" 칸, 회신 탭 "알림 못 보냄" 표시 |
| 웹훅 없음 | 깊이·회신 카드가 바로 `skipped` (넣어도 영영 안 나감) | `pending` "웹훅 주소가 없어 넣을 때까지 기다림" — 24시간 안에 넣으면 나감 |
| 24시간 지나 닫을 때 | 원인을 덮어씀 | "오래되어 보내지 않음 (…) — 직전: {원인}" |

**웹훅 문제 알림** (`src/lib/chat-webhook-status.ts`, 새로)

```
⚠️ 샌드비 알림이 구글 챗 스페이스로 가지 못하고 있습니다
• 사업 스페이스 「오피오」: 스페이스에서 웹훅이 지워졌거나 주소가 틀렸습니다 (404) · 10/11 13:35부터
  기다리는 알림 3건 (깊이 2 · 회신 1) — 고치지 않으면 가장 오래된 알림은 약 20시간 뒤 버려집니다
  할 일: 그 스페이스 관리자에게 새 웹훅 주소를 받아 환경 변수 DEEP_ALERT_WEBHOOK_URL_14 값을 바꾸고 배포해 주세요 (개발 담당에게 요청)
알림 전달 상태: https://sendb.kr/email#send-health
```

- 시험(개발) 서버가 보내면 첫 줄이 `⚠️ [개발 서버 · 호스트] 샌드비 알림이 …` (회신 운영 알림과 같은 판정·같은 표시, N6). 운영 주소(`NEXT_PUBLIC_BASE_URL=https://sendb.kr`)면 표시 없음
- 받는 곳: `SEND_HEALTH_WEBHOOK_URL` → `REPLY_OPS_WEBHOOK_URL` → `DEEP_ALERT_WEBHOOK_URL` 중 지금 고장 나지 않은 첫 곳
- 고장 표시는 주소의 지문(sha256 앞 16자)과 함께 남긴다. 새 주소로 바꿔 배포하면 예전 고장 표시를 믿지 않고 바로 다시 보낸다 (주소 자체는 저장하지 않음)
- 401·403·404·형식 오류·웹훅 없음은 바로, 연결 실패는 1시간 넘게 이어질 때. 같은 받는 곳은 6시간에 한 번, 고쳐지면 "✅ … 다시 보냅니다" 한 번
- 주소·key·token은 저장도 하지 않는다 (환경 변수 이름만)
- 관리자 "연결 확인 보내기" (`POST /api/email/send-health/webhook-check`, 조직마다 10분에 한 번): 받는 곳마다 확인 글 한 통, 결과를 한국어로

### 다시 돌리며 더 고친 것 (하네스 재실행 중 발견)

- 운영 웹훅을 고쳐 배포해도(같은 환경 변수, 새 주소) 예전 주소의 401·403·404 표시 때문에 회신 운영 알림이 1시간 동안 막혔다 → 주소 지문으로 구별
- 401·403·404였던 받는 곳을 고친 뒤 첫 성공이 상태 표에 남지 않아 "고쳐짐" 알림이 늦었다 (회차 시작의 "없음·형식 오류 지우기"가 성공 기록의 10분 줄이기와 같은 기억을 써서) → 따로 둠
- 회신 운영 알림 글을 구글이 400으로 받지 않으면 5분마다 같은 글을 다시 보냈다 → 같은 주소는 1시간 뒤에 다시
- 자동 멈춘 주소를 풀 때, 멈춘 때와 거의 같은 시각의 발송이 사업 스페이스 판단에서 빠졌다 → 멈춘 때 뒤 1시간까지 본다
- 발송 건강 15분 회수가 requestId 없이 보낸 줄을 상한(3번)까지 다시 보냈다 → 시간 초과와 같게 두 번째에서 그침
- 발송 건강도 `GOOGLE_CHAT_THREADS=on`이면 매일 보고는 조직·받는 곳마다, NHN 결과 확인 알림은 조직마다 한 스레드 (HD-14·HB-8)
- 여러 조직의 같은 NHN 원인을 한 통으로 합치기(HS-11)가 같은 회차에 함께 집은 줄은 합치지 못했다 → 함께 집은 줄도 합침
- NHN 결과 확인 회복 글의 열쇠에 원인을 넣었다 — 같은 때 알린 다른 원인(정체 → 키 오류)의 회복 글이 앞 회복과 겹쳐 빠지지 않게

## 4. 켜기 전 개발 스페이스 확인 (재훈 님, 약 10분)

웹훅 주소는 문서·채팅에 적지 않는다. 개발용 구글 챗 스페이스 하나에서 "앱 및 통합 → 웹훅"으로 시험 웹훅을 만들어 터미널 변수에만 넣는다.

```bash
read -s HOOK   # 시험 스페이스 웹훅 주소를 붙여 넣기 (화면에 안 보임)
RID=8a2c3f1e-1111-4111-8111-000000000001
# ① requestId: 같은 명령을 두 번 → 스페이스에 글이 1통이면 GOOGLE_CHAT_REQUEST_ID=on
curl -s -X POST "$HOOK&requestId=$RID" -H 'Content-Type: application/json; charset=UTF-8' -d '{"text":"requestId 확인"}'
curl -s -X POST "$HOOK&requestId=$RID" -H 'Content-Type: application/json; charset=UTF-8' -d '{"text":"requestId 확인"}'
# ② 스레드: 두 번째 글이 첫 글의 답글로 달리면 GOOGLE_CHAT_THREADS=on
curl -s -X POST "$HOOK&messageReplyOption=REPLY_MESSAGE_FALLBACK_TO_NEW_THREAD" -H 'Content-Type: application/json; charset=UTF-8' -d '{"text":"스레드 확인 1","thread":{"threadKey":"sendb-qa-thread-1"}}'
```

## 6. 대표가 정할 것

1. **밤에 사업 스페이스로 가는 알림** (HB-13 ②·DV-5): 지금은 발송 건강 조치(보류·멈춤)가 밤에도 사업 스페이스에 바로 가고, 밤에 웹훅을 고치면 기다리던 깊이 카드도 그 회차에 나간다(기한 줄은 "출근하면 먼저 · …"로 다시 씀). 사업 스페이스만 08시로 미루고 운영 스페이스에는 바로 보낼지
2. **월요일 아침 몰림** (DV-8): 주말 동안 쌓인 깊이 카드가 월 09:00에 한 스페이스로 여러 통 나간다. 한 워크스페이스에 N건(예: 10건) 넘으면 요약 한 통 + 레코드 목록 링크로 묶을지
3. **운영 매일 보고 시각이 밤일 때** (HD-09): `SEND_HEALTH_REPORT_HOUR`를 22~08시로 두면 운영 보고는 그 시각에 바로 가고 사업 보고만 08시로 미룬다. 운영 보고도 미룰지 (기본값 9시면 해당 없음)
