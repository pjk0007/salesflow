# 상담·고객여정 알림의 유입경로

고객상담 메시지 카드, 도입신청 레코드 알림, 고객여정 카드·미리보기에 같은 형식의 유입 설명을 추가했다. 기존 알림 대상·주기·60초 기준·담당자 태그·중복 방지 규칙은 유지한다.

| 예시 | 근거 |
| --- | --- |
| 홈페이지 · 구글 검색 [확인] | 검색 referrer가 있는 방문 세션이 상담에 직접 연결됨 |
| 메일 · domain2.test [확인] | 유효한 메일 클릭 ID와 상담 방문이 직접 연결됨. 고객여정 카드는 해당 레코드의 클릭과 해당 세션 연결을 사용 |
| 메일 · domain2.test [추정] | 최근 클릭·방문 또는 발송·방문·이메일 단서는 있으나 이번 접수와 직접 연결되지 않음 |
| 유입 미확인 | 단서 부족, 연결 충돌, 후보 과다, 조회 오류 |

`domain2.test`는 가상 예시다. 운영에서는 발송 당시 `email_send_logs.sender_email`의 실제 도메인을 쓴다. 현재 발신 프로필로 과거 발송 주소를 추정하지 않으며, 주소가 없으면 `발신 도메인 미확인`으로 표시한다.

## 확인과 추정의 경계

- 직접 상담 연결은 기존 서버가 검증해 저장한 `journey_context`의 조직·사업·사이트·방문자·세션을 다시 확인한다. 이는 브라우저 경로의 연결 근거이며 수신자 본인 인증이나 마케팅 인과관계를 뜻하지 않는다.
- 메일 클릭은 같은 조직·사업의 발송 레코드, `sent` 상태, 봇 아님, 발송→클릭 순서와 방문 시각을 확인한다. 방문 시작 전 30분부터 시작 후 30초 안의 클릭만 직접 방문 근거로 쓴다.
- 상담의 명시된 레코드와 클릭 대상이 다르면 `미확인`으로 남긴다. 다른 조직·사업의 기록은 읽지 않는다.
- UTM이나 URL의 `sendb_cid` 문자열만으로 확정하지 않는다. 검색은 URL hostname 경계를 확인하고, referrer가 없다는 이유로 직접 유입을 단정하지 않는다.
- 간접 추정은 알림 시점 이전 최근 7일의 연결 방문 중 가장 최근 방문을 사용한다. 발송 이력만 있고 방문 단서가 없으면 메일로 추정하지 않는다. 여러 발신 도메인이 후보면 미확인으로 남긴다.
- 기존 폼/API가 상담 세션을 전달하지 않은 접수는 나중에 이메일이 같아도 `[확인]`으로 승격하지 않는다. 과거 누락 연결을 만들어내거나 고객을 자동 병합하지 않는다.
- 고객여정 피드는 현재처럼 메일 클릭에 직접 연결된 방문만 후보로 사용한다. 이 변경은 검색·익명 방문을 새 알림 대상으로 추가하지 않는다.

## 구현과 실패 처리

- 공통 판정/문구: `src/lib/alert-acquisition/rules.ts`
- 상담·레코드의 읽기 전용 조회: `src/lib/alert-acquisition/repository.ts`
- 부가 조회는 별도 짧은 트랜잭션에서 쿼리당 1.5초 제한을 적용한다. 실패 시 부가 조회만 롤백하고 유입 미확인으로 원래 알림을 계속 만든다. HTTP 전송 전에 트랜잭션을 끝낸다.
- 고객여정 조회는 기존 후보 SQL에서 당시 발신 주소와 봇 여부 두 필드만 추가한다. 카드 재시도에도 기존 저장 ID·대상·멘션 규칙을 유지한다.
- 추가 스키마·마이그레이션·환경 변수·웹훅·외부 패키지는 없다. 운영 DB 접속, 실제 고객/스페이스 시험 발송, 운영 설정 변경, main 병합·배포는 하지 않았다.

## 검증

- 단위 43개 통과: 새 판정·조회 결과→고객여정 카드 전달, 기존 고객상담 카드, 레코드 알림·재시도, 고객여정 카드 회귀.
- 새 격리 PGlite SQL 11개: 사업/조직 격리, 봇·미래 기록 제외, 직접/간접 연결, 레코드 충돌, 검색·메일 추정, 단서 부족, 부가 조회 실패 롤백.
- 기존 고객상담 대기열 SQL 13개, 고객여정 우선순위/라우팅/재시도 SQL 22개 통과. 외부 전송 0건.
- TypeScript 전체 및 변경 파일 ESLint 확인.
- 기존 상담 대기열 검사의 오래된 `message=` 기대값은 실제 고객 상담 링크 계약인 `conversation=`과 내부 메모 전용 `message` 부재 검사로 바로잡았다.
