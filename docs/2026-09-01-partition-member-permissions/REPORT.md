## 한 일 (요약)

조직 `member` 역할 사용자에게 **파티션 단위 권한**을 부여할 수 있는 체계를 만들었다. 발단은 member 계정에서 예약 등록 "설정" 저장이 403 나던 사소한 버그였지만, 조사 과정에서 파티션 데이터 접근(records CRUD·export·delete-all)에 role 체크가 **아예 없어** member가 조직 내 모든 파티션의 레코드를 읽고·쓰고·전체 삭제할 수 있다는 사실이 드러나 범위가 권한 체계 전체로 확장됐다.

`member_scopes` 테이블과 DB를 모르는 순수 판정 코어를 만들고, route 13곳에 가드를 삽입했으며, 관리 API·트리 UI를 붙였다. 2차로 사용자 요청에 따라 파티션/폴더 생성·수정·삭제 권한(B16~B22)까지 넓혔다. 최종 behavior 22/22 통과, 테스트 102개 GREEN.

## 발단 — 버그 하나가 구멍 하나를 드러냈다

| 단계 | 내용 |
|---|---|
| 최초 증상 | member 계정에서 예약 등록 "설정" 저장이 403 |
| 직접 원인 | `PATCH /api/partitions/[id]`의 `role === "member"` 하드 차단 |
| 조사 중 발견 | 정작 **데이터 접근 route에는 role 체크가 0건**. member가 조직 내 모든 파티션 레코드를 읽고·쓰고·삭제 가능 |
| 결정 | 예약 등록 건만 떼지 않고 권한 체계를 통째로 구축. 급한 403은 해당 사용자에게 admin 임시 부여(사용자 결정) |

즉 **막아야 할 것을 열어두고, 열어야 할 것을 막고 있던** 상태였다.

## 핵심 설계 결정 3가지

**(a) allow 기본** — 권한 행이 없는 파티션은 기존과 동일하게 모든 member가 접근한다. 특정 파티션에 권한을 건 순간 그 파티션만 제한 모드로 전환된다. 기존 사용자 영향 0, 데이터 마이그레이션 불필요. 대가는 판정 비용 — "제한이 걸렸나"를 알려면 **타인의 scope까지** 봐야 해서 scope 목록에 사용자 필터를 걸 수 없다.

**(b) 순수 함수 분리로 TDD** — 판정 로직을 DB 모르는 순수 함수로 설계해, B1~B8·B11·B16~B22를 구현 전에 `node:test`로 고정했다. 새 의존성 없이 기존 `pnpm test`를 그대로 썼다. DESIGN은 단일 파일을 상정했으나 테스트가 `@/lib/db`를 끌고 오면 node:test에서 못 돌아 `partition-access-rules.ts`로 쪼갰다.

**(c) 구조 생성은 allow 기본에서 제외** — 대상이 아직 없어 "덮는 scope가 없으면 통과" 규칙을 쓸 수 없고, 적용하면 권한 미부여 member 전원이 파티션을 만들 수 있게 된다.

부수 결정: **org scope는 스키마·판정은 지원하되 UI에서 노출하지 않는다**(사용자 결정). 한 명에게 org scope를 주면 조직 전체가 제한 모드로 바뀌어 나머지 member 전원이 즉시 차단되는 사고를 구조적으로 막는다.

## 2차 범위 확장

1차 완료 후 사용자 지적으로 파티션/폴더 생성 권한(B16~B20)을 추가했다. `partitions/[id]`·`folders/[id]`의 member 하드 차단을 제거하고 권한 판정으로 대체 — **기존 "구조 변경은 관리자 전용" 정책의 의도적 변경**이다.

### 🔴 1. 구조 변경에 allow 기본이 번졌다

member 차단 3곳을 제거하면서 **생성만** allow 기본에서 빼고 **수정·삭제는 빼지 않았다.**

> 권한 행이 0건인 상태 — 즉 **모든 조직의 기본 상태** — 에서 임의의 member가 임의의 파티션을 삭제할 수 있었다.

실측(수정 전):
```
DELETE /api/partitions/48  (권한 0건, member 토큰)
→ {"success":true}  http=200
→ DB 행 수: 0        ← 실제로 삭제됨
```

파티션 삭제는 하위 레코드까지 CASCADE로 날아가는 비가역 작업이다. 판정 축이 1회차 우회 경로와 정반대로 뒤집혔다 — 1회차는 "권한을 걸어야 노출"(미래 리스크)인데 이건 "권한을 안 걸어야 노출"(현재 리스크). **기본 상태가 곧 취약 상태**였다.

수정: `canAccessPartition`에 `denyByDefault` 추가, 구조 변경 4경로에 적용. B21로 고정. 수정 후 403 + 행 보존 확인.

### 🔴 2. `folderId` 무검증 → 자기 권한 상승

`PATCH /api/partitions/[id]`가 `folderId`를 검증 없이 UPDATE했다. member가 자기 파티션을 **자신이 folder scope를 가진 폴더**로 옮기면 `scopeCoversPartition`의 folder 분기가 매칭되면서 그 파티션에 대한 권한을 스스로 만들어낸다.

이 코드는 이전부터 있었으나 member 차단 뒤에 있어 admin만 도달 가능했다. **이번에 차단을 걷어내며 노출면이 새로 생겼다.** 같은 사이클의 *생성* 경로는 이 검증을 하는데 수정 경로만 빠져 있었다.

수정: 같은 워크스페이스 소속 검증 후 400. B22로 고정.

## 배운 것

**1. 권한 차단을 걷어낼 때는 그 자리에 무엇이 들어오는지 끝까지 따라가야 한다.**

이번 사이클 최대의 교훈. `role === "member"` 하드 차단 제거는 "판정을 세밀하게 바꾼다"는 좋은 의도였는데 **차단이 있던 자리를 전부 채우지 못했다.** 생성은 allow 기본에서 뺐으면서 수정·삭제는 빼지 않아 기본 상태가 곧 취약 상태가 됐다. 차단 뒤에 숨어 있던 `folderId` 무검증 코드도 같은 원리로 노출됐다 — 원래부터 허술했지만 admin만 도달 가능해서 문제가 안 됐던 것이다.

→ **가드를 제거하는 diff는 "제거한 가드가 막고 있던 것의 목록"을 먼저 적고 1:1로 대조한다.** 특히 그 가드 뒤 코드의 입력 검증을 재점검한다.

**2. "권한 미설정"이 안전한 기본값인지는 동작마다 다르다.**

데이터 읽기에서 allow 기본은 합리적이다(기존 동작 유지). 비가역 삭제에서는 정반대다. 같은 판정 함수를 쓰더라도 **기본값의 방향은 동작의 파괴성에 따라 갈라져야 한다.**

**3. 100%는 분모의 함수다.**

22/22 통과했지만 우회 경로 5건이 남았다. 원인은 구현이 아니라 DESIGN의 route 조사 범위였다. 접근 제어 사이클은 **"이 자원에 도달하는 모든 경로 전수 조사"를 DESIGN의 명시적 산출물로** 요구해야 한다 — 조사 대상을 `/api/{resource}/*` 디렉토리로 한정하면 형제 경로와 일괄 처리 API를 반드시 놓친다.

**4. 순수 함수 분리가 TDD를 가능하게 했다.**

새 의존성·새 러너 없이 계약을 먼저 고정할 수 있었다. 결함 2건을 고칠 때도 B21·B22를 먼저 박고 수정했다. 반대로 **DB 어댑터와 route 가드는 테스트가 없어** 수동 실증에 의존했고, 결함이 거기서 나왔다.

**5. lcov 행 번호를 evidence 근거로 쓰지 말 것.**

tsx + node:test 조합에서 lcov의 `SF:` 블록은 트랜스파일 결과 기준이라 소스 행과 어긋난다. 1회차에 위양성 4건이 났다. 함수 커버리지(`FNDA`)는 신뢰할 수 있다.
