# 고객상담 렉 재현과 개선

요청 범위: 목록 전환·입력·전송을 재현하고 수정한 뒤 `dev`에 커밋·푸시. 운영 배포는 이번 작업에 포함하지 않는다.

## 원인과 수정

1. **입력할 때 메시지 이력 전체의 날짜·시간을 다시 계산**했다. 실제 `InboxPage`·`ConversationPane`와 운영의 React compiler 설정을 사용한 Chrome 검수에서, 100개 메시지를 연 상담에 글자 하나를 입력할 때 locale 변환이 101회 실행됐다. 메시지 이력을 메모이제이션한 컴포넌트로 분리하고 `Intl.DateTimeFormat` 인스턴스를 재사용했다. 상담 목록의 날짜 변환도 같은 방식으로 바꿨다.
2. **목록과 건수 집계가 하나의 응답에 묶여** 집계가 늦으면 목록까지 기다렸다. `view=rows`와 `view=counts`를 나눠 목록은 기존 4초, 집계는 15초마다 갱신한다. 페이지를 더 읽을 때 집계를 반복하지 않는다. 기존 `view=list` 응답은 호환성을 유지한다. 필터·조직·채널 권한은 두 경로 모두 동일하게 검사한다.
3. **검색 글자마다 전체 상담·메시지 검색을 요청**했다. 300ms 입력 대기를 적용했다. 화면에는 입력 중임을 표시하고 이전 검색 결과가 새 검색 결과인 것처럼 표시되지 않도록 갱신 상태를 구분한다. 페이지 합치기는 중첩 검색 대신 Set을 쓴다.
4. **전송 성공 뒤 다시 조회할 때까지 메시지가 보이지 않았다.** POST가 반환한 확정 메시지를 해당 상담 캐시에 즉시 반영하고 갱신은 뒤에서 진행한다. 전송 중 다른 상담으로 옮겨도 원래 상담에만 반영한다. 재조회 실패를 전송 실패로 표시하지 않는다. 일시적인 상세 조회 오류에도 같은 상담의 기존 내용·입력창을 유지하고 오류/재시도 안내를 표시한다.
5. **끝나지 않는 요청이 입력·전송 대기를 무한히 유지**할 수 있었다. 응답 헤더와 본문을 포함해 일반 요청은 15초, 큰 첨부 업로드는 120초 제한을 추가했다. 전송 결과가 불확실하면 초안과 기존 clientId를 보존하며 자동 재전송하지 않는다. 세션 종료 시 기존 취소 처리도 유지한다.

DB 마이그레이션, 라이브러리 추가, 실제 고객 발송, 운영 환경 변경은 없다.

## 재현 결과

가상 상담 220개, 선택한 상담의 메시지 100개. 실제 React 컴포넌트/훅에 가상 HTTP API를 연결했다. Next navigation만 로컬 검수용으로 대체했고 React compiler를 켰다. 실제 운영 서버 지연/SLA 수치는 아니다.

| 항목 | 수정 전 | 수정 후 | 측정 조건 |
| --- | ---: | ---: | --- |
| 글자 입력 → React commit 중앙값 | 25.8ms | 3.9ms | 같은 27글자 입력, 개발 React Profiler |
| 입력 commit p95 | 27.7ms | 6.2ms | 날짜 locale 변환 101회 → 0회 |
| 상태 목록 전환 | 3,121ms | 340ms | 집계에만 3초 지연 주입 |
| 전송 클릭 → 메시지 표시 | 2,777ms | 320ms | POST 80ms, 전송 후 상세 재조회 2.5초 지연 |
| 연속 7글자 검색에 사용된 검색어 수 | 7개 | 1개 | ‘가상고객 21’ 연속 입력 |

입력의 최초 animation-frame 측정에는 브라우저 스케줄링 영향이 섞여 폐기했다. 위 입력 수치는 input 이벤트부터 React Profiler commit까지 측정한 값이다. 목록/전송 수치는 브라우저 제어 왕복 비용을 포함하는 단일 비교이며 인위적으로 주입한 지연을 분리했는지 검증하는 데 사용했다.

### 추가 검수

- A 상담 초안 → B 상담 초안 → A 복귀: 각 초안 유지.
- 내부 메모 저장 후 고객응대로 전환: 고객 답변 초안 유지, 메모는 한 번 표시.
- POST가 서버에 저장됐으나 응답이 유실된 상황: 15초 뒤 버튼 활성화·초안 유지. 같은 요청 재시도 후 서버 저장 1건·화면 1건 확인.
- 전송 후 상세 재조회에 503 오류 주입: 오류 안내가 나와도 확정 메시지와 입력창 유지, 다음 답변 작성 가능.
- 실제 상담 SQL 검수 22개 통과: 전송·중복 방지·읽음 순번·조직 권한·검색·같은 시각의 페이지 경계 포함.
- 추가 가상 상담 20,000개 SQL 검수: 첫/둘째 페이지 각 100개, 중복 0개, 전체 집계 10,000개, 기존 list API와 분리 조회 결과 동일. 다른 조직 집계 차단 및 검색 집계 확인. PGlite 기준 목록 21.5ms·집계 29.1ms였으며 운영 DB의 실행 계획/부하를 측정한 것은 아니다.
- 통신 deadline·세션 취소·불확실한 전송의 clientId 보존 및 기존 초안 회귀 테스트 17개 통과. 첨부는 일반 요청 제한 이후에도 유지되며 120초 제한에서 종료되는지 가짜 시간으로 확인했다.

- 상담 집중 검사: 17개 통과. SQL 검수 22개 + 20,000개 상담 분리 집계 검수 통과.
- 변경한 제품 코드와 새 테스트의 ESLint 통과.
- Node 24.19.0 / Next.js 16.1.6 `pnpm run build:cloudtype`: 컴파일·TypeScript·225개 정적 페이지·standalone·116개 기존 migration 복사 완료.
- 최종 소스와 격리 빌드 복사본의 제품/SDK/공개 파일/스크립트/마이그레이션/설정 **1,855개 파일 SHA-256 일치**.
- 최초 병렬 전체 검사에서는 기존 `channel-source-export/output.test.ts`의 40ms collector 테스트 1개가 자원 경합 중 실패했다. 해당 코드를 수정하거나 검사를 건너뛰지 않았고, 빌드와 분리한 전체 순차 검사에서 두 차례 통과했다. 마지막 실행에는 추가한 첨부 예산 검사도 포함된다.
- 운영 DB·개발의 실제 고객 DB 접근, 실제 외부 발송, 운영 배포: 0건. 로컬 검수 서버는 종료했다.

## 10월 22일 운영 배포 확인

CloudType `sendb` 배포 내역에서 적용 중인 커밋은 `5b2737a06c8bca5281e7013152a203eb672a65c1`로 확인했다. 제목은 ‘운영 DB 장애 수정을 원격 main에 병합’이며, 원격 main의 커밋 시각은 10월 22일 15:33 KST다. 앞선 #39는 세션 조회 지연 복구 수정이다.

사용자가 짚은 18~19시를 확인했지만, 콘솔은 상대 시각만 표시하고 서비스 이벤트 목록은 비어 있어 그 시간의 별도 배포/재시작을 확정하지 못했다. 커밋 시각을 배포 시각으로 간주하지 않았다. 운영 DB는 조회하지 않았다.

재현 기준은 `dev`의 `71a7451`이다. 운영 main과 dev에는 고객 메신저/화면 차이가 있지만, 이번에 지적한 입력 시 이력 렌더링·결합 집계·검색 요청·전송 후 재조회 대기 경로는 운영 소스에도 남아 있음을 비교 확인했다. 따라서 확인한 원인은 공통 코드의 재현 가능한 병목이며, 18~19시 운영 장애 전체가 이 원인 하나 때문이었다고 단정하지 않는다. 이전 공통 DB 개선과 이번 상담 화면 개선을 구분해야 한다.

## 재실행

Node 24, pnpm 10.15.0 기준. 별도 실제 DB 설정 없이 실행한다.

```powershell
node scripts/check-inbox-performance.cjs
node scripts/inbox-performance-ui.cjs
# http://127.0.0.1:3121/ 에서 목록·입력·전송 검수
# http://127.0.0.1:3121/?send=lost 에서 POST 응답 유실 검수
```

기준 버전 비교는 `INBOX_QA_BASELINE=71a7451`, 다른 포트는 `INBOX_QA_PORT`로 지정한다. ‘측정 저장’을 누르면 `/__qa/report`에 Profiler 결과와 가상 API 요청 내역이 남는다. 검수 UI는 격리 API만 사용하며 실제 메일·알림톡·Google Chat으로 발송하지 않는다. CSS는 현재 저장소의 `.next/static/css`를 사용한다. 별도 빌드 복사본은 `INBOX_QA_CSS_DIR`로 지정할 수 있으며, CSS가 없으면 스타일 없는 기능 검수가 가능하다.
