# DESIGN 3 — 사업별 답장 받을 주소 (Reply-To)

- **사이클 ID**: 2026-10-04-reply-to (DESIGN-2 뒤)
- **근거**: 대표 확인(2026-10-04). 발신 도메인 20개 중 메일을 받는 도메인은 `matchesplan.com`뿐이고(공개 DNS MX 조회), 샌드비는 Reply-To를 넣지 않는다(`src`에 Reply-To 0건). 그래서 고객이 cs@matchesplan.me 같은 발신 주소로 답장하면 되돌아가고 우리는 모른다. 결정: ① 답장은 **사업(워크스페이스)마다 따로** 받는다 ② 14곳 실제 발송 시험에 답장 시험을 넣는다
- **비용**: 0. 발신 도메인에 메일함을 만들지 않고, 답장만 이미 메일을 받는 주소로 보낸다

> **2026-10-04 바뀜 — Reply-To 방식은 철회했다.** 개발 서버 실제 발송에서 NHN이 `Reply-To` 사용자 지정 헤더를 금지 헤더로 거절해, 답장 주소가 있는 사업의 메일이 모두 실패했다. 1절(헤더 넣기)·3절(설정 칸·안내)과 5절의 R1·R3·R6은 지금 동작이 아니다. 지금 동작과 바뀐 결정은 **6절**을 본다. 2절의 칸·API와 4-1절은 그대로다.

## 1. 동작

> 철회(2026-10-04) — NHN이 `Reply-To`를 사용자 지정 헤더로 받지 않는다. 어떤 발송 경로도 Reply-To를 넣지 않는다 (6절)

- 워크스페이스에 **답장 받을 주소** 하나 (비우면 지금처럼 Reply-To 없음)
- 그 워크스페이스로 나가는 **모든 메일**(AI 첫 메일, AI·템플릿 후속, 템플릿 자동·반복, 수동 발송, 테스트 발송)에 `Reply-To: <답장 받을 주소>` 헤더를 넣는다
  - 워크스페이스는 메일을 받는 레코드의 `records.workspace_id`(파티션의 워크스페이스)로 정한다
  - NHN 발송 요청의 `customHeaders`에 넣는다 (지금 `List-Unsubscribe`를 넣는 자리와 같은 방식). NHN 문서에 사용자 지정 헤더 칸은 있지만 Reply-To 허용이 명시돼 있지 않다 → 실제 발송 시험으로 확인한다 (4절)
- 보내는 주소(From)는 그대로 발신 묶음의 주소다

## 2. 데이터

> 2026-10-04 뒤: 칸(`workspaces.reply_to_email`)과 설정 API의 읽기·저장·검사·MX 조회·권한은 남겨 두었지만 **발송에 쓰지 않는다**. 지우는 마이그레이션은 없다 (6-3절)

- 마이그레이션 0073: `workspaces.reply_to_email varchar(200)` (NULL 허용, 기본 NULL)
- 저장 검사: 이메일 형식, 200자 이하. 저장할 때 그 도메인의 MX를 조회해 **없으면 경고**(저장은 막지 않는다 — DNS 일시 오류일 수 있다). 결과는 응답에 `mx: "ok" | "none" | "unknown"`으로 돌려준다
- 권한: 관리자(owner·admin)만 바꾼다. 조직 범위. 토큰에 적힌 역할이 아니라 **DB의 현재 역할과 token_version**으로 확인한다(`requireAdmin`) — 강등되거나 조직에서 빠진 관리자의 옛 토큰은 401 (REVIEW-3 F1)

## 3. 화면

> 철회(2026-10-04) — 설정 칸·템플릿 테스트 발송의 사업 고르기는 뺐고, 규칙 화면 안내는 MX 기준으로 바꿨다 (6-3절)

- 워크스페이스 설정 탭: "답장 받을 주소" 칸과 설명 — "이 사업으로 나가는 모든 메일의 답장이 이 주소로 옵니다. 메일을 받을 수 있는 주소여야 합니다(예: 회사 메일)." MX가 없으면 노란 경고
- AI 규칙 수정 화면 요약 칸: "답장: x@… " (워크스페이스 값, 없으면 "없음 — 답장이 발신 주소로 갑니다")
- 발신 묶음 칸: 묶인 주소의 도메인에 MX가 없고 워크스페이스 답장 주소도 비어 있으면 "이 주소들은 답장을 받을 수 없습니다. 워크스페이스에 답장 받을 주소를 정하세요" 안내 (MX 조회는 서버에서 하고 도메인별로 하루 캐시)

## 4. 검증

- 로컬: 가짜 NHN 기록(`mock-log.jsonl`)에 `customHeaders`를 남기도록 하네스를 고치고, 경로 다섯 곳 모두 `Reply-To`가 워크스페이스 값으로 들어가는지 본다. 워크스페이스 값이 없으면 헤더가 없어야 한다
- 실제(개발 서버, 14곳 시험): 시험 파티션의 워크스페이스 답장 주소를 `ceo@matchesplan.com`으로 둔다. 받는 분 한 명이 시험 메일에 답장하면 그 답장이 ceo@matchesplan.com에 도착해야 한다. NHN이 헤더를 거절하거나 지우면 여기서 드러난다 — 그때는 DESIGN 3-B(워크스페이스 계정 1개 + 도메인 별칭)로 간다
  - **결과(2026-10-04)**: NHN이 거절했다 → 6-1절
- 운영 반영 뒤 사업별 주소는 대표·담당이 워크스페이스 설정에서 넣는다

## 4-1. 같이 고치는 DESIGN-2 남은 두 가지

- **발송 이력 "보낸 주소"를 보낼 때 값으로** (fork 3 리뷰 policy-F5): 지금은 `email_send_logs.sender_profile_id`로 프로필의 **현재** 주소를 보여 줘서, 프로필 주소를 바꾸면 과거 이력이 바뀌어 보인다. 0073에 `email_send_logs.sender_email varchar(200)`(NULL 허용)을 더하고, 로그를 넣는 모든 경로에서 실제 `senderAddress`를 저장한다. 화면은 `sender_email`을 먼저 쓰고, 없으면(옛 로그) 프로필 현재값을 "(현재 프로필)" 표시와 함께 쓴다
  - 큰 표에 NULL 허용 칸 추가는 다시 쓰기 없이 바로 끝난다 (Postgres 11+)
- **템플릿 첫 메일 대기열의 문의 우선**: `email_automation_queue`에서 `kind='first'`(문의)를 `kind='first_bulk'`(가져오기)보다 먼저 꺼낸다. 같은 종류 안에서는 지금처럼 id 순

## 6. 실제 발송 결과(2026-10-04)와 바뀐 결정

### 6-1. 무슨 일이 있었나

- 9290217을 개발 서버(sendb-dev)에 올리고 4절의 실제 발송 시험을 했다. 시험 파티션의 워크스페이스에 답장 받을 주소를 넣자 NHN이 그 워크스페이스의 메일을 **모두** 거절했다. NHN 응답: `The 'customHeaders' contains an invalid name or body.` (사용자 지정 헤더에 잘못된 이름이나 값이 있다)
- 답장 받을 주소를 비우자(= Reply-To 헤더 없음) 같은 시험에서 12통이 모두 성공했다. 발신 묶음 주소 3개에 4·4·4통씩 돌아갔고 2통은 미뤄졌다. 실패 원인은 Reply-To 헤더 하나다
- 곧 9290217에서는 답장 받을 주소 칸에 값이 들어가면 그 사업의 모든 메일(AI 첫 메일·후속, 템플릿 자동·반복, 수동, 테스트 발송)이 나가지 않았다. 운영 서버(main)에는 들어가지 않았다

### 6-2. 근거 — NHN이 받는 사용자 지정 헤더

출처: NHN Cloud 콘솔 Email 서비스 가이드의 "사용자 지정 헤더" 안내 (2026-10-04 확인)

- 이름: 영문·숫자·하이픈(`[A-Za-z0-9-]`) 1~50자
- 값: 1~1000바이트
- 쓸 수 없는 이름 18개: `From`, `To`, `Cc`, `Bcc`, `Date`, `Subject`, `Content-Disposition`, `Message-ID`, `Sender`, `Reply-To`, `Newsgroups`, `Content-ID`, `Content-MD5`, `MIME-Version`, `Content-Transfer-Encoding`, `Content-Description`, `In-Reply-To`, `References`
- `List-Unsubscribe`는 쓸 수 있다 (`List-Unsubscribe-Post`도 금지 목록에 없다). 수신거부 헤더는 그대로 쓴다
- 발송 요청(`sender/eachMail`) 본문에도 답장 주소 칸이 없다 → **NHN으로 보내는 한 답장 주소(Reply-To)를 따로 정할 길이 없다**
- 1절에 적었던 "Reply-To 허용이 명시돼 있지 않다 → 실제 발송 시험으로 확인한다"의 답이 "금지"로 나온 것이다

### 6-3. 바뀐 결정

- **고객 답장은 메일을 보낸 주소(From)로 간다.** 답장 주소를 따로 정하는 기능은 두지 않는다
- **답장을 받으려면 발신 도메인 자체가 메일을 받게 한다 (DESIGN 3-B).** 발신 도메인 DNS에 메일 수신(MX)을 연결하고, 메일을 받는 워크스페이스 계정 하나에 그 도메인을 도메인 별칭으로 붙여 답장을 모은다. DNS와 Google Workspace 관리자 권한이 필요하고, 어느 도메인부터·어느 메일함으로 받을지는 대표가 정할 일이다 (REVIEW-4 "남은 것")
- 코드에서 바뀐 것 (자세한 것은 REVIEW-4)
  - **발송**: 모든 경로에서 Reply-To를 뺐다. 발송 요청의 사용자 지정 헤더는 수신거부 두 줄(`List-Unsubscribe`·`List-Unsubscribe-Post`)뿐이고, 모양은 9290217 전(ed2eee8)과 같다
  - **안전장치**: NHN에 보내기 직전 한 곳(`NhnEmailClient.sendEachMail`)에서 금지 이름, 형식이 틀린 이름, 틀린 값(빈 값·1000바이트 초과·줄바꿈·NUL), 대소문자만 다른 중복을 빼고 보낸다 (`src/lib/nhn-email-headers.ts`). 경고는 (이름, 까닭)마다 프로세스에서 한 번만 남기고 값은 적지 않는다. 이 종류의 실수가 다시 메일 전체를 막지 않는다
  - **화면**: 워크스페이스 설정의 "답장 받을 주소" 칸과 템플릿 테스트 발송 창의 "답장 받을 주소 (사업)" 고르기를 뺐다. AI 규칙 화면의 요약 칸은 "답장 — 보낸 주소로 갑니다"이고, 발신 프로필 칸은 묶음 주소 중 MX가 없는 도메인을 "이 주소들은 답장을 받을 수 없습니다 — 도메인에 메일 수신(MX)을 연결해야 답장이 옵니다"로 알린다 (워크스페이스 설정 링크 없음)
  - **MX 캐시**: 받는 도메인(ok)은 하루, 없음(none)·확인 못 함(unknown)은 10분. MX를 연결하면 10분 안에 안내가 걷힌다 (안내 상자 끝 줄에도 적었다)
  - **남겨 둔 것**: `workspaces.reply_to_email` 칸(지우는 마이그레이션 없음), 설정 API의 `replyToEmail` 읽기·저장·형식 검사·MX 조회, PATCH의 `requireAdmin`. 발송에는 쓰지 않는다
  - **그대로인 것**: 4-1절 두 가지 (`email_send_logs.sender_email`, 반복 대기열에서 `first`를 `first_bulk`보다 먼저)
