## 결론과 증거의 범위

발송 기록이 커지는 동안 자동 발송의 중복 확인과 고객별 이력 조회에 필요한 인덱스가 빠져 있었다. 개발자의 운영 수정 커밋은 이를 운영 DB 장애 원인으로 명시한다. 동일 쿼리 조건을 가상 로그 30만 건에 실행해 전체 스캔과 인덱스 추가 후 개선을 재현했다. 로그인 정보를 기다리는 화면에는 별도의 시간 제한·재시도가 없어, 서버 지연이 사용자의 무한 로딩으로 확대될 수 있었다.

운영에는 10월 22일 인덱스·쿼리 제한 및 세션 복구 수정이 이미 반영돼 있었지만, 조사 시작 시 dev에는 빠져 있었다. 이번 수정은 해당 변경을 dev에 맞춰 반영하고, 인덱스 생성 실패 복구와 정기 작업 잠금의 연결 점유를 보완한다.

**확정하지 않은 것:** 당일 최초 실행 SQL, 전체 중단 시간, 영향 사용자 수, 당시 DB 연결 수·잠금 대기·CPU. 재배포 뒤의 실행 로그에는 최초 장애 시점이 남아 있지 않았다. 운영 DB는 접근하지 않았다. 아래의 공유 풀 고갈은 코드상 위험과 로컬 재현 결과이며, 당일 실제 발생했다고 단정하지 않는다.

## 왜 지연이 커졌는가

1. `auto-personalized-email.ts`는 고객마다 `partition_id + recipient_email` 중복 확인과 `record_id` 쿨다운 확인을 한다. `email-automation.ts`도 `template_link_id + recipient_email`로 중복을 확인한다. 일치하는 발송이 **없는 신규 고객**은 `LIMIT 1`이 있어도 표 끝까지 검사할 수 있다. 이 확인이 고객 수만큼 반복돼, 발송 로그 증가와 대량 준비 작업이 겹치면 비용이 커진다.
2. 기존 dev의 조회 인덱스는 조직·발송일 및 요청 ID 중심이었다. 위 조건의 복합 인덱스와 record 인덱스가 없었다. 전체 이메일 검색도 제목/주소 `ILIKE '%검색어%'`에 합쳐져 정확한 주소를 입력해도 불필요한 부분 검색을 수행했다.
3. 애플리케이션 DB 풀에 기본 statement timeout이 없었다. 느린 쿼리가 연결을 오래 잡으면 같은 DB/풀을 사용하는 로그인 정보·상담 조회도 지연될 수 있다. PostgreSQL의 statement timeout은 서버에서 실행 중인 SQL의 제한이며, JavaScript 풀에서 연결을 기다리는 시간까지 제한하지 않는다. [PostgreSQL 설정 문서](https://www.postgresql.org/docs/current/runtime-config-client.html)
4. 별도로 발견한 구조적 위험: 잠금만 잡으려고 공용 풀 연결을 reserve하고, 실제 업무 SQL은 같은 풀에서 또 연결을 요청하는 정기 작업이 8개 파일에 있었다. 풀이 모두 예약되면 각 작업이 서로 반환을 기다릴 수 있다. 일부 경로는 unlock SQL 실패 시 뒤의 `release()`까지 실행되지 않았다. 세션 advisory lock은 해제하거나 세션이 종료돼야 풀린다. [PostgreSQL 잠금 문서](https://www.postgresql.org/docs/current/explicit-locking.html)
5. 기존 세션 화면은 `/api/auth/me`의 헤더 또는 본문이 끝나지 않으면 로딩을 끝낼 수 없었다. 일시적인 서버 오류와 실제 401도 사용자에게 다르게 처리할 필요가 있었다.

인덱스는 마이그레이션 트랜잭션에 추가하지 않았다. CONCURRENTLY는 트랜잭션 블록 안에서 사용할 수 없으며, 실패하면 INVALID 인덱스가 남을 수 있어 시작 경로에서 복구한다. [PostgreSQL CREATE INDEX 문서](https://www.postgresql.org/docs/current/sql-createindex.html)

## 실제 PostgreSQL 재현

`scripts/check-incident-db.ts`가 loopback 전용 PostgreSQL에 무작위 시험 DB를 만들고 30만 건을 삽입한다. `.invalid` 주소만 사용하며 테스트 후 자신이 만든 DB만 제거한다. 데이터 디렉터리·PID·포트·DB 이름을 검증하며 운영/개발 DB URL을 받지 않는다.

처음 세 개 중 record 조회는 기존 조직·시간 인덱스로 불필요한 행을 걸러냈고, 나머지 중복 조회와 전체 주소 조회는 전체 스캔이었다. 모든 개선 후 계획은 해당 인덱스를 사용했다. 자세한 결과: [가상 DB 검증 JSON](evidence/incident-db-evidence.json).

추가 실험: 유효 인덱스 재실행 시 OID 유지, 실패한 concurrent index의 INVALID 복구, 다른 인스턴스 동시 생성 방지, 일시적 테이블 잠금 해제 후 자동 재시도, SQL timeout 후 다음 조회 성공. 공용 풀 2개를 reserve하면 40ms statement timeout을 켜도 SQL이 연결 대기에서 끝나지 않는 현상을 재현했다. 수정 후 잠금 4개를 보유한 동안 별도 공용 풀의 조회 20개가 완료됐고, 다섯 번째 잠금 작업은 연결 없이 대기한 뒤 앞 작업 종료 시 실행됐다.

## 적용 범위와 남은 운영 확인

- 이 작업은 dev 커밋·푸시까지다. main 병합, 운영 배포, 운영 DB 조회/변경, 실제 고객 발송은 하지 않는다.
- 잠금 연결은 공용 풀 밖에 **최대 4개/프로세스**를 추가한다. 나중에 운영 적용할 때 기존 DB 한도에 공용 풀(기본 20), 잠금 4, 인덱스 생성 1, 그 외 전자서명·통계·다른 앱 연결을 합산해야 한다. 다중 인스턴스라면 인스턴스 수까지 고려한다. 이 커밋은 DB 서버 한도를 변경하지 않는다.
- 다른 종류의 워커가 업무 트랜잭션용으로 reserve하는 연결까지 전부 분리한 것은 아니다. 느린 SQL, 다른 서비스의 연결 포화, 긴 외부 API 호출은 별도 원인으로 남을 수 있다.
- FIFO 잠금 대기는 공용 풀을 점유하지 않는다. 단, 앞선 작업 자체가 끝나지 않으면 뒤 작업도 기다린다. 업무 큐/발송 선점·중복 방지 및 기존 API 제한은 유지한다.
- 최대 3회 인덱스 재시도가 모두 실패하면 로그의 인덱스 이름과 SQLSTATE를 보고 권한·디스크·장기 트랜잭션을 확인해야 한다. 10분보다 오래 걸리는 실제 대형 인덱스 작업은 별도의 유지보수 계획이 필요할 수 있다.
- 부분 문자열 검색은 기존 ILIKE를 유지하므로 모든 종류의 검색을 빠르게 만든다는 보장은 없다. 통계 대시보드 기능 전체와 기존 main/dev 차이의 일괄 병합도 이번 범위에 포함하지 않는다.
- 다음 장애가 발생하면 운영 담당자가 발생 시각·요청 경로·응답 시간, SQLSTATE 57014, DB 활성/대기 연결과 쿼리 계획을 함께 보존해야 최초 요청까지 확정할 수 있다. 이번 보고서는 그러한 당시 기록을 추정으로 채우지 않았다.
